The proposed flow and what changes
Write prompt / add media→+ · Repositories→@repos: · choose or switch repo→Repo chip in draft→Send / start workspace
  • The + button opens a two-row popover. Use a maximum height and scrolling when space requires it; two rows should not need an artificial scrollbar. The menu and repository autocomplete stay anchored to the composer on desktop and mobile, sized to fit the viewport.
  • Upload media retains the current image/video picker, paste, drag-and-drop, previews, and model restrictions. Disable only that menu item when images are unsupported. Today the entire + button is disabled in that situation.
  • Repositories is the permanent second menu item. After the GitHub App is connected, it opens the authorized repository list directly. Reopen it to switch repositories before starting; the selected repository chip updates while the prompt, model, and media stay intact. If GitHub is disconnected, show a short empty-state message linking to Settings → Connections. Keep authorization there and return to the saved draft and picker afterward. Do not open a connection panel or right sidebar from this menu.
  • Match the recording’s compact dark dropdown: a muted Repositories heading, GitHub icons, simple repository-name rows, rounded hover highlights, and full owner/repository details on hover or focus. Typing after @repos: filters the list; arrows and Enter choose a row, and Escape dismisses it. Show all repositories available to the connected GitHub App, including ones not yet imported into Nap. Fetch every page; do not restrict the list to existing Nap projects. Respect installation access and Nap’s permission requirements. Loading, empty, revoked-access, and retry states stay inside this popover.
  • Selection immediately updates the draft’s repository chip and closes the list. There is no Add to session confirmation. Branch and environment configuration remain outside the picker, in source settings before starting; keep preview optional and draft-PR publication configurable. Connecting and selecting are preparation steps. Create the imported project when the user sends the task. If only a repository is selected, offer Open workspace without inventing a task or starting a model run.
  • In an existing workspace, its repository stays bound. The GitHub action opens its details or offers Start new session from GitHub. It must not silently replace the current codebase.

The inline @repos: list, row styling, and absence of a connection drawer are observed in your recording. Nap’s two-action menu, single selected source chip, and switching behavior are proposed adaptations. The recording does not show the final selection result. Nap will not require Devin-style indexing to list authorized repositories.

Sidebar and thread management scope

Match Devin's spacing, navigation hierarchy, low-contrast surfaces, and footer placement. Use T3's richer thread cards for active work and compact rows for parked work. Start around a 256px desktop sidebar with a saved resize width, collapse control, and mobile drawer. The sidebar scrollbar must never be visible, including on hover or while scrolling. Keep wheel, trackpad, touch, and keyboard scrolling functional, with the account footer fixed outside the scrolling list.

The important app and data changes
Organizing work

Pin, order, unread, done, snooze, and archive determine where a row appears. These are new durable navigation metadata.

Running a workspace

Queued, working, failed, ready, and put away describe execution and sandbox state. A running sandbox is not proof that the agent is working.

  1. Preserve the current isolation model. Initially, one sidebar session continues to map to one Nap project and its current conversation. Starting another task on the same repo creates another isolated workspace. Existing project URLs and histories remain valid. Multiple independent conversations sharing one sandbox would require separate routing, lease, snapshot, and Git branch work; that is outside this navigation plan.
  2. Preserve drafts across authorization. The dashboard currently holds its draft in React state, while GitHub returns to Settings. Add an owner-bound draft ID and an allowlisted return destination to the connection flow. Save text, model, repo choice, and media before leaving; restore on success, cancellation, or failure. Use browser storage suited to media, such as IndexedDB, with expiry and sign-out cleanup. Stop navigation with a recoverable message if draft storage fails.
  3. Unify session creation. Extend the start flow to distinguish template and GitHub sources. Reuse #117's owner checks and import service. Carry the first prompt/model/media into the imported session and sequence it after workspace preparation. Use a stable operation ID so callback reloads, network retries, and repeated Send cannot create duplicate workspaces or submit the first task twice.
  4. Add navigation metadata and summaries. Store pin/order, done/archive state, snooze time, and a read watermark per owner/project. Use revision checks for ordering and Undo so a stale browser cannot overwrite a newer action. Return summary status, repo, PR, and pending-feedback count in a list endpoint; avoid opening every transcript or polling GitHub once per row.
  5. Make status truthful. Derive agent activity from the queue/job lifecycle and completed work from its terminal events. Use a separate workspace-running indicator if needed. New activity should clear or supersede stale Done/read state according to documented rules. Snooze hides the row until a time; it does not schedule a model run.
  6. Keep cloud lifecycle explicit. Done, snooze, and archive do not shut down a sandbox or merge a PR. Keep Put away as the resource-release action. Disable archive/done for active work in the first release rather than hiding a task that still needs attention; retain existing busy checks for deletion and shutdown.
Implementation order and acceptance checks
  1. Composer entry and GitHub return. Extract a shared plus-menu component and GitHub picker, persist the draft, add the return target, and integrate repo selection with session start. Check direct inline opening, every authorized repository page, filtering, keyboard selection, switching without losing the draft, disconnected/connected states, revoked access, no repos, cancel, failed setup, media-model restrictions, and double-submit recovery. Assert that no connection drawer, side panel, or dim backdrop opens.
  2. Shared sidebar shell. Refactor the existing sidebar used by both the dashboard and workspace. Apply the Devin layout, T3 card anatomy, settings footer, selected states, responsive drawer, and resize persistence. Preserve New session, search, rename, put away, delete, and account actions. Verify long-list scrolling with no visible scrollbar on desktop and mobile, including systems configured to always show scrollbars.
  3. Durable management. Add metadata and list summaries, then pin/order, read state, Done/reopen, archive/restore, snooze/wake, and Undo. Verify refresh, two tabs/devices, failed saves, old sessions, and status updates while another workspace is open.
  4. Interaction polish and parity. Add keyboard navigation, row context menus, focus restoration, accessible reorder, drag feedback, reduced motion, and large-list pagination. Then extend to bulk actions and optional automation policies after core state transitions are proven.

The finished path should let someone type a prompt, attach images, connect GitHub, pick a repo, and start work without reconstructing their draft. They should then be able to find, pin, reorder, park, and resume that work with the same sidebar on every Nap page.

Existing-PR import and a PR inbox remain in the broader GitHub roadmap from the previous comparison. A third plus-menu option or Review destination should appear only when that backend exists.
