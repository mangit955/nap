# Gotchas

Learned the hard way; don't rediscover them. `CLAUDE.md` routes here by area —
read the section covering whatever you are about to touch, not the whole file.

## Workspace, build and tooling

- **Packages resolve to TypeScript source**, via `"exports": { "./*": "./src/*.ts" }` in each `package.json`. Import as `@nap/shared/version`, not `@nap/shared`. There is no build step for tests or typecheck, and no root barrel to import from — which is what enforces the no-barrel-files rule.

- **Relative imports need an explicit `.ts` extension** (`allowImportingTsExtensions` is on in `tsconfig.base.json`). Safe because `tsc` never emits — Vite and Bun do the transpiling.

- **Adding a cross-package dependency requires re-running `bun install`** to create the workspace symlink, or the import resolves at typecheck but fails at runtime.

- **`bun run <script>` resolves against the nearest `package.json`, and a shell's cwd persists between commands.** A stray `cd` is enough for `bun run test` to quietly run a single package's scripts, or for `bun add` to install into the wrong workspace — both of which have happened. Run from the repo root unless you specifically mean not to.

- **Anything the root `vitest.config.ts` imports must be a *root* devDependency.** `@vitejs/plugin-react` installed into `apps/web` fails at config load with `ERR_MODULE_NOT_FOUND`, because the config resolves from the root.

- **A `PostToolUse` hook reformats each file after you write it.** So an `Edit` whose `old_string` came from text you wrote earlier in the turn can fail to match — Biome may have reflowed it. Re-read the file rather than guessing at the diff.

- **`next dev` writes `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` itself**, and re-creates them if deleted. They are committed so the tree stays clean. The generated note is worth heeding: Next 16 differs from what most training data assumes, and `apps/web/node_modules/next/dist/docs/` is the version-accurate reference.

- **Turbo runs tasks in strict env mode**, so an exported variable does *not* reach a task unless it is listed in that task's `passThroughEnv` in `turbo.json`. `DATABASE_URL=… bun run dev` silently produced a "missing DATABASE_URL" boot failure until `dev` declared it. The normal path is a `.env` file, which Bun auto-loads from the app directory.

- **Bun installs and dispatches; Node executes.** `bun run` honours a binary's shebang, so Vitest and Next.js run under Node. Only `apps/api` and our own entrypoints use the Bun runtime. This is deliberate — see "Bun/Node split" in `docs/PLAN.md`.

- **The integration suite loads `apps/api/.env` itself**, via `test/integration-setup.ts`. Bun auto-loads that file for the API, but Vitest runs under Node, which does not — so without it every integration run would need the variables exported by hand.

- **`process.loadEnvFile` is a Node API that Bun does not implement.** It is fine in `test/integration-setup.ts` (Vitest → Node) and throws in anything run by `bun run`. Scripts under `bun run` parse the file themselves.

- **A test in `test/` can only import a workspace package if the *root* `package.json` depends on it.** Bun links `@nap/*` into the root `node_modules` for the packages something depends on, and nothing depended on `@nap/agent` or `@nap/context` — so `test/project-root.test.ts` failed to resolve them until they were added as root devDependencies. Same rule as `@vitejs/plugin-react`: resolution for repo-level files happens from the root. `test/architecture.ts` reads only `packages/*` and `apps/*` — their manifests and their `src` — so root devDependencies do not disturb it.

- **Hoisting makes an undeclared workspace import work anyway.** Every `@nap/*` package is linked into the root `node_modules`, so a package can import a sibling it never declared and have it resolve, typecheck and pass CI — and because the deployed image is one workspace-wide install from `COPY . .`, it ships. `checkSourceImports` in `test/architecture.ts` is what catches it: it reads the specifiers in each package's `src` and `scripts` rather than its manifest, which is where a layering violation is actually written.

- **Biome lints HTML, which makes it a participant in any corpus of deliberately bad pages.** `apps/napbench/fixtures/` holds nine hand-written applications the product judge has to be able to tell apart, and several are bad on purpose — inline `onchange` handlers, no stylesheet, decorative SVGs with no title. Biome 2.5 parses `.html` and reported 69 errors against them, all of them describing the fixture correctly. The directory is excluded in `biome.json` rather than the rules being relaxed: linting a specimen would make our lint configuration part of the corpus's design, and the benchmark would end up measuring adherence to it. The TypeScript beside them is inside every gate as usual.

- **`apps/web` imports workspace packages only because `next.config.ts` lists them in `transpilePackages`.** They resolve to raw TypeScript source (`"exports": { "./*": "./src/*.ts" }`, no build step), which Next otherwise treats as published JavaScript and fails to parse. `bun run build` is the only gate that catches a missing entry — the vitest projects resolve through Vite and do not care.

## Types and data contracts

- **`Omit` over a discriminated union silently collapses it.** `Omit<NapEvent, "seq">` flattens every member into one object whose `type` and `payload` are independent unions — so `tool.call` would accept a `turn.failed` payload, and adding `seq` back no longer yields a `NapEvent`. Distribution needs a naked type parameter: `T extends unknown ? Omit<T, K> : never`. `packages/shared/src/ports/event-store.ts` exports a `DistributiveOmit` doing this — use it rather than writing a second copy. The type tests caught this; nothing at runtime would have.

- **`created_at` is `timestamptz`, so the driver returns a `Date` — but the event contract types `createdAt` as an ISO string.** Whatever implements `EventStore` maps it with `.toISOString()`. `packages/db/src/schema.ts` explains why the column stays a real timestamp.

- **`apps/api` env is validated at boot by a pure `parseEnv(record)`**, not by reading `process.env` at import time. Keep it that way — it is what lets the env tests run without mutating global state, and it keeps boot order independent of import order.

- **A field added to an event payload has to default, or every session written before it becomes unreadable.** Rows are parsed against `NapEventSchema` on the way out of Postgres, and a strict payload with a new required key rejects the payload that was written last week — replay throws, and the failure surfaces as a session that will not load rather than as a schema mistake. `turn.started`'s `source` is the one field carrying a `.default()` for this reason, and the default has to be a *fact* about the old rows (a turn recorded before there was a verifier to prompt one was prompted by a user), never a placeholder.

- **An event read back from Postgres is never string-identical to the one that went in, so comparing the two raw finds no match.** `created_at` is `timestamptz`: `…T12:00:00Z` returns as `…T12:00:00.000Z`. This only matters in one place and it matters a lot there — `PostgresEventStore.append` deciding, on a retry, whether the interrupted attempt already committed. Compared raw, the answer is always "no" and the event is written twice, which is a duplicated message in somebody's chat rather than a failing test. Normalize through `new Date(...).toISOString()` before handing anything to `isSameEvent`.

- **Content alone cannot identify an event, because a turn legitimately emits the same one twice running.** Two `command.output` chunks carrying the same text in the same millisecond agree on type, session, turn, `createdAt` and payload — everything but `seq`, which is the field in doubt. A retried append that matched on content alone would read the *previous* event as its own lost write, drop the new one and hand back a `seq` already published. `AppendOptions.retryAfterSeq` is a watermark for exactly this: rows at or below it were durable before the attempt began, so only what came after it can be the attempt's own.

- **A `Proxy` cannot reach a class's `#private` fields.** The receiver becomes the proxy, so any method touching `#state` throws `TypeError: Receiver must be an instance of class`. Wrapping an object that has private state means spelling out the delegated methods.

## Model and provider

- **Read the `claude-api` skill once per milestone that touches the Anthropic API, and pin what you learn here as a gotcha.** Never answer from memory — the model id, `effort: "xhigh"`, `display: "summarized"`, `stop_reason: "refusal"` handling and tool-call mechanics are all details that change, and the intelligence plane is where a stale recollection costs most. But do not re-read it per task either: the skill inlines its whole documentation set, most of which (Managed Agents, Bedrock, Vertex, model migration) can never apply here, and it dominated one session's context to answer a single question about tool-definition shape. The first task of a milestone reads it and writes the answers down; every task after that reads *this file*. A written record is not recollection — the `usage.input_tokens`, `signal`-argument and `maxRetries` notes below are exactly that, captured once and load-bearing ever since.

- **`usage.input_tokens` from the Anthropic API is the *uncached remainder*, not the input total.** Cache writes and cache reads are billed and reported in their own fields (`cache_creation_input_tokens`, `cache_read_input_tokens`), so a heavily-cached call can report a few hundred input tokens against a prompt of tens of thousands. `toTokenUsage` in `packages/agent/src/claude-provider.ts` sums all three, because a budget built on the unsummed number would be wrong by most of the prompt. There is a test pinning this.

- **The Anthropic SDK takes `signal` in its *second* argument, not the request body** — `messages.stream(body, { signal })`. And under `exactOptionalPropertyTypes` a narrow client type must say `signal?: AbortSignal | undefined`, since "absent" and "present but undefined" are different types and no-signal is the normal case.

- **A throttled model arrives as a 200 that fails halfway through, and no status code goes with it.** OpenRouter accepts the request, starts the stream, and reports the upstream rate limit as an SSE `error` frame; `core/streaming.js` turns that into `new APIError(undefined, body, …)` — **`status` is `undefined`** and the only clue is `type`, copied from `body.error.type` (`rate_limit_error`, `overloaded_error`). Every status-based retry rule is blind to it: `RateLimitError` is constructed *only* from a 429 response, so `isRetryable` gave up on the first attempt and a turn that three retries would have saved died instead. Worse, `APIError.makeMessage` looks for `message` at the *top* of the body, does not find it one level down at `body.error.message`, and falls back to `JSON.stringify(body)` — which is how a wall of vendor JSON ended up in a user's chat. Match on `type` before `status`, and pull the sentence out of the body yourself (`describeError`). A rate limit also needs its own backoff: half a second is right for a dropped socket and spends all three attempts inside the same per-minute window.

- **The SDK's own retries are invisible to a test.** `new Anthropic()` retries twice by default, so a provider that also retries makes three attempts look like nine and "gives up after N" unprovable. `ClaudeProvider` constructs the client with `maxRetries: 0` and owns the loop.

- **All of a turn's `tool_result` blocks go back in one user message.** Parallel tool use is on by default: a single assistant message can carry several `tool_use` blocks. Answering them in separate user messages is accepted by the API and quietly trains the model to stop asking for tools in parallel — the failure is a slower agent, never an error. Execute the batch, then send every result together, including the failures: a failed tool is a `tool_result` with `is_error: true`, never a dropped block. This is the shape `executeTool`'s `ok` field exists to feed.

- **`@anthropic-ai/sdk` and `@anthropic-ai/claude-agent-sdk` are different products.** The first is the Messages API client this repo uses. The second is Claude Code packaged as a library — it owns the agent loop and ships the built-in `Read`/`Write`/`Edit`/`Bash`. We want neither of those: the loop has to emit typed events and be cancellable, and the only tools that may exist are the six that proxy to `SandboxManager`. The plan originally specified the second one — see the amendment note in `docs/PLAN.md` §0 for why it did not survive contact with the testing strategy.

- **A tool call and its result travel together or not at all.** The API rejects a `tool_use` block with no answering `tool_result`, and vice versa — so anything shortening a conversation to fit a budget cannot simply delete the biggest block it finds. `NapContextEngine` reclaims tool output by replacing the *content* while keeping the block and its `toolCallId`, and drops history a whole turn at a time so both halves leave together. Deleting a result to save tokens does not produce a smaller request, it produces a 400. There is a test asserting no orphan in either direction, at five budgets.

- **A turn's bill is the assembled context *times* its step count, and the context budget does not cap it.** Two different ceilings, and the one that fires is not the one people reach for: `NAP_CONTEXT_BUDGET_TOKENS` caps a single request, `TurnBudget`'s `DEFAULT_MAX_TOKENS` caps the sum over a turn's round trips, and every round trip re-sends the whole transcript. A real four-turn session died on the second while sitting at a fifth of the first, which means **the truncation ladder can be perfectly correct and never run**. The consequence for anything that adds to the prompt: a kilobyte of context is a kilobyte charged ten to forty times, so "it fits" is not the test — and if you are about to raise a ceiling, measure which one first. `NapContextEngine`'s staleness pass is what came of that. **ADR-0011 has the numbers**, and `packages/context/scripts/measure-audit-session.ts` reproduces them against a committed log for free; don't copy them here, two copies of a measurement is one that goes stale.

- **The system prompt has no "verify your work" instruction, and that is the design.** `claude-opus-5` already checks its own work; telling it to do so again produces redundant tool calls and long reports *about* the checking rather than fewer mistakes, and removing such instructions costs no capability. The omission reads as an oversight, so `system-prompt.test.ts` fails on a phrase list plus any `/\bverif/i` match. If you are about to "improve" the prompt by adding a verification step, that is the thing this is here to stop.

- **The prompt's facts must match `packages/sandbox/template/` exactly.** The first draft claimed a `public/` directory the template does not have and said nothing about Tailwind v4 having no config file. Neither produces a confused agent — both produce a confident one, writing files nothing serves. Tests pin both.

- **The context token budget is a cost limit, not the model's context window.** `claude-opus-5` accepts 1M tokens; `DEFAULT_BUDGET_TOKENS` is 120k, and the gap is deliberate — a bigger window is not a reason to raise it. Token counts are a local estimate (~4 chars/token) because the exact number is a network call per string, which would make the budget untestable and every turn a round trip.

- **Anything that can spend real money defaults to the free path.** `ClaudeProvider` takes `model`, `effort` and `maxTokens`; `bun run harness` runs on `ScriptedLLMProvider` + `InMemorySandboxManager` unless given `--real`, and a real run defaults to Sonnet at `medium` with 12 steps and a 40k context budget. The fakes exercise the same composition the real components plug into, so the wiring is verifiable for free and spend is reserved for what only a real API can prove — the request shape, and that a real sandbox ends up with a real commit. Build the free half first, and ask before spending.

- **Bedrock is a transport, not a vendor — and its client throws before it ever reaches the network.** `packages/agent/src/bedrock.ts` reaches the same models through an AWS account: same Messages API, same `tool_use`/`tool_result` blocks, same streaming, same refusal semantics, so nothing above `LLMProvider` can tell the difference. Only two things change — the client class and an `anthropic.` model-id prefix. `AnthropicBedrockMantle` **throws at construction** when no region resolves from `awsRegion`, `AWS_REGION` or `AWS_DEFAULT_REGION`, which is why callers check for a region themselves rather than letting a stack trace stand in for a sentence. A Bedrock API key goes in as `apiKey` (bearer) or `AWS_BEARER_TOKEN_BEDROCK` — no SigV4 needed. None of this weakens the no-second-vendor rule below; that rule is about *different vendors*, whose failures are silent.

- **OpenRouter is the only route this project uses, and it reaches every vendor's models — not just Anthropic's.** It publishes a *native Anthropic Messages endpoint*, so `@anthropic-ai/sdk` reaches it with `baseURL: "https://openrouter.ai/api"` — note the root, not `/v1`, because the SDK appends `/v1/messages` and a doubled `/v1/v1/` 404s in a way that reads like the service is missing. **Their docs hedge that the endpoint is designed for Anthropic models; that is not a restriction, and it was measured rather than assumed.** A request to `openai/gpt-5.6-luna` comes back as a well-formed `tool_use` block with `stop_reason: "tool_use"`, accepts `cache_control` markers without complaint, and — the part that matters — reports `usage` in *Anthropic's* shape (`cache_read_input_tokens`), not OpenAI's `prompt_tokens_details.cached_tokens`. That is what keeps `toTokenUsage` honest, and it is exactly why nothing goes near the OpenAI-shaped `/chat/completions` endpoint, which returns the other shape and would make `TurnBudget` under-count silently. **Mind the separator** — OpenRouter namespaces with `anthropic/`, Bedrock with `anthropic.`; `toOpenRouterModel` therefore passes through any id already containing a `/` and prefixes anything else, so `openai/gpt-5.6-luna` survives and a bare `claude-sonnet-5` still becomes Anthropic's. Pricing is each vendor's own plus a top-up fee, so Claude through here is Anthropic's price and buys *access*, never savings; the savings come from choosing a cheaper model.

- **OpenRouter reserves the whole of `max_tokens` against your balance before the request runs, which Anthropic does not.** Anthropic bills tokens *generated*, so a high ceiling on a short answer is free; OpenRouter treats the ceiling as admission control and answers `402 "You requested up to 64000 tokens, but can only afford 418"` before the model sees anything. So `DEFAULT_MODEL_CONFIG.maxTokens` (64k) needs roughly $1.60 of credit on Opus 5 just to be *allowed* to ask a one-line question. Budget by the ceiling on this route, not by the expected answer. The failure costs nothing and is not retried — `isRetryable` only retries 5xx, rate limits and dropped connections, so a 402 stops at the first attempt.

- **OpenRouter does not implement `messages.countTokens` — it 404s** — and that turned out to be a better test rather than a worse one. Counting the prefix and comparing it to the documented minimum only supports an *inference* that caching will happen; a non-zero `cache_creation_input_tokens` on a real call **is** the claim. `prompt-caching.integration.test.ts` now sends the real `SYSTEM_PROMPT` + `TOOL_DEFINITIONS` and asserts on the counters, which works on every route. Related and sharper: **an assertion that a cache entry was *written* is clock-dependent.** An entry lives ~5 minutes, so re-running inside the TTL finds the prefix warm — `cache_creation_input_tokens` is 0, `cache_read_input_tokens` is thousands, and the test fails against code that is working perfectly. The fix is to salt the prefix with a `crypto.randomUUID()` line so every run starts cold; without it the test measures how recently you last ran it.- **Debug on `openai/gpt-5.6-luna`, demo on `anthropic/claude-opus-5`.** Most turns during development are spent debugging the loop — event ordering, tool sequencing, did the commit land — which needs a model that returns well-formed tool calls, not a good one. Luna is ~$0.10/$0.60 per MTok against Sonnet 5's $2/$10, so an afternoon of running the loop costs cents rather than dollars; that is the whole reason it is the `NAP_MODEL` and `HARNESS_DEFAULTS` default. **What crossing vendors actually costs is two things, and OpenRouter's translation absorbs both:** `toTokenUsage` sums `input_tokens` with both cache fields because Anthropic reports the uncached remainder, where OpenAI's `prompt_tokens` already includes cached tokens — same code, double count; and Anthropic answers N tool calls in **one** user message where OpenAI wants N `role: "tool"` messages, inverting the rule `agent-service.test.ts` pins. Going through the *Anthropic* endpoint means OpenRouter normalises both before we see them, which is measured, not assumed. **What it does not absorb:** the system prompt's deliberately missing verification instruction is tuned to Claude, so prompt-quality regressions on a cheap model are a property of the model and not a bug to chase. `packages/shared/src/ports/llm-provider.ts` is still the seam that would carry a genuinely different vendor SDK in v2.

- **Prompt caching is a prefix match, and the minimum prefix is per-model and *not monotonic*.** The API renders a request as `tools` → `system` → `messages`, so `ClaudeProvider` puts one `cache_control` marker on the system block (which covers the tool schemas rendered before it) and one on the last block of the last message (which covers the conversation so far). A prefix shorter than the model's minimum **silently does not cache** — no error, just a zero in `cache_creation_input_tokens`. The minimums do not follow model recency: **512** on `claude-opus-5`, **1024** on `claude-sonnet-5`, 2048 on Opus 4.7, 4096 on Opus 4.6 and Haiku 4.5. Sonnet 5 is the `NAP_MODEL` default *and* the stricter of the two we run, so 1024 is the number that binds; our tools+system prefix estimates at ~1188 by the local 4-chars/token rule, which is not a comfortable margin — `prompt-caching.integration.test.ts` measures it with `count_tokens` rather than trusting the estimate.

- **Use explicit per-block `cache_control`, never the top-level automatic form.** The SDK accepts a top-level `cache_control` that places the breakpoint for you, and it is simpler and wrong here: automatic caching exists only on the first-party API, so Bedrock — a transport T-12 deliberately built — would silently stop caching. Per-block markers work everywhere. Related: a breakpoint walks back **at most 20 content blocks** to find a prior entry, which a tool loop can exceed in three steps if it stops moving the marker to the end.

- **A marker on the system prompt only pays off while the prompt is byte-identical.** `NapContextEngine` assembles `systemPrompt` as the contract *plus the file listing*, so the prefix changes the moment the agent writes a file and cross-turn hits stop. Within a turn it is built once and reused on every step, which is where the saving actually is — a 12-step turn reads it 11 times. Moving the listing into the first user message would fix the cross-turn case and would change the prompt that `system-prompt.test.ts` pins with a snapshot; that is a deliberate separate task, not a tidy-up.

- **Both the reasoning and the answer are streamed, coalesced, and folded back together at every layer that reads them.** The model's `thinking` and `text` deltas arrive on the SDK's `MessageStream` (`stream.on("thinking" | "text", (delta, snapshot) => …)`; the wire events are `content_block_delta` with `delta.type` of `thinking_delta` or `text_delta`, and the helper hands over *the piece, then the running total*, so forwarding the second argument repeats every earlier word in every event). `ClaudeProvider` forwards them to `LLMRequest.onThinkingDelta` and `onTextDelta`; `AgentService` buffers each through a `DeltaStream` that flushes at 120 characters or 400ms, whichever comes first, and emits `agent.thinking` and `agent.message` events. That keeps a turn at a few dozen rows instead of thousands and leaves the durable-append-then-fanout path untouched, so a reload mid-turn replays what has been written so far. **The assembled `result.text` is emitted only when nothing was streamed** — both halves of that are load-bearing and each is a mutation: emitting it as well prints the whole answer twice, and dropping the fallback means a model or route that sends no text deltas says nothing at all. **The flush sits before the refusal and error branches**, since a turn that failed is where the reasoning is the only account of what happened. Two request-level facts are easy to undo by accident: `display: "summarized"` is required, because the default on `claude-opus-5` is `"omitted"` — which still streams thinking blocks but with empty text, so the symptom is silence rather than an error — and a retried attempt is a new stream that re-sends its reasoning from the start.

- **Whether reasoning comes back is a property of the *model*, not of the route — and the cheap model is the one that talks.** Measured twice on the same endpoint, same request, same `thinking: { type: "adaptive", display: "summarized" }`: `anthropic/claude-opus-5` produced **no** `agent.thinking` events across five model calls, while `openai/gpt-5.6-luna` produced five in one turn, carrying real summarized reasoning. An earlier version of this note concluded from the Opus run alone that OpenRouter's Anthropic endpoint drops thinking deltas; that was wrong, and it was wrong in the direction that would have sent someone to rewrite the transport. **Do not generalise a capability from one model to a route.** OpenRouter documents reasoning only for its *unified* OpenAI-shaped API — a `reasoning` parameter returning a `reasoning` field — which is still the endpoint this repo must not use, because its `usage` shape would make `TurnBudget` under-count silently. The Anthropic-shaped endpoint forwards what the upstream model emits, and that is model-specific.

- **A coalescing window belongs to the buffered text, not to the stream.** `DeltaStream` originally started its window at construction; a model takes seconds to produce its first token, so that window had always expired by the time the token landed and the delta was emitted alone. The first real turn printed `I` / `'ll look at the current app first.` and `There` / `'s now a button…`. The window now opens when text first enters the buffer and closes with it. Worth knowing what this did **not** fix: threshold chunking always leaves a remainder, so the piece after the last flush can be a single character — a real run ended a message with `.` on its own event. That is invisible in the pane, because the transcript folds a run of `agent.message` events into one paragraph, and it was invisible for the leading fragment too. **The fragments were never a rendering bug; they were an event-log one**, and the fix is about not writing a row per character.

- **Prose in pieces has to be rejoined in two places, and neither is optional.** `NapContextEngine` appends to the open assistant *text block* rather than pushing a new one, so the conversation the model is re-sent looks the way it did when it wrote it — one answer, not a paragraph broken at whatever sizes the network delivered, and not a message that grows a content block per event. `buildTranscript` does the same for the pane. Both join text only to text from the same speaker: a tool call between two pieces of prose means the model said two things, and folding across it would attribute the second half to before the tool ran. **A short answer looks identical either way** — its deltas coalesce into one event — so any test meaning to prove streaming needs prose long enough to cross the flush threshold, or it passes against code that streams nothing.

## Sandbox and storage

- **A project's thumbnail can only be taken while its sandbox is alive, so it is taken at every moment one is known to be up — and only those.** A preview URL answers for exactly as long as the sandbox behind it, and the dashboard is looked at days later with nothing running, so the card shows the app as of the last such moment: the end of a turn that committed, a project coming back up (`#resumeLogged`, gated on `created` — a sandbox that was already serving has not changed since whatever last photographed it), and the instant before a close or a reaper sweep destroys the sandbox (`putProjectAway`, before `tearDownProject`). **Turn-end capture alone is not enough and the reason is worth remembering**: it leaves every project made before the browser existed with no picture and no way to get one short of paying for another turn, which is exactly the state this repo was in the day captures shipped. The close path takes deliberately shorter deadlines than the turn path, because a person is waiting on that request. In all four places a failure is a log line and nothing more — the sandbox still has to be snapshotted and destroyed, and refusing to close one over a screenshot would trade a billing problem for a cosmetic one. Three further constraints hang off it. It uses **`waitForPreview`, not `getPreviewUrl`**: the second only composes an address, and a screenshot of an address nothing answers at is a picture of an error page, indistinguishable from the user's app being broken. Its key is **derived from the project id and overwritten**, so unlike a snapshot there is no row naming it — which makes it the one object a delete cannot find by listing, and `deleteProject` removes it explicitly and deliberately leaves it out of `objectsDeleted` (deleting a key that was never written succeeds, so counting it would claim an object was removed for every project that never had a picture). And the capture is **behind the `PageCapture` port with the browser optional**: `NAP_CHROME_PATH` unset means turns run exactly as before and the card falls back to the colour hashed from the project id, which is what every card showed before this existed. On the client the image is a plain `<img crossOrigin="use-credentials">` — the API is another origin, so without that attribute the request carries no cookie and every card 401s, and `next/image` is not an option at all because its optimizer is a server holding none of the user's credentials.

- **E2B's contract differs from ours in three places**, all resolved in `packages/sandbox/src/e2b-sandbox-manager.ts` and all found by running the conformance suite for real. `commands.run` **throws `CommandExitError` on any non-zero exit** — ours treats a failing command as data, so the adapter converts it; without that, a failing build reaches the agent as an infrastructure fault. `AuthenticationError` extends `Error`, **not** `SandboxError`, so an `instanceof SandboxError` catch-all silently misses a bad API key. And E2B validates the *shape* of a sandbox id before looking it up: an arbitrary string is `400: Invalid sandbox ID`, not a 404, which is why the conformance harness supplies `unknownSandboxId()` rather than inventing one.

- **The sandbox project template is built by hand** — `bun run template:build` in `packages/sandbox`, never by a test. It publishes a named, billable artifact that later sandbox creation depends on. `packages/sandbox/template/` is a separate app with its own React/Vite toolchain: it is outside our tsconfigs on purpose, so the only thing that type-checks it is a `tsc` run *inside* a sandbox, in the integration suite. That check earned itself immediately by catching two broken imports.

- **The template's `scripts` are the entire surface the verification loop can see, and an edit to them is not live until the template is rebuilt.** `@nap/verify` discovers checks by package-script name, so adding or removing one means editing `packages/sandbox/template/package.json` *and* running `bun run template:build` — and projects created from an older image keep the old manifest in their git history, so they stay blind until they are recreated. Neither the free suite nor a dry run can tell you which image is published: `test/template-checks.test.ts` reads the manifest from disk, and an in-memory sandbox has no `package.json` to discover from at all. What that blindness costs is recorded in `docs/napbench-verification-measurement.md`.

- **Anything from a model that reaches a command line must be shell-quoted.** `shellQuote` lives in `packages/shared/src/shell.ts` because two unrelated callers need it — git commit messages and the `search_files` grep pattern — and the attacker is whatever the user typed into a chat box. The one deliberate exception is `run_command`'s command itself: quoting it would turn a pipeline into a filename, so what may run is the safety guard's question instead — `packages/agent/src/safety/commands.ts`. Quoting is verified by round-tripping hostile inputs through a real `sh` in the unit tests — asserting on the *shape* of the quoted string does not distinguish safe from unsafe, because the payload text is present either way.

- **A bound port is not a loadable preview.** E2B's `waitForPort` readiness check fires when something binds the port *inside* the sandbox, but users reach it through a public proxy that becomes ready separately, and its 502s during that gap are "not yet" rather than "broken". `waitForPreview` on the `SandboxManager` port polls the real URL for a 200; anything showing a preview should wait on that, not on `getPreviewUrl`, which only composes an address and promises nothing.

- **"Missing" and "could not tell" are different failures, and only one of them may fall back.** Opening a project restores its last snapshot; a snapshot that is *absent* or that git refuses falls back to a fresh template with a `system.notice`, because the work is gone either way and an error page in place of an app helps nobody. A store that cannot be *reached* fails the open instead — hand back an empty template on a transient outage and the next teardown snapshots the emptiness over a good snapshot. The same reasoning orders `packages/runtime/src/restore.ts` the opposite way round from `teardown.ts`: fetch the row and the bytes *before* creating a sandbox, so a storage failure costs nothing and leaves nothing running to be billed for.

- **The project template's `bun.lock` is tracked, which is what makes "install only if it changed" possible.** `bun install` runs during the image build and writes the lockfile into the workdir *before* `git init`, so it is in the initial commit and travels in every bundle. A restore compares the lockfile before and after unbundling, and skips the install when they match — which is what keeps opening a project at seconds rather than a minute. Nothing there boots Vite, either: `setStartCmd` already did that as part of sandbox creation.

- **E2B kills a sandbox five minutes after it is created, whatever is happening inside.** `defaultSandboxTimeoutMs` is 300 000 and the timer starts at creation, not at the last thing anyone did — so a conversation that pauses for a coffee comes back to a workspace that no longer exists, and a reaper meant to snapshot idle projects loses that race every time. Sandboxes are created with an explicit `timeoutMs` and every turn pushes the deadline back through `SandboxManager.extendTimeout`. **The relationship between the two numbers is load-bearing: the reaper's idle threshold must stay below the sandbox TTL**, because the reaper snapshots before destroying and E2B's timer does not. `apps/api/src/env.ts` refuses to boot when they are the wrong way round.

- **The reaper destroys sandboxes it cannot find in the database, and the two guards on that are the whole design.** A sandbox created a moment before the row recording it failed is running, billed, and named nowhere — the only way to find it is `SandboxInventory.list()`, asking E2B what it is running. That capability is dangerous in exactly one direction, so `reconcileCapacity` (`packages/runtime/src/reconcile-capacity.ts`) refuses to use it twice over. **A failed read of the reference set returns immediately rather than carrying on with what it got**: everything below destroys what is *missing* from that set, so an unreachable Postgres would otherwise read as "nothing is referenced" and take the entire estate with it. And **nothing younger than a five-minute grace window is touched**, because a sandbox exists for a moment before anything is written down about it — without the window this pass races every acquire in the cluster and wins some of them. Two further guards are about *whose* sandbox it is, and the second is the one nobody expects: a sandbox with no `projectId` in its metadata was made by something else sharing the account — and a sandbox whose `projectId` this database has never heard of belongs to **our own tooling**. `bun run harness --real` and a funded NapBench run both create sandboxes on the same E2B account against a throwaway database or none at all, so a deployed reaper that destroyed everything it could not account for would kill a benchmark run five minutes in. The same reasoning runs the other way in `PostgresCapacityReconciler`, where an `active` row is only believed stranded once it is older than the same kind of window: reclaiming a healthy row does not destroy anything, but it un-counts a live sandbox, which raises the ceiling that exists to cap the bill.

- **R2 is the S3 API, so the adapter is `@aws-sdk/client-s3` with `region: "auto"` and an account-scoped endpoint** — the bucket is a path, not a hostname. Failures are mapped by `name` and HTTP status rather than `instanceof`, because a missing object arrives as `NoSuchKey` from one call and `NotFound` from another, and the two mean the same thing. Keep `not_found` and `unavailable` apart at all costs: restoring a project falls back to a fresh template for the first and refuses to open for the second, so collapsing them loses work.

- **In the E2B base image, `/usr/local/bin` precedes `/usr/bin` on PATH.** Installing a newer Node from NodeSource lands in `/usr/bin` and changes nothing — `node --version` still reports the image's 20.9, silently, until something refuses to start. The template build relinks the binaries; anything else installing tooling into that image needs to do the same.

- **Deleting a project runs the opposite way round from putting one away.** Teardown writes everything down *before* destroying anything; a delete destroys in the order that keeps a retry possible — sandbox, then the R2 objects, then the rows. The snapshot rows are the only record of which objects exist, so deleting them first strands every bundle: unreferenced, unfindable and billed forever. `packages/runtime/src/delete-project.ts` stops before touching the database if any object delete fails, which is safe because `ObjectStore.delete` treats a missing key as success and the whole call can simply be made again.

- **A turn's work reaches R2 at the end of that turn; the reaper exists to stop paying for idle sandboxes, not to keep work safe.** That split is recent and was earned. Snapshots used to happen only in `putProjectAway` — close, or the reaper — and the reaper runs in this process, so a deploy or a crash left E2B's own timer to delete the only copy of everything since the project last went idle. `captureSnapshot` in `packages/runtime/src/teardown.ts` is a teardown minus the destroy, and `SingleAgentRuntime` calls it after the turn's terminal event is persisted, so nothing the user waits on is delayed. **Only when the turn committed** — a git bundle holds commits, not a working tree, so a turn that changed nothing (and a turn that failed before `finalize`) has genuinely nothing new to capture. **A failed snapshot never fails the turn and is never shown to the user**: the work is still in the live sandbox, the reaper is still the backstop, and a warning nobody can act on is what trains people to ignore the ones that matter. Consequence worth knowing: `tearDownProject` now **reuses an unchanged snapshot** rather than re-bundling, because arriving at an already-stored commit is the normal case once turns snapshot themselves — but a `latestFor` that *fails* must fall through and capture, since knowing whether it changed is an optimisation and the snapshot is not.

- **A project outliving its sandbox is announced, and resuming one runs on the turn queue.** Nothing used to say that a sandbox had been destroyed, so a preview pane kept an iframe pointed at a host that had stopped existing — the provider's "not found" page rendered inside a frame that otherwise looks like a working app. `putProjectAway` now appends **`preview.stopped`** to *every* session of the project, keyed to the destroy rather than to the bookkeeping (a failed row update still means the sandbox is gone) and deliberately silent on the one path that leaves it serving. Bringing a project back is `Runtime.resumeSession`, and it is **serialised against `runTurn` per session** — that is the whole reason it can be offered at all, since both paths create a sandbox when the project has none and a page that resumes while its user types would otherwise start two. That serialisation is the per-session *lease* now, not the in-process `SessionQueue`; both entry points enqueue a request and a worker claims it. Its failures are a `system.notice`, never a `turn.failed`: no turn ran, and `previewState` reads a sandbox failure as the state of the last turn. `POST /projects/:id/open` applies **the same sandbox quota a turn does**, because a ceiling with two doors is not a ceiling. The one thing still not announced by anyone is a sandbox the provider reclaims on its own timer, which is why the preview pane trusts `project.sandboxId` over a replayed `preview.ready` until somebody presses Resume.

- **Opening a project is the only thing that continues a job, and most opens continue nothing.** A process restart leaves a job open rather than failing it, and nothing sweeps for those — an autonomous loop spending tokens with nobody watching is a bill, and a crash loop plus auto-continue is a large one. `resumeSession` folds the log through `continuationFor` (`packages/runtime/src/continue-job.ts`, pure, so what an open costs is a table rather than a trace) and gets one of four answers, three of which spend nothing. **The log is not the only input, because it cannot be**: a turn commits inside `finalize` and the sha reaches the log only with `turn.completed`, so a worker dying in that gap leaves a real commit in the sandbox and a log saying nothing was committed — read from the log alone, that job closes `unverified` and the work sits permanently outside the verification loop. The restored workspace's own `git rev-parse HEAD` goes in beside the fold as evidence, and wins wherever it can be read, since it is the commit the checks are about to run against. It is read only once a job is found open, so the opens that continue nothing still cost no round trip; a HEAD that cannot be read at all falls back to the log. Two of its rules are counter-intuitive and both come from `foldJobs` counting repair attempts from **`verification.started`**. A round that was begun and never answered is *finished* rather than begun again — writing a second `verification.started` for the same round consumes an attempt no repair turn ever used, which is what `announce: false` exists for. And a job left `repairing` is repaired **from the failure the log recorded**, not by re-running the checks: the commit has not moved, so re-asking learns the same thing and costs an attempt for it. That is why `VerifiedCheck` and `RanCheck` meet in a `CheckFailure` — the log keeps no `detail`, so a continued repair says where its failure came from instead of inventing an exit code. Continuing runs turns, so `POST /projects/:id/open` resolves model access exactly as a turn route does: without it the deployment pays for a BYOK user's repair loop.

- **Anything that writes to the real bucket from a test must delete every key it wrote, not the newest one.** `full-cycle.integration.test.ts` runs against a throwaway Postgres and a *real* R2, so the rows naming its objects die with the container — it collects `snapshots.listFor` inside `beforeAll` and deletes them all in `afterAll`. It used to delete exactly one, which was correct only while a run produced exactly one; per-turn snapshots would have silently turned it into an orphan generator. There is no automatic orphan detection: the check is joining `ListObjectsV2` against the `snapshots` table by hand, and it has found real orphans.

## API, auth and logging

- **Splitting the API from the worker without `NAP_EVENT_BUS=postgres` produces a deployment where everything works and nothing appears to.** The worker really claims the request, really runs the turn, really commits and really appends every event to the durable log — and publishes each one to an `InProcessEventBus` inside itself, where the only subscribers are none. Every socket watching that session is on an API pod. So the chat pane sits still, the preview never arrives, and the *logs on both processes are clean*: nothing failed. It is only visible as a reconnect with `?afterSeq=` suddenly delivering a completed turn all at once, because replay reads the log rather than the bus. `bootNap` therefore refuses to start a **worker** on the in-process bus — both halves read the same variable, so failing the one that publishes is what gets it fixed for the pair, while an API started alone on it is an ordinary thing to want and streams nothing only because nothing is running.

- **A semaphore that decrements before waking the next waiter is not a semaphore.** `BoundedPageCapture` hands its permit straight to the queued caller rather than releasing it and letting them re-acquire, because a waiter resumes on a microtask: release-then-wake leaves a window one microtask wide in which a *fresh* caller finds the count under the limit and takes the same permit. At a bound of one that is two Chromiums, which is the exact thing the bound exists to prevent, and it would appear only under load.

- **The per-session lease is a partial unique index, and three things about writing against it are not obvious.** `turn_requests` carries `unique (session_id) where state = 'leased'`, and that index — not any application check — is what stops two processes running a turn on one session and leaving the project holding two sandboxes. (1) **The claim is two statements inside one transaction, not the one the design writes.** A single `update … where id = (select … for update skip locked)` is correct, but when the index fires it has aborted the transaction without ever saying *which* candidate it was about to take, so "try the next one" has nothing to exclude; selecting the candidate first makes the id known before the update that may violate the index. The id has to be captured in a variable **outside** the transaction callback, because by the time the error is catchable there is nothing left inside it to ask. (2) **Cancelling has to name both in-flight states in one statement.** A cancel that matched only `queued` would, when a claim commits underneath it, re-read the row as `leased` and match nothing — the turn would run on happily having been cancelled. One `update … where state in ('queued','leased')` with a `case` that fails the queued ones is what makes the race harmless in either order. A cancelled *queued* request is failed outright rather than left queued and permanently skipped: a row with no terminal state is a chat pane spinning on an event that will never come. (3) **Renewal is how a worker asks whether it is still allowed to run, and zero rows back is fatal.** It is conditional on the request id, the owner *and* the state; a worker that outlived its lease through a GC pause must abort at once rather than keep appending to a session somebody else now owns. A renewal that could not be *asked* — the database blinked — is not a lease that was lost, and aborting on the first of those would make a blip cost every turn in flight. The windows in `@nap/shared/lease-windows` are why that gap is safe: the worker aborts by expiry + one renewal interval, and the janitor only reclaims at expiry + the grace.

- **Orphaning a request and announcing it cannot be one transaction, so the order is load-bearing.** One half is a row in `turn_requests` and the other is an append plus a fanout, and nothing spans them. The janitor takes the row **first** — that is what makes it exclusive, so two janitors ticking at once cannot both close out one request — and marks it announced **only once its events are durable**. `finished_at` is the marker: an `orphaned` row with a null one is a request whose terminal events are still owed, which is what the next tick reads and finishes. Doing it the other way round leaves, on a crash in between, a request that is terminal in the queue and a chat pane still spinning on an event nobody will ever write, which is the exact failure the janitor exists to prevent. The cost of this order is that a crash between the append and the mark can duplicate a `turn.failed`; a second terminal event is untidy, and no terminal event at all is unbounded.
- **An expired lease still holds its session — expiry frees nothing.** The partial unique index is over `state = 'leased'` and knows nothing about the clock, so only the janitor moves a row out of it, and only past the grace. `InMemoryTurnQueue` used to disagree, treating an expired lease as free, and a test asserted that: a fake that hands the session over on expiry is a fake in which the whole fencing argument is invisible, because the zombie and its successor never overlap in it.
- **Opening a project is the second long-running entry point, and it is easy to miss because the route answers immediately.** `POST /projects/:id/open` used to call `resumeSession` and let the promise run detached, which meant the continuation of whatever Job the log left open executed **without a lease**, in whichever pod took the request, possibly beside a worker turn on the same session — the two-sandbox failure the lease exists to prevent, reachable through a door nobody was looking at. It is a queued `resume` request now and takes the same lease a turn does. Two things follow that a reader would not guess. **A queued row carries a concrete model**, so the model settings are *required* on the project routes rather than optional as the ceilings are: the row is written before anything downstream could apply a default, and the default that would eventually be applied is `NAP_MODEL`, which is paid. And **an open can therefore be refused for a model nobody asked for** — `resolveTurnAccess` says no to an Anthropic key against an allowlist holding no Claude model, which used to fall through to the runtime's own default and now has to reach the caller. And **an orphaned `resume` is announced with the `system.notice` alone** — the janitor's `turn.failed` closes a turn a chat pane is waiting on, and an open starts no turn, so writing one puts a failure the user never asked for in the transcript with a retry of an unrelated message. `SessionQueue` in the runtime is no longer the only thing keeping a turn and an open apart, but it is kept: it is the in-process half of the same rope, and the lease is enforced in a database it cannot see. What the route still cannot see is a resume *already queued* — the `already_running` guard reads `project.sandboxId`, which stays null until a worker picks the request up, so opens repeated inside that window queue a row each. They fold to `none` when they run, which is why this is a cost rather than a bug.
- **One store and one bus per process, or the app compiles, boots, and streams nothing.** `composeNap` takes *one* `EventStore` and *one* `EventBus` and hands the same two to the runtime and to `/ws`. Constructing a second pair for the second consumer type-checks perfectly and produces a server where the runtime announces to a bus with no listeners while every open tab waits on an empty one — no error anywhere, just a turn that runs invisibly. Taking them as arguments is most of the defence: a composition that cannot build a store cannot build a spare one by accident.

- **The notify bus never carries the event, and four smaller things follow from that.** `PostgresNotifyEventBus` (`NAP_EVENT_BUS=postgres`) sends `{sessionId, seq}` through `pg_notify` and every process reads the rows out of the durable log — **a notification is a wake-up signal, the log is the delivery**. Carrying the payload would work in every test anyone would think to write and then fail on exactly the largest events, because Postgres caps a `NOTIFY` payload at **8000 bytes** and Nap's events hold command output and file contents. (1) **`LISTEN` cannot go through a transaction pooler**, and the failure has no error in it: the `LISTEN` lands on a backend that is handed back to the pool, so the process hears nothing while every query it runs keeps working. Hence a connection of its own, and `NAP_LISTEN_DATABASE_URL` for a deployment behind Neon's pooled endpoint. (2) **postgres.js reconnects and re-issues the `LISTEN` silently**, which means nothing tells the process the channel ever died — so the bus shouts on a second channel each tick and watches for its own echo, and `/readyz` reads that. A socket being open is not proof the backend is still delivering. (3) **A subscription's cursor starts at the head of the log, not at zero**, or the first event would drag the whole history along behind it — and the head is a query, so an event appended while it is in flight would be skipped. A notification arriving before the answer therefore *wins* and sets the cursor to just below its own `seq`; nothing moves a cursor backwards after that, which is what stops an out-of-order wake-up re-delivering. (4) **The catch-up poll is one query for every session the process is streaming**, via `EventTailReader.readTails`, not a `readFrom` per session: a hundred sessions on a 2s tick is fifty queries a second of pure overhead otherwise (design §24, item 2). One thing that did *not* need changing, pleasantly: `openEventStream`'s note that "the bus delivers synchronously" was load-bearing only for the buffer flush, and an asynchronous delivery either lands in the buffer or passes the `lastSentSeq` gate.

- **Three processes come out of one composition, and which loops start is the only difference.** `role` is `api`, `worker`, `reaper` or `all`, and it gates loops rather than objects: a worker builds the Hono app it never serves and an API builds the runtime it never drives, because a composition function per role is three sets of assumptions about which dependencies each may skip. Two consequences are easy to get wrong. **The reaper must be exactly one process**, since two sweeps would snapshot and destroy the same project at once — `replicas: 1` covers the steady state and a `pg_try_advisory_lock` on a connection of its own covers the rolling update that briefly runs two; a composition given no `sweepLock` sweeps unguarded, which is right for one container and for tests. And **its timers are the only thing referencing its event loop**, unlike the other two, so `startSweeping` is asked to `holdProcessOpen` there — unreferenced, as it is everywhere else, the process would exit before its first sweep. The **janitor rides in the same process on a tighter ticker and is deliberately not under the lock** (design §24, item 3): it is one query with no sandbox behind it, its clock is tighter than the idle sweep's, and two of them are safe because the reclaim holds each row with `for update skip locked` — the moment two exist is a rolling update, which is exactly when turns are being orphaned in bulk.

- **"Is this session busy?" is a lease read, and it has to be, because nothing that asks it runs turns.** Closing a project, deleting one and the idle sweep all call `TurnQueue.anyLeased`, which is `state = 'leased'` over the project's sessions — the same rows the partial unique index is over, and deliberately nothing about the clock, so an expired lease still reads busy until the janitor closes it out. It replaced a per-process `TurnRegistry` lookup that was correct only while the routes and the turns shared a process: an API pod composed apart from its workers read every busy session as idle and would have let somebody close a project mid-turn. The registry survives as a *fast path* for cancelling a turn that happens to be running on the pod the request landed on, and nothing else reads it.

- **The composition is a function; `index.ts` only reads the environment and calls it.** `apps/api/src/compose.ts` assembles the runtime, the agent, the limiters, the routes and the reaper from ports it is handed, so a test — and a load harness, and a worker entrypoint — can build *the same* system with fakes rather than a similar one. What stays in `index.ts` is what a process does: validate the environment, construct the real clients, log what it is about to spend money on, and handle signals. Two things deliberately did not move: `/health`, because `E2BSandboxManager.ping()` is not on the `SandboxManager` port, and the provider, because which vendor pays is an environment fact. `compose.test.ts` is the first test that composes boot — it was worth writing for the assertion that the reaper actually sweeps, which nothing else covered end to end.

- **A turn runs detached, so its promise needs a `.catch` or an unhandled rejection kills the Bun process.** `POST /sessions/:id/turns` answers 202 and leaves `runTurn` running; one throwing turn would otherwise take the server down and disconnect every session. The `.finally` matters as much — it clears the `TurnRegistry` entry, and without it a cancel arriving after the turn ended aborts a controller the *next* turn is about to inherit. Both are tested by mutation in `apps/api/src/turns/routes.test.ts`.

- **`hono/bun`'s `upgradeWebSocket` needs a live `Bun.serve`** — it reads the server off `c.env` and throws without one, so no route that upgrades can be exercised under Vitest. `createApp` takes the adapter as a dependency and all the connection logic lives in `apps/api/src/ws/event-stream.ts` behind a two-method socket type; what is left is covered by `bun run ws:smoke`, which is free. Note the successful upgrade returns a **200**, not a 101 — the runtime has already answered the handshake by then, and `new Response(null, { status: 101 })` is not even constructible under Node.

- **Better Auth is mapped onto this repo's tables, and two settings hold that together.** `betterAuth` takes a `modelName` per model (`user` → `users`, **`session` → `authSessions`**, `account` → `accounts`, `verification` → `verifications`), and `drizzleAdapter` resolves a model by looking that name up as a key in the schema object it is given. `usePlural: true` would look like the tidy answer and is the trap: it maps `session` to `sessions`, which in this repo is a *conversation*, and login rows would go into the chat table. The second half is passing an explicit four-key `schema` rather than the whole one — together they turn a wrong mapping into a loud "model not found" instead of a quiet write into the wrong table, and removing either one alone is the bad case. Ids need `advanced.database.generateId: "uuid"`, or the library inserts its own random strings into uuid columns. Field names in a mapping are *drizzle property* names, not SQL column names.

- **The deployment's own key buys nothing but the `:free` models, and one pure function is what enforces it.** `apps/api/src/turns/model-access.ts` decides which models a caller may name *and* whose account pays, together, because they are the same fact — somebody with no stored key gets the free list on this deployment's account, an OpenRouter key gets the whole allowlist billed to them, an Anthropic key gets the `anthropic/…` entries only. It returns a **concrete** model rather than validating one in place: a caller that has to remember to apply a default afterwards is one that will eventually forget, and the default it would fall through to is `NAP_MODEL`, which is paid. `NAP_FREE_MODEL` is checked at boot to be on the allowlist *and* to end in `:free` — a paid one there is every stranger's turns billed to you, visible only on an invoice. The free tier gets its **own `TurnRateLimiter` instance**, not a second number on one: the window is per-limiter as well as per-user, so sharing would let somebody's paid turns eat their free allowance. `/models` marks unavailable entries rather than hiding them, from `availableModels` in the same file, and a test asserts the two agree for every combination — two lists that drift produce a menu offering models every turn is then refused for naming.

- **A credential is the second thing that varies per turn, and it travels the model's path exactly.** `startTurn({ model, credentials })` → `ClaudeProvider` builds a client per credential, cached by `platform + apiKey` because a client owns a connection pool and one per turn is a fresh TLS handshake per message. **`createClient` is injectable and that is not gratuitous**: the only way to observe which client a turn picked is to make a request with it, so the first version of that test sent live calls to a vendor from the unit suite. **An Anthropic key needs the namespace taken back off** — this codebase spells every model the OpenRouter way, and `anthropic/claude-opus-5` is a 404 at Anthropic's own API, three layers from the key that caused it (`toDirectAnthropicModel`). A credential must never reach an event payload or a log line: the `events` table is the audit log by design and has the retention of a chat transcript.

- **Somebody else's API key is sealed with AES-256-**GCM**, and the authentication is the point.** `apps/api/src/account/secret-box.ts` — a wrong encryption secret or an altered ciphertext *fails* rather than returning plausible garbage that would then be sent to a vendor as a key. Fresh 12-byte IV per seal, never reused, which is why `seal` takes no IV argument. The store handles **ciphertext only** (`UserKeyStore`), so encryption stays in the layer that has the secret and the database, its backups and its query log hold nothing anybody can spend. **Nothing ever answers with a key** — `GET /account/api-key` returns `{configured, platform, hint}` and its test uses `toEqual`, not `toMatchObject`: the realistic regression is not somebody adding the plaintext back (the route has never had it) but passing the whole stored row through and shipping the ciphertext, and a `not.toContain` on the plaintext stays green through exactly that. Keys are verified against the vendor before storing, but **a network failure is not a bad key**: that check catches typos and must not become a gate.

- **better-auth's `anonymous` plugin needs a column, and it is easy to ship without one.** `users.is_anonymous` is declared by the plugin rather than wanted by anything here; without the migration the flag is silently absent and a demo visitor is indistinguishable from a paying account — which is the free tier not applying to the people it exists for. The library types a session user as `Record<string, any> & {…}`, so `session.user.isAnonymous` is `any`; it is parsed with a two-line Zod schema rather than cast, and a failed parse reads as `false`, because the safe answer to "is this a throwaway?" grants less rather than more. One user row per visitor, so demo projects are isolated — a single shared demo account would show every visitor everyone else's work.

- **`unique(provider_id, account_id)` on `accounts` is a backstop, not the mechanism** — and the difference was only found by deleting it. A repeat GitHub login finds the same person because the library looks the row up before inserting, so dropping the constraint leaves every sign-in test green. It catches the race the lookup cannot: two callbacks for one account arriving together, both finding nothing, both inserting. Since no ordinary path reaches it, `packages/db/src/accounts.db.test.ts` asserts it directly, on SQLSTATE `23505`. Same reasoning as `unique(session_id, seq)` in the event store.

- **The auth client throws when there is no server, and answers when there is one — those are different code paths and only one of them was handled.** `authClient.signIn.email` returns `{ error }` for a *refused* sign-in and **rejects** for a sign-in it could not send at all: API down, connection dropped, browser offline. Uncaught, that rejection went nowhere — `submitting` was never cleared, the button sat on "One moment…" for as long as the page stayed open, and nothing on screen said why. Found by pressing the button with the API not running, which is the normal state of a local checkout, and not by any test. The message for it is deliberately not the one for a bad password: telling somebody their credentials failed when the network is down sends them off to reset a password that was fine. `live-sign-in.test.tsx` mocks the client and pins both branches.

- **CORS credentials and a wildcard origin are mutually exclusive, so the web origin is configured rather than reflected.** A browser will not attach a cookie to a cross-origin request unless the response names the origin exactly *and* sets `Access-Control-Allow-Credentials` — `*` with credentials is refused outright. `apps/api` had no CORS middleware at all until sign-in needed one, which meant the browser could not reach the API from `:3000`; every hand-written call now goes through `apps/web/src/api/credentialed-fetch.ts` so `credentials: "include"` lives in one place instead of four.

- **Authorization is deny-by-default, and the route table is what enforces it.** A `requireUser()` call at the top of each handler protects the routes somebody remembered; the failure worth designing against is the route added later by someone who did not know to add it. So one `app.use("*", requireUser(...))` sits ahead of every route in `apps/api/src/app.ts`, and the only public paths are the ones named in `require-user.ts` — `/health`, `/livez`, `/readyz` (each polled by something that has no session and never will), `/api/auth/*` (you cannot require a session to reach the thing that issues sessions) and `/auth/providers`. **`authenticate` being absent means refuse, not allow**, so an app wired up without it reaches nobody's data. `route-coverage.test.ts` reads Hono's own `app.routes` and fails naming any route missing from `route-table.ts`, in both directions — an unclassified route *and* a table entry for a route that no longer exists, since the second is an authorization test passing against nothing. **Another user's resource is 404, never 403**: a 403 confirms the row exists, which is a fact about someone else's data. Ownership is enforced in the *query* — `ProjectStore` takes a userId and `SessionRecord` carries one down from the join `PostgresSessionStore` already performs — because a filter a handler has to remember is one that will eventually be forgotten, silently. **The fakes enforce it too**: `InMemoryProjectStore` filters on the id rather than accepting and ignoring it, or every authorization test above it would pass against a store that leaks.

- **Both spending limits live at the turn route, and they answer differently on purpose.** `POST /sessions/:id/turns` is the only way to start a turn, so it is the only place either ceiling has to be applied. A rate limit is a *speed* problem — **429 with a `Retry-After` header**, not just a body, because that header is what a proxy or client library obeys on its own. A sandbox quota is a *state* conflict — **409**, since the fix is closing a project rather than waiting, and a `Retry-After` would be a lie. Both carry a `code` so the browser tells them apart without parsing prose. Three things are load-bearing and each was a mutation: **a refused attempt does not consume the allowance** (otherwise a retrying client pushes its own recovery away forever, and the advertised wait never arrives); **the limiter window slides**, so `Retry-After` can be computed exactly rather than guessed at a fixed boundary; and **a turn whose project already has a sandbox skips the quota entirely**, or the cap silently means "projects you may talk to" and a user at their limit finds the conversation they are in has stopped accepting messages. `NAP_MAX_SANDBOXES_TOTAL` is a cluster-wide ceiling beyond what the milestone asked for: per-user limits alone multiply by the number of users, which is the arithmetic that matters the first time strangers use it.

- **The rate half of it is a table, and every property it had survived the move.** `TurnRateLimiter` is a port now (`@nap/shared/ports/turn-rate-limit`); the deployment's implementation is `PostgresTurnRateLimiter`, one row per **accepted** turn in `turn_rate_events(user_id, tier, at)`. A `Map` in the process was a correct sliding window in the wrong place — two replicas meant two allowances, so the free-tier ceiling that makes an open demo door affordable multiplied by the replica count. Four things are load-bearing. **The database's clock, everywhere**: `check` takes no `now`, because the only clock every replica agrees on is Postgres's, and `retryAfterSeconds` is therefore computed in SQL rather than from a `Date` the driver handed back. **The count and the insert are one transaction under `pg_advisory_xact_lock`**, keyed per user and tier rather than globally like the capacity lock, since the count being protected is over one person's rows — without it a burst of 30 admissions against a limit of 5 lets 18 through, which is what the db suite asserts. **`tier` is what keeps two allowances two**, so somebody's paid turns cannot eat their free ones. **The quota is checked before the rate limit**, which it was not before: the rate check *records*, so asking it first spent an hour of somebody's allowance on a turn a `409` then refused — a person at their sandbox cap could burn their whole hour without starting anything, and durably. The visible consequence is that somebody at both limits now gets the `409`, which is the answer they can act on. And **`sweep` is the reaper's**, called from the composition beside the capacity reconciliation, with its own `catch` — a failure to tidy must not cost that tick the projects it was about to put away, which is the half that spends money.

- **The sandbox half of that route is now advisory.** Counting sandboxes and then creating one is a time-of-check-to-time-of-use race, and under a burst of admissions every caller reads the same number and every one of them decides it is under the cap — so the authoritative ceiling moved to `SandboxCapacity`, reserved in a Postgres transaction under `pg_advisory_xact_lock` at the moment a sandbox is created. Read the rule as **rate and model access at the route; sandbox capacity at the point of creation**. The route's check stays because a `409` in milliseconds beats one after a queue and a cold start, and because its message is the one a person can act on — but nothing there bounds the bill.

- **A reservation has two ends, and forgetting the second one is a cap on projects-ever.** `acquireSandbox` reserves before it creates, activates once the sandbox is recorded against the session, and releases the instant creation fails; `putProjectAway` releases whatever the project holds when its sandbox is destroyed, on both the put-away and the already-gone paths — and *not* on the path that leaves it serving, because that sandbox is still being billed. Without the teardown half, a ceiling of ten stops admitting anybody after the tenth project the cluster ever opened. Rows rather than a counter for a reason a sweep needs: a counter cannot tell a leaked increment from a creation still in flight, so nothing could ever safely decrement it. A `reserved` row whose process died holds its slot until `expires_at` passes and the same project asks again — the row is then handed back rather than duplicated, which is also what lets a project whose sandbox the provider reclaimed still restore. The reaper's `PostgresCapacityReconciler` pass sweeps what no ordinary path gave back, so a slot nobody asks for again comes back in minutes rather than never. **And `activate` reports its rowcount, because a create slower than the two-minute TTL comes back to find its row already reclaimed**; an update matching nothing used to resolve as if it had worked, leaving a running, billed sandbox that no row counted. The asymmetry in how `acquireSandbox` reads its answer is the part worth keeping: an `activate` that *throws* is a store that could not be reached and nothing is known, so the turn goes ahead on a ceiling that is briefly inaccurate — while a returned `reservation_reclaimed` is a definite answer, and only that one costs the sandbox and the turn.

- **The command guard matches the *head of a shell segment*, never a substring.** `inspectCommand` splits on `;`/`&&`/`||`/`|`, pulls `$(…)` and backticks out as commands of their own, follows `sh -c`, and strips `sudo`/`env`/`VAR=x` — then matches only the resulting command name. Searching the raw string for "curl" instead is shorter, blocks `echo "run curl to fetch it"`, and there is an allow-list row that fails when someone tries it. Both tables are the test: `packages/agent/src/safety/commands.test.ts` pins ~28 blocked forms *and the rule each is blocked by*, plus 16 ordinary ones that must run. The guard is not the isolation boundary — the E2B VM is — it exists so a prompt-injected model does not get the whole VM.

- **Hono resolves no route parameters inside a wildcard middleware, and says nothing about it.** In `app.use("*", …)` the matched route *is* `*`, so `c.req.param("sessionId")` is `undefined` even on a request to `/sessions/:sessionId/turns` — the field is simply absent, which is indistinguishable from a request that had no session. Every turn and cancel had been logged without a session id from M0-6 until this was found. Ids for the log context come from `apps/api/src/log-ids.ts`, which reads the raw path; enriching from inside each handler is the alternative and it is worse twice over — a line in every route that someone will forget, and too late for the 401s and 404s that never reach a handler.

- **The log-context seam is in `@nap/shared/logging`, and the logging library is not.** Every layer has to report under the same ids and the dependency direction allows exactly one shared home, so the `AsyncLocalStorage`, the `LogContext` and a deliberately narrow `Logger` interface live in the base package — while pino, the stream and the level stay in `apps/api/src/logger.ts`, which calls `setRootLogger` once at boot. A real pino logger satisfies that interface structurally, with **no adapter and no cast**: `createLogger`'s return annotation is what proves it, and it is the one place the two shapes meet. The default root discards, so importing the module never writes anywhere. Two ways to add context and they are not interchangeable — `withLogContext` opens a scope (the request, the turn), `addLogContext` enriches the scope already open. Authentication needs the second: the caller's id is learned after the context was opened and before the request's own summary line is written, so nesting would leave the one line carrying the status code as the only line that could not say whose it was.

- **Logs carry the *shape* of a turn, never its content.** `packages/runtime/src/turn-log.ts` renders each event as `{eventType, seq}` plus identifiers — tool name, file path, failure reason, token counts — and no message text, no diffs, no command output. All of that is already in the `events` table, addressable by the very ids on the line, and that table is the audit log by design (`docs/PLAN.md` §5); copying it into logs is a second home for a user's private project with a different retention and different readers. `seq` is on every line because log timestamps are per-line and two events appended in the same millisecond sort arbitrarily by them. A test asserts no payload text reaches a field, and the `switch` over the discriminator is what makes a new event type a compile error rather than a line with only its name.

- **`/health` answers 200 even when it is degraded.** A non-2xx is how an orchestrator decides to restart or de-register a process, and neither fixes an unreachable database — it removes the instance that was still able to report it, and during a shared-dependency outage takes every instance out at once. The verdict is in the body, named per dependency. The endpoint is also public, necessarily, so `createHealthProbe` caches for 5s and collapses concurrent polls: without that, anyone who can reach it can drive unlimited load against E2B's API at our expense. Every probe has a deadline, because the characteristic database failure is an accepted connection that never answers. `E2BSandboxManager.ping()` is deliberately **not** on the `SandboxManager` port — that port is about one project's workspace and every method takes a sandbox id, while "is the provider up?" is a question about the deployment that the in-memory fake could only answer meaninglessly.

- **Liveness, readiness and health are three questions, and one endpoint can only answer one of them.** `/health`'s 200-when-degraded is right for a human and fatal for a probe, so `/livez` and `/readyz` exist beside it rather than instead of it. `/livez` **touches nothing** — whatever a liveness probe consults becomes a reason to kill the container, so including the database there means a Neon blip restarts every replica, the healthy ones included. `/readyz` is the only one that answers with a *status code*, because that is all a load balancer reads, and it checks **the database and not the sandbox provider**: an unreachable database means this pod cannot serve while another can, whereas every replica shares E2B, so de-registering on it empties the rotation instead of shifting work. Its probe is a second `createHealthProbe` rather than a reading of `/health`'s, so a slow sandbox `ping()` cannot delay the answer to "may this pod have traffic" — and it is cached for **1s where `/health` caches for 5s**, because that 5s is there to stop a public endpoint billing an E2B call per poll and readiness only runs a local `select 1`, where staleness costs a probe interval in each direction. Absent probes mean *ready*, matching the rest of `AppDeps`: an app assembled with no database has nothing to be unready for. Readiness **fails** when the Postgres LISTEN connection is down, and it is a second check in the same probe rather than a change to the route. Failing rather than warning was the open question (design §24, item 5) and the answer is that a pod with a dead listener still serves every event — the catch-up poll sees to that — but two seconds late, and another pod does not. The check only exists under `NAP_EVENT_BUS=postgres`; with the in-process bus there is nothing to be down.

- **A health check's deadline is sized by the slowest *healthy* case, not the impatient one.** `/health`'s probe timeout was 2s and reported `degraded` on the first poll after every cold boot, because a Neon instance that has scaled to zero takes **~1.8s** to answer its first query — measured, not guessed. A false outage is worse than a missed one: it is the reading that teaches people to stop trusting the endpoint, and anything automated watching it acts on a lie. The default is 5s. The same shape of mistake is waiting in any probe pointed at serverless infrastructure that idles down.

- **`bun run acceptance` is the v1 acceptance run, and it spends real money.** `apps/api/scripts/acceptance.ts` drives `docs/PLAN.md` §6 over the real HTTP and WebSocket surface — needs `bun run dev` alongside it, takes `--keep` to leave the preview up for a demo. Deliberately absent from the permission allow-list and matched by no vitest glob, for the same reason `test:integration` is: the prompt is the only checkpoint before the spend. **Two of §6's steps are not machine-checkable and it does not pretend otherwise** — whether the preview *looks* right, and whether an edit arrived by HMR rather than a reload — so they print as `LOOK` lines while their checkable halves are asserted. Two traps it walked into, both worth not repeating: a per-turn socket opened at `seq=0` replays the whole session, so searching *all* of a stream's events for `turn.completed` finds the **previous** turn's and reports the new one finished before it started; and grepping written source for "dark"/"purple" reported a false negative against a correct app, because Tailwind v4 `@theme` tokens express it as `oklch(0.14 0.02 300)`. A third, and the only one a person rather than a test caught: **closing a project destroys the sandbox its preview URL points at**, so a URL captured before step 5 is dead by the end of the run — a restored project comes back on a *new* host and re-announces `preview.ready`, which is the announcement to print. Anything handing a preview URL to a human should poll it for a 200 first; the cost of being wrong is someone opening "Sandbox Not Found" and concluding the product is broken.

## Web and UI

- **A `.test.ts` under `apps/web` runs in Node, with no DOM.** Filename decides the project, not directory, so a hook test named `use-x.test.ts` is collected by `unit` and a React one fails on a missing `document`. Web tests are `.test.tsx` **even with no JSX in them**. Relatedly, nothing under the `web` project can open a real WebSocket: Node's global (undici) throws `ERR_INVALID_ARG_TYPE` dispatching its own `Event` into jsdom's `EventTarget`, before any handler runs. That is why `useEventStream` takes a socket factory — and why proving the client against a live server needs a browser rather than a cleverer test.

- **One subscription per workspace, and the count is the only thing that catches a second one.** Every `useEventStream` call is a connection of its own — its own replay, its own backoff, its own `seq` — so three panes calling it for one session was three sockets carrying identical frames, and two panes were free to sit at different sequence numbers in the same frame: the preview offering the address of a sandbox the transcript had already watched stop. `useSessionLog` holds the one subscription above the panes and hands down the answers, and the guard is `resume-flow.test.tsx` counting sockets. Counting only *injected* sockets is not enough — a pane that subscribes for itself is written `useEventStream({ sessionId })` with no factory at all, and reaches the global `WebSocket` unseen; `sockets().countGlobalToo(vi.stubGlobal)` is what makes that case fail. Derive a view from the log where more than one pane reads it, and leave it at its call site where only one does. Measured in a real Chrome over CDP (`Network.webSocketCreated`), one workspace load went from **3 sockets and 2 listing requests to 1 and 1** — all three of the old sockets being the same URL, same session, same `seq=0`. That is the cheapest way to check this rule for real, and it needs no turn and no model: sign up over `/api/auth/sign-up/email`, `POST /projects`, and open `/p/<id>`, which starts no sandbox for a project that has never run.

- **What a project is doing is one function, and the order of its clauses is the contract.** The record (a row read once at mount), the log (live, but arriving second and blind to a sandbox the provider reclaimed on its own timer) and the request this page has in flight all describe it, and none of them is sufficient. `projects/project-phase.ts` reconciles them in a stated precedence; five modules used to do it independently, and two bugs lived in the gaps — the put-away screen flashing on every open, and a running project announcing "Nothing running yet" for the two seconds before its log replayed. **Most of those clauses cannot be guarded by a component test.** The interesting cases are single frames between a paint and the effect that acts on it, and jsdom flushes effects inside the same `act`, so deleting the clause that fixes the flash leaves every rendering test green and only the pure function's own test red. That is the reason it is a pure function taking seven inputs rather than a hook.

- **jsdom parses `<dialog>` and implements none of its methods.** `showModal` and `close` are absent, so a component that calls either throws on mount and every test of it fails against correct code. `api-key-panel.test.tsx` stubs both to toggle the `open` attribute, which is the one observable thing they share with the real implementations — and the stub is honest about what it costs: the focus trap, Escape and the inert backdrop are exactly the reasons to use a real `<dialog>` rather than a `div` with `role="dialog"`, and they are exactly what no test here can see. Relatedly, the backdrop-click close is the native `closedby="any"` rather than a click handler comparing `event.target` to the element: the hand-written form is a mouse-only path with no keyboard equivalent, and Biome's a11y rule is right to refuse it.

- **A fixture that renumbers itself makes a rerender test pass for the wrong reason.** The preview frame is keyed on the `seq` of the event that announced it, and the first version of its reload tests built fresh events per call from a shared counter — so *every* rerender moved the key, and both "it reloads" and "it does not reload" were measuring the fixture rather than the component. Build the events once and reuse the same objects when the assertion is about what changed between two renders.

- **A component test can assert on markup that cannot hold the assertion.** Two ways this happened in the chat pane, both silent: a `<pre>` whose lines are one text node makes `getByText(/^line 1$/)` match nothing, so "it clamped the output" passed against code that clamped nothing — output now renders one element per line. And `<summary>` maps to *no* role in this ARIA implementation, so `getByRole("button")` inside a `<details>` finds nothing; query the `group` the `<details>` exposes. Relatedly `role="log"` on a `<ul>` orphans every `listitem` under it — pick the live-region role or the list semantics, not both.

- **Syntax highlighting splits a line into a dozen elements, so `getByText` finds none of them.** Prism wraps every token in its own `<span>`, and testing-library's default matcher compares an element's *own* normalized text — so a query for a whole line of source matches nothing, even though the line is plainly on screen. Assert on a container's `textContent` for the content, and pair the line number with its line (`getByText("2").parentElement`) for the structure; that second one is what catches numbers rendered against the wrong lines. Highlighting itself has no accessible surface at all — it is colour — so the one assertion that it happened has to query the token elements directly, which is the deliberate exception to the no-class-names rule.

- **Every failure's wording lives in `apps/web/src/errors/failure-copy.ts`, and the recoveries deliberately differ.** Three surfaces can describe the same `turn.failed` — the transcript, the preview pane, the box you type into — and left alone each grows its own vocabulary, so one failure reads as three problems depending on where you look. The copy is keyed as a `Record` over the reason union, so **a sixth failure reason added in `@nap/shared` fails web typecheck** rather than rendering an empty box, and a test iterates `TurnFailureReasonSchema.options` asserting none of it matches a banned-phrase list (`/something went wrong|unexpected|an error occurred/i`) and that no two reasons share a title. **"Try again" is not the universal answer**: a budget-exceeded turn would spend the same budget and stop in the same place, and a refusal re-sends words the model already declined — both get a rephrase, and the retry *button* is only rendered when the copy says `recovery: "retry"` and there is a message to resend. That message is folded onto the `turn-end` item by `buildTranscript`, because with two failed turns on screen "the last user message" is the same string for both and one button would silently re-send the wrong request. A 401 redirects to `/sign-in?expired=1` and the page explains itself — a redirect with no reason is worse than a bare spinner, since at least a spinner does not pretend nothing happened.

- **A sign-in that answers 200 is not a sign-in, and the page has to ask.** Safari and Brave block third-party cookies outright regardless of `SameSite`, and the deployed app and API are on different sites (`vercel.app` and `railway.app`), so `POST /api/auth/sign-in/*` **succeeds**, the identity row is written, and the browser silently refuses the `Set-Cookie`. `result.error` is null, so the obvious code redirects; every request after that is a 401 and the person watches the app do nothing at all. The demo door is where it reads worst — one press, no form to blame, an immediate bounce — but every method fails the same way. `LiveSignIn` therefore asks the server who it is (`sessionSurvived`) before navigating, and **detects the condition rather than the browser**: a user-agent test is wrong in both directions, since Brave fails this way while reporting itself as Chrome, and a first-party deployment has no such problem in any browser. The check **fails open** — it guards one browser behaviour rather than gating entry, so a blip while asking must not strand somebody whose cookie was stored fine. This only makes the failure readable; **the fix is one registrable domain across both halves** (`docs/DEPLOY.md`; `isCrossSite` compares registrable domains, so it says `false` under one and the cookie goes back to `Lax` with no further code change). Not covered: the social path leaves the page entirely and returns through the API, so a dropped cookie there lands on `/sign-in?expired=1` — misleading rather than silent, which is the lesser of the two.

- **The landing page's rim light is a canvas raster, and the order of its beats is what makes it affordable.** `apps/web/src/glow/` masks each glow layer with a PNG it draws — `roundRect`, stroke with a conic gradient of *opacity*, blur, `toDataURL` — because a width-20 stroke blurred 32px is a soft band that reads as light, where a bordered box with a CSS blur reads as a lit border. **Every angle the pulse animates is a registered `@property`**; an unregistered custom property has no type, so the browser cannot interpolate it and the gradient jumps between keyframes instead of sweeping — silent, and it looks like a broken easing curve. The retrigger writes `data-playing` false then true **across two `requestAnimationFrame`s**: in one frame the writes coalesce and nothing restarts. **The card morphs between four shapes, and it does so in the dark on purpose** — the mask is sized to one specific box and cannot be interpolated, so the timeline is light pulses → contents fade out → *then* the empty body changes shape, and the mask is rebuilt once, debounced, after it stops. `GAP_MS` in `morph-card.tsx` is derived from those beats and must never be picked by hand: a gap shorter than the handover lights a rim that is still moving. Layers leave via `display: none` while it moves, not `opacity: 0` — a transparent element is still laid out and still rescales its mask. Radii are resolved to real numbers (`radiusFor`), because a pill written as 9999 interpolates numerically and renders a stadium for nine tenths of the morph before snapping. Under reduced motion the palette still rolls but `data-playing` is never written; there is no `prefers-reduced-motion` block in the CSS, so the two cannot disagree. **The palette is rolled onto the stage, not the card** — custom properties inherit, and a copy of `--ai-c1…` on the card would be an own declaration beating the inherited one, so the rim would never change colour. **The roll covers the rim and nothing else.** The stage used to drift through the same arc, a few points of saturation at the top of the lightness range, on the theory that a surface changing colour with the light reads as being lit by it; it reads as the page tinting itself every few seconds, and it drags every neutral on the page along with it. The stage is a fixed grey now and `palette.test.ts` asserts a roll writes no `--ai-bg*`, because a roll writing a property no stylesheet reads is invisible until somebody notices the page changing colour again. The light-theme token ramp is scoped to `.ai-stage` for the same class of reason: on `:root` it would restyle the dark workspace by accident. jsdom implements none of `matchMedia`, `ResizeObserver`, `IntersectionObserver` or `getContext`, so `apps/web/src/testing/setup.ts` stubs all four to quiet no-ops; the effect has no accessible surface and is checked by eye, not by a test.

- **`background-clip: text` and an animated element are mutually exclusive, and the failure is a blank page.** An element running an animation of opacity, transform or filter is composited into a layer of its own, and a composited descendant contributes *nothing* to an ancestor's text clip — so a heading clipped to text whose words animate has no glyphs to clip to, paints no background, and renders its `color: transparent` ink as nothing at all. No error, no warning, no clue in the computed styles, which all read exactly as intended. The landing headline hit this and the effect was cut rather than worked around; anything reaching for clipped text again needs the clip and the animation on *different* elements, one animation each. Related, for whoever tries the sweep again: `background-attachment: fixed` is what makes separate word boxes share one band of light instead of each staging its own flash, and **percentage background positions run backwards** when the image is wider than its positioning area.

- **A real browser is two commands away, and this repo's effects need one.** Chrome is at `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`; `--headless=new --screenshot` is enough for a static look, and anything involving animation needs `--remote-debugging-port` plus a CDP socket, because `--virtual-time-budget` does **not** advance CSS animations — a page screenshotted that way shows every `animation-fill-mode: both` element holding its *first* frame, which looks exactly like the bug you are hunting. Driving it properly also allows `Emulation.setEmulatedMedia` for `prefers-reduced-motion`, and `Runtime.evaluate` to read computed styles and `getAnimations()` off the live page. The invisible-headline bug above survived four wrong hypotheses and was found in one screenshot.

- **`data-no-trail` is a page-wide contract, not a prop.** The landing page's badge trail refuses to drop a badge onto any element carrying that attribute, and deflects its phantom cursor around one — the hero's content column, the footer line and each end of the header bar wear it today. An attribute rather than a ref because the things to avoid are not the trail's siblings: the header is drawn over the stage from `landing.tsx`, two levels up, and threading a ref through would make every future overlay somebody's job to remember. Two things bit here and both are in `geometry.ts`: the clearance around text is deliberately wider than the badge-to-badge gap (a badge touching a sentence is a word with something stuck to it), and a deflected point must be pushed **half a badge past** the boundary rather than onto it — a badge is centred on the point, so a point on the edge still lands half its box inside, every drop is refused, and the trail empties while the phantom slides along a wall. That failure reads as the effect being dead, not as a rule working.

- **The job strip sits above the transcript's scroller and does not shrink, so anything it expands into has to cap and scroll itself.** The strip is `shrink-0` on purpose — a job's status that scrolls away with the conversation is one somebody goes looking for during the exact minute it matters — and the consequence is that its expanded history pushes the chat down rather than being pushed. Against the *real* kept session (`testing/audit-session.json`) four jobs of real objectives ran past 1000px in a 440px column, which leaves the transcript a sliver; hand-written fixtures are uniformly too tidy to show it, since their objectives are six words long. Two things fix it and both are about real prose rather than taste: the list carries its own `max-h`/`overflow-y-auto`, and each objective is `line-clamp`ed to two lines. **`line-clamp` is a visual clip, not a truncation** — the whole sentence stays in the DOM, so a screen reader still gets what somebody actually asked for, and a test asserting on the full objective still passes. Related: the history and the strip both draw check outcomes, so the markup for one check lives in `job-marks.tsx` — two copies would drift, and what drifts is `absent` against `failed`.

- **The transcript is folded twice, and the second fold's key rule is the same trap as the first's.** `transcript.ts` turns events into items; `step-group.ts` turns a run of adjacent tool-call items into the one "8 actions" card that gets drawn. They are separate because they answer different questions — the log's shape versus how much of it a reader should see at once — and because the interesting cases in each are then checkable without rendering. **The group keeps the key it opened with**, exactly like the coalesced thinking passage: React renders the card under that key, so keying it to the newest member would remount it on every `tool.result` and spring a card shut in the middle of a turn somebody was reading. A `files` item with no step to hang it on (a client that connected between a call and its result) joins the run around it rather than splitting one card in two. And **failure beats running beats done** when summarising a group — a failure inside a collapsed card is a failure nobody reads, so it has to reach the card's own face. Related: the card and each step inside it are both `<details>`, so `getByRole("group")` throws on ambiguity; the outermost is first in document order.

- **`useStickToBottom` must measure the *previous* scroll height, not the current one.** The transcript follows a running turn only when the reader was already at the bottom — but by the time any effect runs, the new content is laid out, so measuring then finds the reader hundreds of pixels adrift and concludes they scrolled away when in fact the floor moved. The prior height lives in a ref for exactly that comparison. It is a `useLayoutEffect`, or the wrong frame paints and the pane visibly jumps. Its trigger is **one value, not a dependency array**: a caller passing `[a, b]` builds a new array every render, which Biome cannot verify and which would run it on every frame — the single `signal` is then a legitimately unused dependency, and the one place in `apps/web` where suppressing `useExhaustiveDependencies` is right rather than lazy. Testing it in jsdom means defining `scrollHeight`/`clientHeight`/`scrollTop` on the node, since jsdom lays nothing out; the test must also drive the real *sequence* (mount → move the reader → grow the content), because the distinction the hook exists to make is invisible to a test that only sets up an end state.

- **A turn's prompt reaches the log *before* the event saying who wrote it, so the transcript classifies messages in a pass of its own.** The runtime writes the `user.message` and then hands the turn to the agent, which is what emits `turn.started` — so a fold carrying a "current prompt source" forward sees every repair prompt as the user's, and the one thing the repair treatment exists to prevent (a synthesized prompt drawn in a user bubble, so self-correction reads as the app talking to itself) is exactly what it renders. `buildTranscript` therefore collects the `turnId`s whose `turn.started` says `verification` first, and attributes messages by id rather than by position; each repair runs in a `TurnScope` of its own, which is what makes the id load-bearing. Position would also be wrong on every window a client joins mid-turn — and in that window there is no `turn.started` at all, where `user` is the right answer, because guessing the other way labels somebody's own words as the machine's. Related: the retry button must be fed only *user* messages, or a failed repair offers to re-send the verifier's account of a check nothing has re-run.

- **`role="separator"` is for a widget, and Biome will tell you so.** A turn boundary in the transcript is a paragraph break drawn as a line, so it is a plain `<div>` with `sr-only` text and an `aria-hidden` rule — the role would demand `aria-valuenow` and a `tabIndex`, and would put something focusable-looking between every pair of turns. The pane dividers *are* widgets and do carry it (`ui/splitter.tsx`), but not on an `<hr>`: an `<hr>` is void, and the handle needs a child so its grab area (7px) and its visible line (1px) can be different sizes. Relatedly, an `aria-label` is not text content — `toHaveTextContent` will not see it, which is what the transcript's per-event-type treatment table asserts on.

- **`overflow: hidden` on a `static` box clips no absolutely positioned descendant, and `sr-only` is absolutely positioned.** Both app shells pinned themselves to `h-dvh` and clamped every leak with `overflow-hidden`, and both still scrolled the whole window — the dashboard by 197px, taking the rail and the header with it. A clipping box only clips what it is the *containing block* for, and a static one is that for nothing positioned: Tailwind's `sr-only` is `position: absolute`, so the hidden "Open {name}" label on the third row of project cards resolved against the initial containing block, escaped `main`'s scroller *and* the root clamp, and left `document.scrollingElement.scrollHeight` 197px taller than the viewport while `document.body.scrollHeight` still read exactly one screen — which is why nothing in the DOM looks wrong and why walking children of `<body>` finds nothing. The rule is that **anything that clips is `relative`**, and `useDocumentScrollLock` is the second half: it clamps `html` and `body` for as long as a shell is mounted and restores them on unmount, so the next `sr-only` somebody adds clips instead of scrolling the page. Two things about measuring it: `window.scrollBy` scrolls a clamped viewport anyway — `hidden` means "not by input", not "not at all" — so a probe that uses it cannot tell the lock from nothing, and the honest test is a real wheel through CDP `Input.dispatchMouseEvent`. And the offender is only findable by filtering on `position` and comparing `getBoundingClientRect().bottom` against `innerHeight`, since an ancestor-overflow walk *excludes* the very elements that escape.

- **A folder under `app/` whose name starts with `_` is private and is not routed.** Next's App Router opts `_folder` out of routing entirely, so a scratch page at `app/__look/page.tsx` 404s with no error anywhere — it looks exactly like a dev server that failed to pick the file up. Worth knowing because a throwaway route rendering the panes against fixture events is the cheapest way to *see* this app's workspace: it needs no auth, no database and no sandbox, where reaching `/p/<id>` for real needs all three.

- **A word that animates must keep its animation class forever, not just while it is the newest.** `StreamingText` reveals only the words that just arrived, and the obvious implementation compares the current word count against the previous render's. It is wrong in a way no green test shows: a word that was new last frame is old this frame, loses the class, loses `animation-fill-mode: both` with it, and snaps from mid-blur to sharp. The stagger delay for each word index is written into a ref the first time that index renders and never recomputed. Relatedly, **the transcript folds a run of `agent.thinking` events into one passage keyed to the `seq` it opened with** — keyed to the newest event instead, the element remounts on every frame the model is thinking and restarts the reveal of every word already on screen. And **"is this passage live" is `it is the last item`, full stop**: adding a `turnStartedAt` check looks like a safety net and is a bug, because a finished turn ends *with* its terminal event (so the last line has no prose to reveal anyway) while a client that reconnected mid-turn has no `turn.started` in its log and would have the passage it is actually watching frozen.

- **The landing page's poured bento fuses only while the blend is more than twice the gap, and that is arithmetic rather than taste.** `liquid/` traces one outline through the *smooth* union of the tiles' distance fields: between two boxes `g` apart the blended field bottoms out at `g/2 - k/4`, so the neck only closes above `k = 2g`. Just above it the neck is a hairline the grid can catch on one seam and miss on the next, which renders four tiles joined and one adrift and looks like a bug in the tracer rather than two numbers that need to move together — `GAP` and `BLEND` in `capabilities.tsx` are commented as the pair they are. Too *large* fails from the other end: at four or five times the gap the whole silhouette rounds off until the waists flatten, and the effect disappears while every number looks reasonable. Two more things about that section. **Interior seams have no silhouette to bend**, so the fusion is only ever visible where the shape meets the background — it is filled *and* stroked for exactly that reason, and it sits on the page's darkest surface because a white shape on the next shade up has no readable edge at the one place worth looking. And **the design space is written down twice**: the tiles are placed in fixed pixels, but the box that scales them is a Tailwind class, which has to be a literal string for the compiler to see it — a test asserts the classes still quote `SPACE`, because drift there puts every tile slightly off the shape drawn for it, at some widths only.

- **A fixed design space cannot be scaled to its container in CSS alone, and both ways of trying fail without a word.** The landing page has two of these — the poured bento and the live demo — because their contents are placed in the same plain pixels the shape behind them is traced from. The obvious fit is `scale: calc(100cqw / 880)`, and it is **invalid**: `scale` takes a *number*, a container unit is a *length*, and a length over a number is still a length, so the browser drops the declaration and the computed style reads `scale: none`. Written as a Tailwind arbitrary property it fails one layer earlier — `[scale:calc(100cqw/880)]`, `[container-type:inline-size]` and `aspect-[880/492]` compile to **no rule at all**, so the class sits in the markup pointing at nothing. Both failures look identical and look like nothing: the section renders at 1:1 and simply hangs off the side of its column on any screen narrower than the design, which on a wide monitor is invisible. The bento shipped like that for a session. The fix is `useSpaceScale`, which measures and writes a ratio to `--space-k`; the numbers go to the stylesheet as **unitless** custom properties, because `calc()` divides by numbers and not by lengths. **Read the computed style when a layout looks fine but you cannot explain why** — `getComputedStyle(el).scale` over CDP is what found this.

- **A component that renders a still *and* animates must not let the still write the shared state.** The live demo lights the copy beside it by writing `data-beat` on the section, and the paint function did that for every frame it drew — including the one frame drawn when nothing is playing. The result: a reader with `prefers-reduced-motion` got two of the three beats permanently dimmed, waiting for a highlight that would never move. The attribute is now written only from inside the loop, so no attribute at all means all three at full strength — the same "start visible, hide only once something can bring it back" rule `useReveal` follows. A test asserts the section has no `data-beat` on render.

- **`getByText` walks into `aria-hidden` subtrees, so "this illustration is not announced" cannot be asserted with a text query.** The three panels beside the landing page's beats are `aria-hidden` drawings, and `queryByText("build me a habit tracker").not.toBeInTheDocument()` fails against markup that is doing exactly the right thing — testing-library's text queries are DOM queries, not accessibility-tree queries. Assert the element's `closest("[aria-hidden='true']")` instead. Only the `*ByRole` family respects hidden-ness, which is the general reason to reach for it first.

## Testing

- **Testcontainers hangs under Bun, so the load harness cannot use `startMigratedPostgres`.** `new PostgreSqlContainer().start()` never resolves on Bun: the container really appears and really reports healthy, and the process then waits forever with nothing on stderr — which reads exactly like a slow image pull. Every Vitest suite is fine, because Vitest runs on Node. The load harness is not, because it needs `Bun.serve` for the WebSocket upgrade. `startDockerPostgres` in `packages/db/src/testing/docker-postgres.ts` is the Bun-safe path — plain `docker run`, poll until it answers SQL, then the same migrations from the same folder. Anything else that has to hold a real database *and* a real socket open at once will want it too.

- **A committed turn now runs the project's checks, so a runtime test whose sandbox has no `package.json` verifies as *errored*.** `InMemorySandboxManager` starts empty while a real sandbox comes up from a template, so a scripted turn that commits reaches `verification.started` and then abandons its job, having found nothing to discover checks from. That is honest — a sandbox that cannot hand over its manifest taught the verifier nothing — but it is rarely what a test about something else meant. Pass `seed: { "/home/user/app/package.json": … }` to give the fake a project, and script the check commands: unscripted ones throw, which the runtime catches and reports as a run that learned nothing, quietly.

- **A fake that is convenient will make a test pass for the wrong reason — check what it makes *impossible*.** The WebSocket endpoint must subscribe to the bus *before* reading history, or events appended in between reach nobody. The test for it used a store whose `readFrom` waited on a gate and then queried, so events emitted while the gate was held were still in the history when it finally ran: moving the subscribe after the read changed nothing and the test passed. It only bites once the fake snapshots *first* and gates the resolve. The same session had a second one — "close unsubscribes" passed with `unsubscribe()` deleted, because a `closed` flag suppressed the send anyway. A flag that short-circuits the symptom hides the leak; assert on the resource (`bus.subscriptions`, `vi.getTimerCount()`), not on the visible effect. Both were found only by running the mutation, which is what step 2 of the definition of done is for.

- **Chrome asks for `/favicon.ico` once per browser *process*, not once per page — so a test that shares a browser with earlier tests can never observe it.** The sandbox template declares no icon, so every generated application 404s that request and produces one console error; `PlaywrightBrowserSession` filters it, because left in it would sit in every trajectory and penalise every task equally. Proving the filter works needs a browser that has not already asked: with a shared one, rounds 2 and 3 against the same origin produce no favicon request at all, and the assertion passes against a page that was never going to produce the thing being filtered. The diagnostics test therefore launches a browser of its own. Two consequences beyond the test: in a real suite this noise lands on whichever check runs first and never again, and Chrome's own message for it — "Failed to load resource: the server responded with a status of 404" — names nothing, so the adapter appends `message.location().url` to every console error or the report records a line that identifies no resource.

- **`goto` resolves at `domcontentloaded`, and the errors worth collecting arrive after it.** A failed data fetch and the favicon both land between that point and network idle, so reading diagnostics immediately catches them in some runs and not others — an intermittent difference between two runs of one task, which is worse than a consistent one. `diagnostics()` waits for `networkidle` first, and that wait is load-bearing rather than defensive: deleting it fails the adapter's diagnostics test. A *further* fixed delay after it was tried and removed, because nothing on this evidence needed one and an unmeasured constant in a hot path is a cost nobody can justify later.

- **Playwright's role engine reads the accessibility tree, so `role=listitem` never matches a `display: none` element — and a test written with it cannot prove that a query filters hidden markup.** The adapter's `count` and `isVisible` are both documented as seeing only what a user can see, and the mutation that removed the filter stayed green until the fixture asserted through a *text* selector, which does match hidden nodes. The same asymmetry bites the other way: `isVisible` must filter to visible matches *before* taking the first, because a page that renders one copy for mobile and hides another puts the hidden one first, and asking "is the first match visible" then reports a working layout as broken.

- **A count cannot be waited for the way everything else can, because "nothing yet" and "nothing at all" are the same reading.** An empty page is perfectly stable right up until it renders, so a settling rule alone returns zero for any application that fetches before it paints. `count` therefore waits for *something* to appear first and only then lets the number settle — which means an expected zero costs the whole deadline before it can be believed, exactly as `expectNoText` does. A check asserting an empty list should declare a short `timeoutMs` rather than pay the default for it; four assertions that did not turned one integration file from 7 seconds into 67.

## Load testing

- **The async WebSocket module's name is version-dependent, and getting it wrong aborts the run rather than failing a check.** On the k6 in this checkout (v2.0.0) it is `k6/websockets`; `k6/experimental/websockets` still resolves but warns it is going away; `k6/net/websockets` — the name most of the documentation and every recollection uses — fails k6's dependency resolution before a single VU starts. The legacy `k6/ws` is not an option at all: it blocks the VU for the socket's lifetime, so a VU cannot hold a stream open *and* POST the turn that fills it, which is the whole journey. Check the installed version before writing the import.

- **k6 clears the cookie jar between iterations, and the failure looks like the API refusing load.** One VU is one *person* here — signed in once through the demo door, one project, coming back for turn after turn — so the jar has to survive with `noCookiesReset: true` in `options`. Without it the first turn of every VU succeeds and every turn after it is a 401, which arrives in the metrics as a near-100% `http_req_failed` and a turn completion rate of 0.004%. Nothing says "you forgot your cookie"; the run simply reports the system as broken. The tell is iterations finishing in milliseconds.

- **k6 only reports a tagged sub-metric if a threshold names it.** Per-stage figures — which is how the first point of material degradation gets found — exist only because `apps/api/k6/ramp.js` declares a deliberately generous threshold for every `metric{stage:N}` it wants back. They are not judgements and must never be the thing that fails a run; §23's real thresholds are the untagged ones.

- **A threshold has to use its metric's own aggregation, and one wrong pair discards the lot.** `http_req_failed` is a `Rate`, so `count>=0` on it is rejected with "unsupported aggregation method" — and k6 then runs the whole test having applied *no* thresholds, so the run completes, looks green, and proves nothing. Same trap for a `count` on a Trend. Metrics must also be constructed in the init context, which is why the error categories are a fixed list of counters rather than one per code observed.

- **`time_to_first_event` was bounded below by sandbox acquisition, and stopped being on 24 August 2026.** `SingleAgentRuntime.runTurn` used to acquire the sandbox *before* it emitted `user.message`, so on a project's first turn nothing at all reached the client until the workspace existed — around 3.1s with the calibrated fake, and a real cold start is no faster. Every figure recorded before that date carries it: §23's 2s threshold could not be met on a first turn however fast the queue was, so `docs/scaling-baseline.md` and the first two cluster ramps are reporting cold starts inside that percentile. The message is now emitted and drained *before* the acquisition, which is what a person experiences as the system having heard them and what turns the preview pane to *starting*. **`queue_wait` still carries it**: that is measured to `turn.started`, which `AgentService` emits after the context is built in a sandbox that has to exist first, and no threshold on it may be read as a statement about a cold start.

- **An in-memory fake sandbox belongs to one process, and on a cluster that turns most turns into first turns.** A worker pod claiming a project's next turn misses on `resume`, so the runtime opens a new sandbox and the run pays `CALIBRATION.sandboxCreateMs` again — which is what put `queue_wait` and `time_to_first_event` over their thresholds on the first cluster run, the harness measuring itself. `sharedSandboxManager` writes each sandbox into Postgres so any pod can reattach by id, the way a vendor-side sandbox really behaves. **Compose it inside `slowSandboxManager`, never outside**: the calibrated cold start hangs off `create`, and a reattach that reached it would pay the very number the shared store exists to stop. Nothing there is slowed on purpose — no funded run ever timed a `resume`, so inventing a figure for one would be inventing this bug back.

- **A connection string shared between a pod and a cluster-scoped operator is resolved twice, in different namespaces.** KEDA's postgresql scaler reads `DATABASE_URL` out of the same Secret the pods mount, and resolves it from the *operator's* namespace — so `nap-postgres:5432` works perfectly for every pod and answers `no such host` for the scaler. The ScaledObject then sits at `READY=False` and the workers never scale, with nothing wrong in any pod's log. Fully qualify it: `nap-postgres.nap.svc.cluster.local`.

- **prometheus-adapter discovers nothing for its first ten minutes.** `--metrics-relist-interval` defaults to 10m, and until the first relist `custom.metrics.k8s.io` answers with an empty resource list — so an HPA on a custom metric reads `<unknown>` and silently scales on whatever else it has. A run that brings a cluster up and starts loading it immediately spends its whole ramp on the fallback trigger and never knows. The scrape itself can be perfectly healthy throughout; check the adapter, not Prometheus.

- **`kubectl wait --for=condition=ready pod --selector=…` fails immediately when the apply that creates the pod has only just returned.** "no matching resources found" is not a timeout — it is `wait` refusing to wait for something that does not exist yet, and it exits non-zero and takes a `set -e` script with it. `kubectl rollout status deployment/…` is the one that waits for both the creation and the readiness.

- **The load harness measures the pool it ships with, so the sampler must not be counted in it.** `createDatabase`'s default is 10 connections and `index.ts` boots with it, so the harness keeps it: pool exhaustion under a hundred concurrent turns is a finding, not a nuisance to configure away. The sampler opens its own connection deliberately — it must not compete for what it is measuring — and identifies itself with an `application_name` that its `pg_stat_activity` query then excludes, or the pool reads two connections wider than it is at exactly the moment saturation is being judged.

- **A laptop that goes to sleep mid-ramp produces a run that passes every threshold and is worthless.** The cluster ramp is forty minutes of nobody touching the keyboard, so macOS suspends the Docker VM, k6 and the sampler together — and everything resumes exactly where it left off, with no gaps, no duplicates and no errors. The only trace is in the tail: one run froze for 900 seconds inside the 100-VU plateau, and that stage reported a `turn_duration` p50 of **925 seconds**, a delivery p99 of 897,000ms, and 138 event rows in fifteen minutes. Nothing in the report says "the host slept", and the thresholds it crosses are the duration ones nobody reads first. Run it under `caffeinate -dimsu infra/k8s/load/run.sh`, and check `cluster-samples.jsonl` for a gap between consecutive `at` stamps before quoting anything.
