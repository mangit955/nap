# Gotchas: Web and UI

Learned the hard way; don't rediscover them. Read this before touching `apps/web` — components, the landing page, browser checks.

- **A `.test.ts` under `apps/web` runs in Node, with no DOM.** Filename decides the project, not directory, so a hook test named `use-x.test.ts` is collected by `unit` and a React one fails on a missing `document`. Web tests are `.test.tsx` **even with no JSX in them**. Relatedly, nothing under the `web` project can open a real WebSocket: Node's global (undici) throws `ERR_INVALID_ARG_TYPE` dispatching its own `Event` into jsdom's `EventTarget`, before any handler runs. That is why `useEventStream` takes a socket factory — and why proving the client against a live server needs a browser rather than a cleverer test.

- **One subscription per workspace, and the count is the only thing that catches a second one.** Every `useEventStream` call is a connection of its own — its own replay, its own backoff, its own `seq` — so three panes calling it for one session was three sockets carrying identical frames, and two panes were free to sit at different sequence numbers in the same frame: the preview offering the address of a sandbox the transcript had already watched stop. `useSessionLog` holds the one subscription above the panes and hands down the answers, and the guard is `resume-flow.test.tsx` counting sockets. Counting only *injected* sockets is not enough — a pane that subscribes for itself is written `useEventStream({ sessionId })` with no factory at all, and reaches the global `WebSocket` unseen; `sockets().countGlobalToo(vi.stubGlobal)` is what makes that case fail. Derive a view from the log where more than one pane reads it, and leave it at its call site where only one does. Measured in a real Chrome over CDP (`Network.webSocketCreated`), one workspace load went from **3 sockets and 2 listing requests to 1 and 1** — all three of the old sockets being the same URL, same session, same `seq=0`. That is the cheapest way to check this rule for real, and it needs no turn and no model: sign up over `/api/auth/sign-up/email`, `POST /projects`, and open `/p/<id>`, which starts no sandbox for a project that has never run.

- **What a project is doing is one function, and the order of its clauses is the contract.** The record (a row read once at mount), the log (live, but arriving second and blind to a sandbox the provider reclaimed on its own timer) and the request this page has in flight all describe it, and none of them is sufficient. `projects/project-phase.ts` reconciles them in a stated precedence; five modules used to do it independently, and bugs lived in the gaps, such as a running project announcing "Nothing running yet" for the two seconds before its log replayed. **Most of those clauses cannot be guarded by a component test.** The interesting cases are single frames between a paint and the effect that acts on it, and jsdom flushes effects inside the same `act`, so deleting a clause that covers one leaves every rendering test green and only the pure function's own test red. That is the reason it is a pure function taking seven inputs rather than a hook.

- **jsdom parses `<dialog>` and implements none of its methods.** `showModal` and `close` are absent, so a component that calls either throws on mount and every test of it fails against correct code. `api-key-panel.test.tsx` stubs both to toggle the `open` attribute, which is the one observable thing they share with the real implementations — and the stub is honest about what it costs: the focus trap, Escape and the inert backdrop are exactly the reasons to use a real `<dialog>` rather than a `div` with `role="dialog"`, and they are exactly what no test here can see. Relatedly, the backdrop-click close is the native `closedby="any"` rather than a click handler comparing `event.target` to the element: the hand-written form is a mouse-only path with no keyboard equivalent, and Biome's a11y rule is right to refuse it.

- **A fixture that renumbers itself makes a rerender test pass for the wrong reason.** The preview frame is keyed on the `seq` of the event that announced it, and the first version of its reload tests built fresh events per call from a shared counter — so *every* rerender moved the key, and both "it reloads" and "it does not reload" were measuring the fixture rather than the component. Build the events once and reuse the same objects when the assertion is about what changed between two renders.

- **A component test can assert on markup that cannot hold the assertion.** Two ways this happened in the chat pane, both silent: a `<pre>` whose lines are one text node makes `getByText(/^line 1$/)` match nothing, so "it clamped the output" passed against code that clamped nothing — output now renders one element per line. And `<summary>` maps to *no* role in this ARIA implementation, so `getByRole("button")` inside a `<details>` finds nothing; query the `group` the `<details>` exposes. Relatedly `role="log"` on a `<ul>` orphans every `listitem` under it — pick the live-region role or the list semantics, not both.

- **Syntax highlighting splits a line into a dozen elements, so `getByText` finds none of them.** Prism wraps every token in its own `<span>`, and testing-library's default matcher compares an element's *own* normalized text — so a query for a whole line of source matches nothing, even though the line is plainly on screen. Assert on a container's `textContent` for the content, and pair the line number with its line (`getByText("2").parentElement`) for the structure; that second one is what catches numbers rendered against the wrong lines. Highlighting itself has no accessible surface at all — it is colour — so the one assertion that it happened has to query the token elements directly, which is the deliberate exception to the no-class-names rule.

- **Every failure's wording lives in `apps/web/src/errors/failure-copy.ts`, and the recoveries deliberately differ.** Three surfaces can describe the same `turn.failed` — the transcript, the preview pane, the box you type into — and left alone each grows its own vocabulary, so one failure reads as three problems depending on where you look. The copy is keyed as a `Record` over the reason union, so **a sixth failure reason added in `@nap/shared` fails web typecheck** rather than rendering an empty box, and a test iterates `TurnFailureReasonSchema.options` asserting none of it matches a banned-phrase list (`/something went wrong|unexpected|an error occurred/i`) and that no two reasons share a title. **"Try again" is not the universal answer**: a budget-exceeded turn would spend the same budget and stop in the same place, and a refusal re-sends words the model already declined — both get a rephrase, and the retry *button* is only rendered when the copy says `recovery: "retry"` and there is a message to resend. That message is folded onto the `turn-end` item by `buildTranscript`, because with two failed turns on screen "the last user message" is the same string for both and one button would silently re-send the wrong request. A 401 redirects to `/sign-in?expired=1` and the page explains itself — a redirect with no reason is worse than a bare spinner, since at least a spinner does not pretend nothing happened.

- **Behind the `/backend` proxy, three things break quietly.** better-auth takes a base URL that has a path as the *whole* auth path, so `…/backend` alone routes sign-in to `/backend/sign-in/…` and 404s — both ends pass `…/backend/api/auth` explicitly, and the API shows the library each request at its public address (`auth/public-url.ts`). Vercel's external rewrites cache by default on newer projects, and this one carries every authenticated response, so caching is switched off for `/backend/*` and a test asserts it. And Vercel does not forward WebSocket upgrades: `/ws` stays on Render's host, the cookie is not sent there, and the page carries a stream ticket instead — a socket that opens without one is a 401, which the hook's ordinary reconnect retries with a fresh ticket.

- **A sign-in that answers 200 is not a sign-in, and the page has to ask.** A browser that refuses the session cookie lets `POST /api/auth/sign-in/*` **succeed** — the identity row is written, `result.error` is null, the obvious code redirects — and every request after that is a 401 while the person watches the app do nothing at all. `LiveSignIn` therefore asks the server who it is (`sessionSurvived`) before navigating, and **detects the condition rather than the browser**: a user-agent test is wrong in both directions, since Brave reports itself as Chrome and cookie blocking is a setting. The check **fails open** — it guards one browser behaviour rather than gating entry, so a blip while asking must not strand somebody whose cookie was stored fine. The social path is not covered: it leaves the page and returns through the API, so a dropped cookie there lands on `/sign-in?expired=1`. *History:* this was written when the app was on `vercel.app` and the API on `railway.app`, later `onrender.com` — two sites, so the cookie was third-party and **every** Safari and Brave visitor hit it, by every method. The fix was one site across both halves — the API published under the web app's origin at `/backend` — and since #86 production refuses to boot on two (`apps/api/src/env.ts`, `docs/DEPLOY.md` § One site for both halves); what remains for this check is somebody who blocks cookies outright.

- **The landing page's rim light is a canvas raster, and the order of its beats is what makes it affordable.** `apps/web/src/glow/` masks each glow layer with a PNG it draws — `roundRect`, stroke with a conic gradient of *opacity*, blur, `toDataURL` — because a width-20 stroke blurred 32px is a soft band that reads as light, where a bordered box with a CSS blur reads as a lit border. **Every angle the pulse animates is a registered `@property`**; an unregistered custom property has no type, so the browser cannot interpolate it and the gradient jumps between keyframes instead of sweeping — silent, and it looks like a broken easing curve. The retrigger writes `data-playing` false then true **across two `requestAnimationFrame`s**: in one frame the writes coalesce and nothing restarts. **The card morphs between four shapes, and it does so in the dark on purpose** — the mask is sized to one specific box and cannot be interpolated, so the timeline is light pulses → contents fade out → *then* the empty body changes shape, and the mask is rebuilt once, debounced, after it stops. `GAP_MS` in `morph-card.tsx` is derived from those beats and must never be picked by hand: a gap shorter than the handover lights a rim that is still moving. Layers leave via `display: none` while it moves, not `opacity: 0` — a transparent element is still laid out and still rescales its mask. Radii are resolved to real numbers (`radiusFor`), because a pill written as 9999 interpolates numerically and renders a stadium for nine tenths of the morph before snapping. Under reduced motion the palette still rolls but `data-playing` is never written; there is no `prefers-reduced-motion` block in the CSS, so the two cannot disagree. **The palette is rolled onto the stage, not the card** — custom properties inherit, and a copy of `--ai-c1…` on the card would be an own declaration beating the inherited one, so the rim would never change colour. **The roll covers the rim and nothing else.** The stage used to drift through the same arc, a few points of saturation at the top of the lightness range, on the theory that a surface changing colour with the light reads as being lit by it; it reads as the page tinting itself every few seconds, and it drags every neutral on the page along with it. The stage is a fixed grey now and `palette.test.ts` asserts a roll writes no `--ai-bg*`, because a roll writing a property no stylesheet reads is invisible until somebody notices the page changing colour again. The light-theme token ramp is scoped to `.ai-stage` for the same class of reason: on `:root` it would restyle the dark workspace by accident. jsdom implements none of `matchMedia`, `ResizeObserver`, `IntersectionObserver` or `getContext`, so `apps/web/src/testing/setup.ts` stubs all four to quiet no-ops; the effect has no accessible surface and is checked by eye, not by a test.

- **`background-clip: text` and an animated element are mutually exclusive, and the failure is a blank page.** An element running an animation of opacity, transform or filter is composited into a layer of its own, and a composited descendant contributes *nothing* to an ancestor's text clip — so a heading clipped to text whose words animate has no glyphs to clip to, paints no background, and renders its `color: transparent` ink as nothing at all. No error, no warning, no clue in the computed styles, which all read exactly as intended. The landing headline hit this and the effect was cut rather than worked around; anything reaching for clipped text again needs the clip and the animation on *different* elements, one animation each. Related, for whoever tries the sweep again: `background-attachment: fixed` is what makes separate word boxes share one band of light instead of each staging its own flash, and **percentage background positions run backwards** when the image is wider than its positioning area.

- **A real browser is two commands away, and this repo's effects need one.** Chrome is at `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`; `--headless=new --screenshot` is enough for a static look, and anything involving animation needs `--remote-debugging-port` plus a CDP socket, because `--virtual-time-budget` does **not** advance CSS animations — a page screenshotted that way shows every `animation-fill-mode: both` element holding its *first* frame, which looks exactly like the bug you are hunting. Driving it properly also allows `Emulation.setEmulatedMedia` for `prefers-reduced-motion`, and `Runtime.evaluate` to read computed styles and `getAnimations()` off the live page. The invisible-headline bug above survived four wrong hypotheses and was found in one screenshot.

- **`data-no-trail` is a page-wide contract, not a prop.** The landing page's badge trail refuses to drop a badge onto any element carrying that attribute, and deflects its phantom cursor around one — the hero's content column, the footer line and each end of the header bar wear it today. An attribute rather than a ref because the things to avoid are not the trail's siblings: the header is drawn over the stage from `landing.tsx`, two levels up, and threading a ref through would make every future overlay somebody's job to remember. Two things bit here and both are in `geometry.ts`: the clearance around text is deliberately wider than the badge-to-badge gap (a badge touching a sentence is a word with something stuck to it), and a deflected point must be pushed **half a badge past** the boundary rather than onto it — a badge is centred on the point, so a point on the edge still lands half its box inside, every drop is refused, and the trail empties while the phantom slides along a wall. That failure reads as the effect being dead, not as a rule working.

- **The transcript is folded twice, and the second fold's key rule is the same trap as the first's.** `transcript.ts` turns events into items; `timeline.ts` turns items into the rows that get drawn — a run of work as a group with a one-line summary, the newest of it as the live row, and a finished turn as one "Worked for 1m 12s" fold. They are separate because they answer different questions — the log's shape versus how much of it a reader should see at once — and because the interesting cases in each are then checkable without rendering. **Every id is the key of the item it opened with**, exactly like the coalesced thinking passage: a group is `group:<first entry's key>` and a fold is `fold:<its prompt's key>`, and the open/closed state above is a set of those ids — so keying either to its newest member would spring it shut on every `tool.result`, in the middle of a turn somebody was reading. The live row is the opposite on purpose: "Thinking" and "Running bun" are the *same* id (`LIVE_ACTIVITY_ROW_ID`), so going from one to the other changes the row in place instead of unmounting it. **A command that exits non-zero is `ok: true`** — `run_command` reports the exit in its output's first line (`exit code 1`) rather than failing the call — so "did this fail" is `entryFailed` in `work-log.ts`, which reads both, and anything checking `status` alone draws a broken build as a success. Related: every expander in the work log is a `button` with `aria-expanded`, not a `<details>`, so a test opens one by role and name — and a test about what is *inside* a row has to open it first, which is what `expandAll` in `chat-transcript.test.tsx` is for. **A failure inside a turn that completed sits behind its fold on purpose** — that is T3's fold, which hides everything between the prompt and the answer — so the "Worked for" row carries no mark of it; the group row inside does, with its X, its danger tint and ", tool call failed" in its name.

- **`useStickToBottom` must measure the *previous* scroll height, not the current one.** The transcript follows a running turn only when the reader was already at the bottom — but by the time any effect runs, the new content is laid out, so measuring then finds the reader hundreds of pixels adrift and concludes they scrolled away when in fact the floor moved. The prior height lives in a ref for exactly that comparison. It is a `useLayoutEffect`, or the wrong frame paints and the pane visibly jumps. Its trigger is **one value, not a dependency array**: a caller passing `[a, b]` builds a new array every render, which Biome cannot verify and which would run it on every frame — the single `signal` is then a legitimately unused dependency, and the one place in `apps/web` where suppressing `useExhaustiveDependencies` is right rather than lazy. Testing it in jsdom means defining `scrollHeight`/`clientHeight`/`scrollTop` on the node, since jsdom lays nothing out; the test must also drive the real *sequence* (mount → move the reader → grow the content), because the distinction the hook exists to make is invisible to a test that only sets up an end state.

- **A turn's prompt reaches the log *before* the event saying who wrote it, so the transcript classifies messages in a pass of its own.** The runtime writes the `user.message` and then hands the turn to the agent, which is what emits `turn.started` — so a fold carrying a "current prompt source" forward sees every repair prompt as the user's, and the one thing the repair treatment exists to prevent (a synthesized prompt drawn in a user bubble, so self-correction reads as the app talking to itself) is exactly what it renders. `buildTranscript` therefore collects the `turnId`s whose `turn.started` says `verification` first, and attributes messages by id rather than by position; each repair runs in a `TurnScope` of its own, which is what makes the id load-bearing. Position would also be wrong on every window a client joins mid-turn — and in that window there is no `turn.started` at all, where `user` is the right answer, because guessing the other way labels somebody's own words as the machine's. Related: the retry button must be fed only *user* messages, or a failed repair offers to re-send the verifier's account of a check nothing has re-run.

- **`role="separator"` is for a widget, and Biome will tell you so.** A turn boundary in the transcript is a paragraph break drawn as a line, so it is a plain `<div>` with `sr-only` text and an `aria-hidden` rule — the role would demand `aria-valuenow` and a `tabIndex`, and would put something focusable-looking between every pair of turns. The pane dividers *are* widgets and do carry it (`ui/splitter.tsx`), but not on an `<hr>`: an `<hr>` is void, and the handle needs a child so its grab area (7px) and its visible line (1px) can be different sizes. Relatedly, an `aria-label` is not text content — `toHaveTextContent` will not see it, which is what the transcript's per-event-type treatment table asserts on.

- **`overflow: hidden` on a `static` box clips no absolutely positioned descendant, and `sr-only` is absolutely positioned.** Both app shells pinned themselves to `h-dvh` and clamped every leak with `overflow-hidden`, and both still scrolled the whole window — the dashboard by 197px, taking the rail and the header with it. A clipping box only clips what it is the *containing block* for, and a static one is that for nothing positioned: Tailwind's `sr-only` is `position: absolute`, so the hidden "Open {name}" label on the third row of project cards resolved against the initial containing block, escaped `main`'s scroller *and* the root clamp, and left `document.scrollingElement.scrollHeight` 197px taller than the viewport while `document.body.scrollHeight` still read exactly one screen — which is why nothing in the DOM looks wrong and why walking children of `<body>` finds nothing. The rule is that **anything that clips is `relative`**, and `useDocumentScrollLock` is the second half: it clamps `html` and `body` for as long as a shell is mounted and restores them on unmount, so the next `sr-only` somebody adds clips instead of scrolling the page. Two things about measuring it: `window.scrollBy` scrolls a clamped viewport anyway — `hidden` means "not by input", not "not at all" — so a probe that uses it cannot tell the lock from nothing, and the honest test is a real wheel through CDP `Input.dispatchMouseEvent`. And the offender is only findable by filtering on `position` and comparing `getBoundingClientRect().bottom` against `innerHeight`, since an ancestor-overflow walk *excludes* the very elements that escape.

- **Next remounts a page whose dynamic segment changed, so anything that must survive a switch between projects lives in `app/p/layout.tsx`.** `layout-router.js` keys each segment's subtree by `createRouterCacheKey(segment)`, which for `[projectId]` is `projectId|<id>|d`, so a client-side `/p/A → /p/B` throws away the whole page. With the sidebar inside the page that meant its list fetched again on every switch, and the row a double-click's first click had opened replaced before its second click landed. The frame, the sign-in gate and the sidebar are therefore `WorkspaceFrame`, rendered by the layout. Two things follow. The page's own reset is **our** `key={projectId}` on `AppShell` (`live-workspace.tsx`), not Next's remount: that is a rendering detail rather than a promise, and under cache components the old segment stays mounted, hidden, in an `<Activity>`. `project-switch.test.tsx` fails with the key deleted, because A's prompt is still on screen in B's frame. And the session row no longer holds a click back for 300ms to see whether a second one follows: the first click navigates, and the second click of a double-click is swallowed. Where the first click leaves the page (`/dashboard`) or closes the mobile drawer, double-click rename cannot work without that delay, so it was given up there in favour of the row's menu. That was the owner's call, not an oversight. A row whose caller passes no `onSelectProject` is a plain link and does a full document load, so every in-app caller passes one.

- **The workspace's sidebar switches projects with `history.pushState`, not the router, and so the project is read from the pathname, never from params.** `router.push('/p/<id>')` fetched the page from the server on every click: the route is dynamic, Next keeps a dynamic page for 0 seconds (`staleTimes.dynamic`), and nothing of the project's own could start until that answer came back — about half a second on Vercel, for a page that holds nothing but the id. Next 16 patches `pushState` (`client/components/app-router.js`): it copies the router's tree into the new entry, so back and forward restore it, and it moves `usePathname`. It does **not** render the page segment again, so `params` and `useParams` keep naming whichever project the tab first opened. `useOpenProjectId` (`workspace/open-project.ts`) reads the pathname, and both the frame and `LiveWorkspace` use it; `app/p/[projectId]/page.tsx` reads no params on purpose. Since the segment no longer changes on a sidebar switch, the `AppShell` key above is the *only* reset. A modified click is still the browser's or the list's: middle-click opens a new tab, and ⌘/Ctrl-click is the list's multi-select.

- **A project this tab has seen is drawn from memory on coming back, and only the transcript may draw it.** `hooks/remembered-logs.ts` keeps each project's committed log in module state, keyed by owner and project (12 logs, in memory only). Every sign-out clears it through `auth/forget-signed-out.ts`, the delete operation itself (`remove` in `use-session-navigation.ts`) drops a project's log, and `AppShell` stops offering one — and forgets it — once the record answers 404, since no session would ever arrive to replace it. The owner key is what makes a batch committed by a workspace still open during sign-out unreadable by whoever signs in next; `useEventStream` given a `remember` key resumes its socket after the kept `seq` and puts the kept events in the replay buffer, so they are committed together with the catch-up at `ready`. `events` and `replayed` therefore read exactly as after a full replay — nothing, then the whole log at once — and the announcement to the sidebar, `phaseOf`, the file listing and the preview handshake count the catch-up as history, as they must. The kept log is offered beside them as `remembered`, which only the chat pane draws; `use-session-log.test.tsx` fails if any fold reads it. The key is read through a ref, not as an effect dependency, so taking it away stops the keeping and the drawing without reconnecting a socket that may be live. Handing it to `events` early is the tempting shortcut and the bug: the preview would point at a sandbox swept minutes ago, and every event that arrived while away would be announced as news. `project-switch.test.tsx` and the "coming back" cases in `use-event-stream.test.tsx` fail if it is done. The map is module state, so `testing/setup.ts` clears it after every test; a test that opens the same project twice and means two first visits clears it itself, as `open-cost.test.tsx` does.

- **A folder under `app/` whose name starts with `_` is private and is not routed.** Next's App Router opts `_folder` out of routing entirely, so a scratch page at `app/__look/page.tsx` 404s with no error anywhere — it looks exactly like a dev server that failed to pick the file up. Worth knowing because a throwaway route rendering the panes against fixture events is the cheapest way to *see* this app's workspace: it needs no auth, no database and no sandbox, where reaching `/p/<id>` for real needs all three.

- **A reply fades in by `@starting-style`, which fires only for elements that are new, so what fades is decided by what React inserts.** The rule is gated on `data-streaming`, which `ChatMarkdown` sets only on the live passage — so a block fades when it first appears and a paragraph that grows in place does not fade again, without any bookkeeping in a component. What breaks it is a remount: **the transcript folds a run of `agent.thinking` (or `agent.message`) events into one passage keyed to the `seq` it opened with** — keyed to the newest event instead, the element remounts on every chunk and every block already on screen fades in again. And **"is this passage live" is `it is the last item`, full stop**: adding a check on the in-flight turn's `startedAt` looks like a safety net and is a bug, because a finished turn ends *with* its terminal event (so the last line has no prose to fade anyway) while a client that reconnected mid-turn has no `turn.started` in its log and would have the passage it is actually watching frozen. Related, for the live row's spotlight: the lit copy of "Thinking" is drawn from `data-spotlight-text` by a CSS `::after`, not as a second text node — two text nodes would put the label in `textContent` twice and make every `getByText` for it ambiguous.

- **The landing page's poured bento fuses only while the blend is more than twice the gap, and that is arithmetic rather than taste.** `liquid/` traces one outline through the *smooth* union of the tiles' distance fields: between two boxes `g` apart the blended field bottoms out at `g/2 - k/4`, so the neck only closes above `k = 2g`. Just above it the neck is a hairline the grid can catch on one seam and miss on the next, which renders four tiles joined and one adrift and looks like a bug in the tracer rather than two numbers that need to move together — `GAP` and `BLEND` in `capabilities.tsx` are commented as the pair they are. Too *large* fails from the other end: at four or five times the gap the whole silhouette rounds off until the waists flatten, and the effect disappears while every number looks reasonable. Two more things about that section. **Interior seams have no silhouette to bend**, so the fusion is only ever visible where the shape meets the background — it is filled *and* stroked for exactly that reason, and it sits on the page's darkest surface because a white shape on the next shade up has no readable edge at the one place worth looking. And **the design space is written down twice**: the tiles are placed in fixed pixels, but the box that scales them is a Tailwind class, which has to be a literal string for the compiler to see it — a test asserts the classes still quote `SPACE`, because drift there puts every tile slightly off the shape drawn for it, at some widths only.

- **A fixed design space cannot be scaled to its container in CSS alone, and both ways of trying fail without a word.** The landing page has two of these — the poured bento and the live demo — because their contents are placed in the same plain pixels the shape behind them is traced from. The obvious fit is `scale: calc(100cqw / 880)`, and it is **invalid**: `scale` takes a *number*, a container unit is a *length*, and a length over a number is still a length, so the browser drops the declaration and the computed style reads `scale: none`. Written as a Tailwind arbitrary property it fails one layer earlier — `[scale:calc(100cqw/880)]`, `[container-type:inline-size]` and `aspect-[880/492]` compile to **no rule at all**, so the class sits in the markup pointing at nothing. Both failures look identical and look like nothing: the section renders at 1:1 and simply hangs off the side of its column on any screen narrower than the design, which on a wide monitor is invisible. The bento shipped like that for a session. The fix is `useSpaceScale`, which measures and writes a ratio to `--space-k`; the numbers go to the stylesheet as **unitless** custom properties, because `calc()` divides by numbers and not by lengths. **Read the computed style when a layout looks fine but you cannot explain why** — `getComputedStyle(el).scale` over CDP is what found this.

- **A component that renders a still *and* animates must not let the still write the shared state.** The live demo lights the copy beside it by writing `data-beat` on the section, and the paint function did that for every frame it drew — including the one frame drawn when nothing is playing. The result: a reader with `prefers-reduced-motion` got two of the three beats permanently dimmed, waiting for a highlight that would never move. The attribute is now written only from inside the loop, so no attribute at all means all three at full strength — the same "start visible, hide only once something can bring it back" rule `useReveal` follows. A test asserts the section has no `data-beat` on render.

- **`getByText` walks into `aria-hidden` subtrees, so "this illustration is not announced" cannot be asserted with a text query.** The three panels beside the landing page's beats are `aria-hidden` drawings, and `queryByText("build me a habit tracker").not.toBeInTheDocument()` fails against markup that is doing exactly the right thing — testing-library's text queries are DOM queries, not accessibility-tree queries. Assert the element's `closest("[aria-hidden='true']")` instead. Only the `*ByRole` family respects hidden-ness, which is the general reason to reach for it first.

- **The sidebar draws every action before the server answers, and it never edits rows in place to do it.** `useSessionNavigation` holds the server's last list and a queue of pending actions, and the rows it returns are the queue folded over the list (`projects/navigation-overlay.ts`), using the same `applyNavigationChange` the store runs. Two consequences carry the design. A refusal is cheap to show: its action, and the rest of its group (a drag sends un-settle *then* pin), leave the queue. The fold runs again, the row is where the server has it, and `actionError` names it. A poll landing mid-flight cannot flicker a row back, because it only replaces the list under the same queue. The writes go **one at a time** and read the revision the server last confirmed when they are *sent*, not when they are made. Sending them in parallel, or stamping the revision at click time, makes the second of two quick changes to one row a 409. Each of those has a test that fails when the rule is removed. A settle is drawn with a stamp no earlier than the row's newest request, because the server only counts a settle that is not before it, and this clock may be behind the server's.

- **`min-w-0` lets a flex item shrink to nothing, and its text still paints at full width unless something stops it.** A session card's branch sat in a `min-w-0 flex-1` box beside the pull request, diff and model chips, and its last 12 characters were a `shrink-0` span. When the chips took the whole line, which they do at the default 256px, the box was 0px wide and the tail painted straight over `#287` and `+87`. Now the tail is `shrink-0 max-w-full truncate`: it keeps its width while the head gives way, and is cut, with an ellipsis, only once it alone is wider than the room. A tail that may shrink is cut alongside the head, losing the part that tells sibling branches apart. A branch Nap made for a job (`nap/<uuid>`, `jobBranch` in `@nap/shared/github-protocol`) is not drawn at all: `isJobBranch` recognises it, so the name and its recognition cannot drift apart. A container query hides the branch outright under 3rem rather than drawing an icon and a sliver of a letter, and the model chip is the one that gives way at 208px. The `N feedback` chip is still `shrink-0`, so with large numbers at 208px the line can still pass the card's edge (#301). jsdom passes any of this; `sidebar-drag.integration.test.ts` measures each chip's painted text every 4px from 208 to 420 and fails if the tail may shrink, if it loses `max-w-full`, if the model is `shrink-0`, or if the container query goes.

- **Dragging between the sidebar's shelves broke in four ways that only a browser shows, and each fix is load-bearing.** `dashboard/sidebar-drag.tsx` and `sidebar-drag.integration.test.ts` (raw CDP against `NAP_CHROME_PATH`, free) hold the proof. (1) **The boundaries move the row being dragged.** *Pinned* and *Active* appear as the drag starts and push every row down 56px, after dnd-kit has taken the pointer's offset into the row. The card then sat below the cursor and every drop landed a row low. A modifier anchors it to the row's top, read from the DOM in `onDragStart` before React draws them. (2) **No `DragOverlay`.** The overlay measures its own rect at a moment of its own, so whether that rect already includes the shift varied from run to run. The same drag passed once and failed the next. The row itself moves, lifted with a z-index. (3) **`overflow-clip` on the list.** A transform past the list's edge grows the scroller's overflow, auto-scroll chases it, and the list runs away under the pointer. `clip` is not a scroll container, so the sticky bulk bar still sticks. (4) **Drop targets are measured again every 50ms while dragging.** The stock measurement happened before the boundaries existed. That cadence belongs to `DroppableMeasurements` in `sidebar-drag.tsx`, not to dnd-kit's numeric `measuring.droppable.frequency`: dnd-kit 6.3.1 never clears that timeout on unmount, so it fires after the layer is gone, React reads `window.event` dispatching the update, and after jsdom teardown that throws `window is not defined` — an unhandled error that turned CI red with every assertion passing, and only under load. `sidebar-drag.test.tsx` guards it by counting armed timers after unmount. Two smaller ones: dnd-kit only stops the *propagation* of the click that ends a drag, so the row's link would still be followed (`swallowNextClick`). Its exported `CSS` shadows the browser's `CSS.escape` in any file that imports it. The stock vertical strategy assumes one evenly spaced list, and the shelves sit past an `mt-auto` gap. Rows crossing it shifted by the whole gap and the shelf headers slid up, so `shelvesStrategy` shifts by the dragged row's height and leaves the headers still. Removing (1) or the click swallow fails that browser test; jsdom passes either way.

- **The drag layer is a dynamic `import()`, and arriving after the rows remounts them.** The rows' shell changes type when it loads. That drops the focus of anybody already on a row, and in tests it fails whichever case happens to run first in a file. The sidebar starts the fetch while its list is still loading (`preloadDrag`), so the layer is normally there before the first row is drawn. If it arrives late, the list puts focus back on the row that had it. The landing page draws a sidebar with no `navigation` and never fetches the layer.

- **On touch, a finger lifting fires `pointerleave` before the click, so a menu that closes its submenu on pointer leave sends the tap to whatever sat underneath.** In Chrome at 390px, with the Copy submenu drawn below its owner, tapping Copy → Branch closed the submenu as the finger lifted, and the click landed on Archive, the menu item that had been under Branch. `session-context-menu.tsx` therefore ignores pointer leave when `pointerType` is `touch`, and clicking a submenu's owner only ever opens it, because a toggle would shut what the pointer had just opened. On touch a submenu stays open until something else is tapped: another item (which also chooses it), the other submenu's owner, or outside the menu (which closes the whole menu). A submenu fits on neither side of its menu below about 476px, and up to about 700px when the menu opens mid-screen, so `placeSubmenu` drops it below its owner item, or ends it at the owner's top when there is no room below. A desktop-width or mouse-only browser test sees none of this. The Chrome case runs at a real 390px viewport with `mobile: false` and touch emulation on, because the fixture has no viewport meta and `mobile: true` lays it out at Chrome's 980px default.

- **The preview holds a new frame out of sight until load or a timeout, and two things about frames make that easy to break unseen.** `preview-pane.tsx` keeps at most two: the one on screen and the newest one loading behind it, which takes over on its `load` or after `SWAP_TIMEOUT_MS`. (1) **The frame that takes over must stay the same element.** A frame is keyed by its own identity, never by its role. Keyed `"shown"` and `"incoming"`, the takeover reuses the old element and points it at the new address, so the app the user just waited for loads a second time. A browser also reloads an iframe that is moved in the document, so a survivor must never be reordered either. The first test in "a new announcement" asserts the node that loaded is the node left on screen. (2) **jsdom fires no `load` on an iframe and applies no stylesheet.** Every load in the tests is a `fireEvent.load`, which is what lets them hold a frame unloaded. But a Tailwind class is invisible to them: a loaded frame lost its `bg-white` with every test green, and a real Chrome found it in one run. The hidden and loaded styles are inline for that reason, and `toHaveStyle` now guards the white. The cheapest look at it is a throwaway route rendering `PreviewPane` against a local server that answers slowly, driven by `playwright-core` from `node_modules/.bun` with Chrome's executable path.

- **The event stream commits in batches, so a test that pushes frames has to end them the way the server does.** `useEventStream` holds a connection's replay until the server's `ready` frame and commits it once; live events after that wait `LIVE_BATCH_MS` (about one frame) and land together. One commit per frame used to re-run every derivation of the whole log per event — opening a session of N events was N² work, painted the transcript a piece at a time, and fired a file listing per write the session had ever made (`components/open-cost.test.tsx` counts commits under a `Profiler` so that cannot quietly return). Three consequences for anyone writing a test. **During an uninterrupted replay, event frames stay buffered until `ready`**; if the socket drops first, the accepted frames are committed for the reconnect cursor, while the initial transcript keeps its skeleton until the replay completes — unless this tab has seen the project before, when the chat pane draws the remembered log instead (see above). **A live event after `ready` is not on screen in the same `act`**: wait for it (`findBy…`) or advance fake timers by `LIVE_BATCH_MS`. **Counting renders inside one `act` proves nothing**: React batches everything in an `act` regardless, so a commit-count assertion has to deliver one frame per `act`, as a browser dispatches one task per message. Relatedly, the first file listing runs immediately after `replayed`; later invalidations wait `LISTING_DEBOUNCE_MS`, and a test of those needs fake timers or an equal wait.

- **The workspace's polls back off when idle and stop in a hidden tab, and only the poll can see some of what they look for.** The session activity read (`useTurnSubmission`) and the publication watch (`usePublicationAdmission`) both run on `hooks/poll-loop.ts`: one read at a time, the read returning its own next delay, no timer at all while `document.visibilityState` is `hidden`, and an immediate read on becoming visible or on window focus. Activity is read every second while anything runs, queues or is being admitted, and every 15s otherwise. Measured in a real Chrome on an idle workspace, that went from 60 reads a minute to 4, and in a background tab from 30 (Chrome's own throttling) to 0. **The socket cannot replace the idle read.** A request another client queued writes no event until a worker claims it, so `running` is turned on for it only by the read, and the idle cadence is how late it can be. Focus is what usually catches it, since the person who queued it elsewhere is coming back. **New events bring the next read forward through `soon` and never restart the wait.** A nudge that reset the timer would starve the loop for as long as a turn kept streaming. **An unchanged answer must not call `setActivity`.** It is compared against a ref rather than through the updater form, and the test that guards it counts renders one `act` per read, for the batching reason in the event-stream entry above. jsdom's `visibilityState` never changes, so `testing/page-visibility.ts` overrides it. Headless Chrome does report a tab behind another one as `hidden` (`Target.activateTarget` on a second target), which is how the numbers above were taken.

- **Next preloads a `next/font` face on every route under the layout that calls it, so where a face is declared decides who downloads it.** All three faces used to sit in the root layout, and every route, the workspace included, preloaded about 220KB of woff2 that only the landing page and a few headings draw. The landing page's Newsreader and Inter now live in `app/(landing)/layout.tsx`, a route group holding `/` and the two `/demo/*` apps the landing page iframes that draw them (the ledger and the booking site). The other two demos draw neither face and stay outside it. Bricolage (`--font-display`) is **not** a landing face: sign-in, sign-up, `/welcome`, `/docs` and the preview pane's empty states use it, so it stays in the root with `preload: false`. **Both mistakes are silent.** A page moved out of the group renders in `sans-serif` and Georgia, and a face added back to the root costs every page again. `app/font-placement.test.ts` reads both from source. A static route carries the preload as `<link rel=preload>` in its HTML and a dynamic one carries it as an HTTP `Link:` header, so a check that greps only the HTML reports a dynamic route as clean. Measuring this needs `next start`. That server renames its process to `next-server`, so `pkill -f "next start"` misses it and a stale one keeps answering on the port with another build's chunks. Stop it by port (`lsof -ti tcp:<port> -sTCP:LISTEN`).
