# Gotchas: Sandbox and storage

Learned the hard way; don't rediscover them. Read this before touching `packages/sandbox`, `packages/storage`, snapshots, the desktop, the reaper.

- **A foreign listener beside Chrome's debugger made E2B startup fail closed.** Four real E2B desktops answered the owner's stream with `503 desktop_unavailable`, while the same script starts locally and in a replica built from the template's `e2bdev/base` image. A diagnostic run kept the script's failure line: "Port 9222 is not owned by this desktop." Port 9222 had two listening sockets. Chrome, the recorded owner, held one. No process visible to the desktop user held the other. This is consistent with envd forwarding, but the second listener's process identity and precise forwarding mechanism remain inferred. Sandbox URLs are public by default (`allowPublicTraffic`). The ownership check fails closed on the foreign listener by design. Do not "fix" this by ignoring non-loopback listeners: that could start the desktop while DevTools, which is full browser control, is exposed at the sandbox's public 9222 host. Public DevTools exposure was not measured. The waits in `start-desktop.sh` are now bounded by elapsed time, which `desktop-start.computer.test.ts` guards. That was an earlier, wrong guess at this failure, kept because it is sound on its own. The fix is that Chrome no longer has a debugging port: it speaks CDP over `--remote-debugging-pipe` to a bridge in the driver bundle whose only endpoint is a Unix socket in the private desktop state directory. This removes TCP debugging without depending on the foreign listener's identity or forwarding mechanism ([ADR-0019](../adr/0019-the-desktop-debugger-has-no-port.md)). `desktop-start.computer.test.ts` now starts the desktop beside a foreign 9222 listener. That is verified against Chrome 156 locally. What real E2B VMs have verified since is in [ADR-0019](../adr/0019-the-desktop-debugger-has-no-port.md).

- **A transport failure is not physical completion.** Computer input commits a project reservation before dispatch and retains it until a matched scope-drain proof permits conditional clear. Permanent remote closure rejects delayed originals. The input driver and input children share an inherited lock description; abort/error callbacks never replace child close. Cleanup checks all keyboard keys and pointer buttons. Duplicate terminal cleanup performs no input against a successor. Local Docker exec/result/helper failures preserve source and the VM. See ADR-0018 for recovery and the separate pre-existing lifecycle race.

- **A synchronous mousemove can stall when the pointer is already there.** The installed xdotool timed out moving to its current position in the real local app, so an owner mouse-move followed by a click never reached the click. Chain ordinary mousemove and click in one xdotool invocation; X11 preserves that command order. The same-position regression and the native local-app run cover this path. See [local app evidence](../research/computer-local-app/README.md).

- **A DOM prefix can contain only head scripts and styles.** The actual Chrome 156 policy page exceeded the DOM allowance before its visible blocked message appeared. Observe the body through fixed read-only CDP calls, fall back to the root when there is no body, and mark output truncation. The bounded result then prioritizes page content rather than head metadata. [Regression and native diagnostic](../research/computer-cdp-body/README.md).

- **Chrome browser UI can also be a debugger page target.** The actual Chrome 156 smoke listed an omnibox popup before the app after address-bar input. Selecting the first type page made DOM and console observations target browser UI. Classify web-content URLs as well, retain browser error pages, and keep the debugger connection off the network: it is a private Unix socket ([ADR-0019](../adr/0019-the-desktop-debugger-has-no-port.md)). [Regression and observed target order](../research/computer-cdp-targets/README.md).

- **An encoder's file stop threshold is not its finalized output size.** ffmpeg may write another packet and the MP4 index after reaching `-fs`. The desktop recorder leaves headroom below the accepted output ceiling and tests that agreement against real encoded video. It also records the encoder's PID and Linux start ticks, rather than its timeout monitor: killing only a stalled monitor left ffmpeg alive in the forced-stop experiment. [Reproduction and limits](../research/computer-recording-linux/README.md).

- **Nested repetition in a base64 regex can overflow on a valid video.** The desktop protocol uses a linear alphabet check and a separate length constraint. Its maximum-size regression executes the actual schema; small fixture strings missed the overflow. Transport limits also allow JSON escaping before base64, so a schema-valid text action fits the command envelope.

- **Chrome managed URL policy is not an extension match pattern.** A trailing `/*` in URLAllowlist blocked even the intended localhost dev server during the real desktop spike. Use a scheme, exact host and port without a trailing wildcard; prefix a hostname with a dot to disable subdomain matching. The desktop must prove its own app is visible before any model probe. The spike also hashes that checked JPEG before passing it to the nested image mapper. [Evidence and source](../research/computer-use-spike/README.md).

- **A recording announcement cannot be its only object index either.** `withAppTestRecording` drains `test.started` before capture. Its project/session/turn key remains derivable if upload succeeds but its announcement fails. Project deletion retains that log until object deletion succeeds. Old test starts do not claim a video exists: playback additionally needs an available recording event. Encoder-clock loss and lease loss cannot advertise a playable clip.

- **A test recording that fails to start is logged, never shown, and only its desktop start is retried.** On 2026-11-18 a production "Test the app" on a desktop the build turn never opened passed its assertions and lost its video; a retest on the same machine five minutes later recorded. `withAppTestRecording` now logs each failed step as `test recording could not start` with `step` (`desktop_start` or `recording_begin`), `attempt`, `elapsedMs`, and either `code` and `error` from the result or `err` when it threw, all under the turn's ids. Nothing is logged once the turn has been stopped. The event still says only `capture_failed`. `code` is nearly always `unavailable`, so read `error`: "Desktop operation failed." is the driver's reply from inside the machine, and "Nap's computer is unavailable." is the worker's side: the exec itself failed, or what came back was not a well-formed driver reply. The driver gives that one message for every error inside the machine, so carrying its own message out is a desktop build change that waits for the next template republish. The desktop start is retried once, because `start-desktop.sh` holds a lock for its whole run, but not after `cancelled`, `outdated` or `timeout`, or once the turn is aborted. A start the driver gives up on after its 45-second child deadline comes back `unavailable`, not `timeout`, so that slow failure can still be retried once. The recording's begin is never retried: a begin whose reply was lost may still be spawning ffmpeg, and a second one for the same recording would spawn another encoder writing the same files. Before the begin, one screenshot runs ffmpeg, since starting the desktop runs none and a fresh VM pages programs in from a lazily loaded disk while the recorder allows ffmpeg two seconds to appear and five to give a frame; the warm-up is abandoned after ten seconds (about fifteen in all, since the E2B adapter then waits up to five for its cancel to reach the machine), and a failed or abandoned one is logged as `test recording warm-up failed` with `step: "encoder_warmup"`, and capture goes on. The warm-up also consumes a zoom crop a cancelled computer batch left pending, which would otherwise have cropped the test agent's first screenshot. That cold-disk cause is inferred, not measured. The other guess, that the five-second wait is too short on a cold desktop, did not reproduce on the local desktop image at 2 CPUs and 2 GiB, whose disk is never cold: a cold start followed at once by a recording began in 0.6 to 0.7 s, and in 1.2 to 1.4 s with four CPU-burning loops beside it, six times out of six.

- **A screenshot announcement cannot be its only object index.** An upload can succeed and the following event append can fail. Computer screenshots use deterministic keys from the earlier tool call, and the runtime's `beforeStore` hook drains that call before any upload. Project deletion derives keys from all durable computer calls, including ones with no screenshot event, and keeps the log if reading that index or deleting an object fails. See ADR-0018 for the choice over a second table.

- **A project's thumbnail can only be taken while its sandbox is alive, so it is taken at every moment one is known to be up — and only those.** A preview URL answers for exactly as long as the sandbox behind it, and the dashboard is looked at days later with nothing running, so the card shows the app as of the last such moment: the end of a turn that committed and was neither stopped nor left with a repair to come, and a project coming back up (`#resumeLogged`, gated on `created` — a sandbox that was already serving has not changed since whatever last photographed it). **Turn-end capture alone is not enough and the reason is worth remembering**: it leaves every project made before the browser existed with no picture and no way to get one short of paying for another turn, which is exactly the state this repo was in the day captures shipped. A close or a sweep takes no picture of its own. At a turn's end and at a resume, the runtime only *asks* for one, and the thumbnail lane takes it after the lease has gone back (`ThumbnailLane`, `docs/scaling-design.md` §17 B-7, ADR-0022); a failure is a log line and nothing more. Three further constraints hang off it. It uses **`waitForPreview`, not `getPreviewUrl`**: the second only composes an address, and a screenshot of an address nothing answers at is a picture of an error page, indistinguishable from the user's app being broken. Its key is **derived from the project id and overwritten**, so unlike a snapshot there is no row naming it — which makes it the one object a delete cannot find by listing, and `deleteProject` removes it explicitly and deliberately leaves it out of `objectsDeleted` (deleting a key that was never written succeeds, so counting it would claim an object was removed for every project that never had a picture). And the capture is **behind the `PageCapture` port with the browser optional**: `NAP_CHROME_PATH` unset means turns run exactly as before and the card falls back to the colour hashed from the project id, which is what every card showed before this existed. On the client the image is a plain `<img crossOrigin="use-credentials">` — the API is another origin, so without that attribute the request carries no cookie and every card 401s, and `next/image` is not an option at all because its optimizer is a server holding none of the user's credentials.

- **E2B's contract differs from ours in three places**, all resolved in `packages/sandbox/src/e2b-sandbox-manager.ts` and all found by running the conformance suite for real. `commands.run` **throws `CommandExitError` on any non-zero exit** — ours treats a failing command as data, so the adapter converts it; without that, a failing build reaches the agent as an infrastructure fault. `AuthenticationError` extends `Error`, **not** `SandboxError`, so an `instanceof SandboxError` catch-all silently misses a bad API key. And E2B validates the *shape* of a sandbox id before looking it up: an arbitrary string is `400: Invalid sandbox ID`, not a 404, which is why the conformance harness supplies `unknownSandboxId()` rather than inventing one.

- **E2B stops a command after one minute unless told otherwise, and neither aborting nor a deadline stops what it started.** `commands.run` defaults `timeoutMs` to 60 000, whatever the command is, and the failure looks like the sandbox falling over: a 90-second build came back as a verification that "learned nothing", and a setup command promised ten minutes died at one. So anything that may run long names its limit, from `packages/shared/src/command-windows.ts`, and `InMemorySandboxManager` enforces the same default against a scripted `runsForMs` so that forgetting fails a test. The second half is the less obvious one. The SDK's `signal` only drops the connection, and the command carries on. Its deadline and its `kill` do signal, but only the one pid envd spawned: upstream envd sets no process group, so `tsc` under `bun run` under `bash` outlives both. A caller that wants the work gone passes `stopOnGiveUp`, and the adapter then runs the command in a group of its own and signals the group through a second command when the call gives up (`packages/sandbox/src/e2b-exec-group.ts`). The id comes from a file the group writes rather than the SDK's pid, because that pid is the shell around `setsid` and `setsid` forks if it already leads a group. `--wait` is what stops a forking `setsid` reporting a check as passed before it has run. It is opt-in because the desktop driver has to survive an abort for long enough to release what it holds. Repository setup does not use it, because its script signals its own process group. A worker that dies outright sends no stop, and nothing else bounds the group: the sandbox's own deadline is no limit, because every later turn on that project pushes it back, so a command that never ends by itself, such as a watcher, can run on through turn after turn. Giving the grouped command a `timeout` of its own, as setup's script has, would close this; nothing does yet. A stopped command exits non-zero, so anything reading exit codes has to check the signal first, or a cancel reads as a failed check and opens a repair turn. For the same reason, do not read a cancel off the error: an abort and a deadline both come back as a `TimeoutError` and so as `code: "timeout"`, with a message that blames `requestTimeoutMs` for the abort, and a sandbox found dead mid-request is a `TimeoutError` too, while a dropped connection is `unavailable`. Neither the class nor the code says why a call gave up, so check the signal. Against a fake envd under Bun, the real SDK rejects within milliseconds on all of these. Real E2B has not yet run the group or the stop: the two cases in `e2b-sandbox-manager.integration.test.ts` are what would.

- **A command that starts something in the background must redirect the whole backgrounded group, or E2B waits for it to end.** E2B answers `commands.run` once the output pipes of the `bash -l -c` shell it runs close (seen in production and reproduced locally, not read in envd's source). In `cd dir && nohup server >log 2>&1 &`, the redirections cover only `server`. Bash forks a subshell for the backgrounded `&&` list, and that subshell keeps the pipes for as long as the server runs, so the call hits the 60-second default above and fails. Every repository with a development command failed to start this way in production until `prepareRepositoryEnvironment` switched to `(cd dir && exec nohup server) </dev/null >log 2>&1 &`. Test such a command under `bash`, not `/bin/sh`. On CI `/bin/sh` is dash, which hands the pipes over, so it passes the broken form (`repository-environment.test.ts`).

- **The sandbox project template is built by hand** — `bun run template:build` in `packages/sandbox`, never by a test. It publishes a named, billable artifact that later sandbox creation depends on. `packages/sandbox/template/` is a separate app with its own React/Vite toolchain: it is outside our tsconfigs on purpose, so the only thing that type-checks it is a `tsc` run *inside* a sandbox, in the integration suite. That check earned itself immediately by catching two broken imports.

- **A machine's desktop runs only if its image is this runtime's build, and an `outdated` refusal is the check working.** The template and the runtime ship separately and a merge to `main` releases, so the published desktop was once older than the driver code the next deploy would run against it. Every driver command now first compares the image's build file with `DESKTOP_BUILD` ([computer use](../computer-use.md#desktop-builds)). Do not clear an `outdated` refusal by setting `DESKTOP_BUILD` to whatever the published image says, or by loosening the gate: either runs a driver against code it was not built for. Republish instead. The build hashes sources rather than the bundled driver because the bundle's bytes differ between Bun versions, and CI pins one that local machines may not have. `DESKTOP_SOURCES` must name every module the bundle inlines; a test compares the two, so a new driver import fails it rather than escaping the hash.

- **The template's `scripts` are the entire surface the verification loop can see, and an edit to them is not live until the template is rebuilt.** `@nap/verify` discovers checks by package-script name, so adding or removing one means editing `packages/sandbox/template/package.json` *and* running `bun run template:build` — and projects created from an older image keep the old manifest in their git history, so they stay blind until they are recreated. Neither the free suite nor a dry run can tell you which image is published: `test/template-checks.test.ts` reads the manifest from disk, and an in-memory sandbox has no `package.json` to discover from at all. What that blindness costs is recorded in `docs/napbench-verification-measurement.md`.

- **The template ships a design system, and three things have to move together when it changes.** `src/index.css` holds the token block every primitive in `src/components/ui` reads, `AGENTS.md` is the brief that tells the agent to restyle those tokens rather than scatter literal colours, and `TEMPLATE_FILES` in `packages/sandbox/src/template.ts` is the list two integration tests check a real project against — a component added without that entry is never verified to have arrived. Two further traps. The `@/` import alias is declared **twice**, in `tsconfig.json` `paths` and in `vite.config.ts` `resolve.alias`: TypeScript resolves it for `bun run typecheck`, Vite for the bundle, and neither reads the other's config, so dropping one gives you a project that builds and does not typecheck or the reverse. And a Tailwind utility naming a token that does not exist — `bg-canvas` after `--color-canvas` was renamed — **compiles to nothing at all**, silently, so palette edits are guarded by `test/template-design.ts` instead: it re-computes the WCAG ratio of every pair the primitives put together, because the alternative is finding out from an axe audit in a funded run.

- **A turn's commit is one sandbox command, and fakes answer it by `COMMIT_COMMAND`.** `commitAll` used to stage, diff, commit and read the sha as four execs, each a round trip. `commitScript` in `packages/sandbox/src/git.ts` now does all four and prints either the new sha or `NOTHING_TO_COMMIT` on its last line. Any other output, empty included, is an error and never a clean tree, so a fake whose `defaultExec` answers `""` fails the commit loudly. The script spells its commands `--all`, `--quiet --cached`, `--verify` and `--message=` on purpose: tests across the repo hold patterns like `/git rev-parse HEAD/` for `currentSha`, and with the old spellings those patterns would answer the commit too, letting a test pass while exercising nothing. Script it through `scriptGit`, or `COMMIT_COMMAND` with `committed(sha)` / `NOTHING_COMMITTED`. One script also means one E2B command timeout of 60 s for all four steps, where each used to have its own.

- **A snapshot's bundle travels as a file, both ways, and is always the whole history.** `bundle` writes it in the same command that prints HEAD's ref, then reads it back with `readFileBytes`. `restoreBundle` uploads it with `writeFileBytes`. It used to come back as base64 through the command's output, a third larger and streamed through the command channel on every turn, and to go in as a base64 text file that a second command decoded. A fake that answers `git bundle create` with stdout alone leaves no file behind, and the snapshot fails with `file_not_found`: answer `BUNDLE_COMMAND` with `bundled(head, bytes)`, which uses the fake's `writes` to leave one. Incremental bundles against the previous snapshot would move less each turn, and were deliberately not built: a restore would then need every bundle in the chain, and the snapshot exists so that recovery depends on one object. The restore's git steps are one `&&`-chained command after the upload, carrying a `probe` that runs on the old tree and the new one in the same round trip: a fake answering `RESTORE_COMMAND` with no stdout reports neither, which the runtime treats as "cannot tell" and installs. Answer it with `restored(before, after)` from `testing/script-git.ts`.

- **Anything from a model that reaches a command line must be shell-quoted.** `shellQuote` lives in `packages/shared/src/shell.ts` because two unrelated callers need it — git commit messages and the `search_files` grep pattern — and the attacker is whatever the user typed into a chat box. The one deliberate exception is `run_command`'s command itself: quoting it would turn a pipeline into a filename, so what may run is the safety guard's question instead — `packages/agent/src/safety/commands.ts`. Quoting is verified by round-tripping hostile inputs through a real `sh` in the unit tests — asserting on the *shape* of the quoted string does not distinguish safe from unsafe, because the payload text is present either way.

- **A bound port is not a loadable preview.** E2B's `waitForPort` readiness check fires when something binds the port *inside* the sandbox, but users reach it through a public proxy that becomes ready separately, and its 502s during that gap are "not yet" rather than "broken". `waitForPreview` on the `SandboxManager` port polls the real URL for a 200; anything showing a preview should wait on that, not on `getPreviewUrl`, which only composes an address and promises nothing.

- **A new sandbox's `preview.ready` is started, never awaited — and the sink, not the call sites, keeps it in bounds.** The runtime used to wait up to its preview timeout for the dev server before the agent's first model call; a restore that reinstalls dependencies spent all of it there. `#startPreviewAnnouncement` now hands the wait to `EventSink.eventually`, which writes the event the moment the dev server answers, wherever the turn's stream has got to. Three rules hold, and each is the sink's or the entry point's rather than something a caller must remember: **it precedes the first ending emitted after it was started** — a `turn.completed`, `turn.failed` or `job.completed` emitted while it is outstanding is held, with everything after it, until it is known; on a turn that is the turn's own ending, and on a resume whichever the continuation it runs writes first; **it is settled before verification**, which probes the preview itself; and **nothing is written after the runtime returns**, because every entry point calls `sink.settle()` in a `finally` and the lease is released the moment it returns. `drain` waits for it only when an ending is held behind it — drain runs all through a turn, and waiting there would put the wait back. The port's `waitForPreview` takes no signal, so the wait is raced against the turn's, and a cancelled turn ends at once — without its announcement, which is therefore not decided by "did this call create the sandbox?" alone: `preview-announced.ts` also announces a running sandbox the log has not announced since its last `preview.stopped`, so the next turn or resume makes good a cancel, and a dev server slower than the timeout, without re-announcing (and remounting) one that was. **That makes a dev server that never answers 2xx at `/` a cost on every call, so only the creating call waits the full timeout**: a sandbox found running and unannounced gets `PREVIEW_RECHECK_MS` instead, which is how long a short turn's ending — and the lease, and a queued message behind it — can be held for a 404 at the root, an API-only server or a crash, on every turn until it answers. The price is that a recheck can miss a server still coming up (a resume right after a cancelled restore); the next call asks again. **A cold open still makes the next message wait.** The resume that created the sandbox settles its announcement before it returns, under its lease, so an ordinary message sent right after pressing Resume is accepted and queued behind that wait, up to `PREVIEW_TIMEOUT_MS` when the dev server never answers (an imported API-only repo, say). Dropping the settle is not the fix, because it writes `preview.ready` after the lease is gone; removing the wait needs a signal telling the running open that a request is queued, so it can give the announcement up to that request, and nothing sends one yet. **Known gap:** the predicate asks the log, not the provider. A sandbox reclaimed without a `preview.stopped` (the provider's timer, or a close whose best-effort append failed), followed by a restore whose turn is cancelled before it answers, leaves the old `preview.ready` as the last word — the pane points at a dead URL until the project is next closed or put away. The follow-up is to compare that event's `url` with `getPreviewUrl(id, port)` and announce on a mismatch. Because it can land mid-stream, the chat's folds (`apps/web/src/chat/transcript.ts`, `timeline.ts`) look past a preview line when joining streamed prose or grouping tool calls. The app-test path still waits, inside `beforeCapture` and for the full timeout even on a sandbox it did not create, because the recording starts as soon as that returns. Its position in the log is the dev server's timing, not a contract: assert the rule (`testing/preview-announcement.ts`), not an index.

- **"Missing" and "could not tell" are different failures, and only one of them may fall back.** Opening a project restores its last snapshot; a snapshot that is *absent* or that git refuses falls back to a fresh template with a `system.notice`, because the work is gone either way and an error page in place of an app helps nobody. A store that cannot be *reached* fails the open instead — hand back an empty template on a transient outage and the next teardown snapshots the emptiness over a good snapshot. `packages/runtime/src/restore.ts` used to fetch the row and the bytes *before* creating a sandbox, so a storage failure cost nothing. For a template project it now reads them while the sandbox is created, and destroys that sandbox on a storage failure: seconds of billing, traded for a reopen that no longer waits for the two in series (ADR-0032). An imported repository still fetches first, because its first download can wait minutes and a sandbox created beside that wait could outlive its own deadline.

- **A reopen installs only when nothing it has can be shown to match, and the proof is a key, never a comparison of file contents read one by one.** The template's `bun.lock` is tracked (`bun install` runs during the image build, before `git init`), so `restoreBundle`'s probe can hash the committed install inputs (`package.json`, both lockfile names, `bunfig.toml`, `.npmrc`, `patches`) and the toolchain on the template's tree and on the project's, inside the restore's own command. Equal, the baked `node_modules` is the project's. Otherwise the project's archive at `projects/<id>/dependencies.tar.gz` is extracted, only if its header key is exactly `dependencyCacheKey(template, project)`, and every other outcome installs. It used to compare lockfiles against the *template's*, so any project that had ever added a package reinstalled on every reopen. Three traps. **The install itself says what may be cached, and there are two kinds**: the install command checks `git status` either side, and caches `node_modules` only when no root lifecycle script, workspace, local package or newly installed package with an install script could have read something the key does not hold. Otherwise it caches Bun's downloaded packages (`kind: "packages"`), and a reopen installs from them with `bun install --offline --frozen-lockfile`, which runs the scripts again on the opened tree. Both installs pass `--backend=copyfile`: Bun hardlinks by default on Linux, so a script editing a dependency in place would edit the cached copy that gets archived. A key read from HEAD cannot see an install that rewrote its lockfile, and a script can read anything. An install that changed a committed file caches nothing and opens with a warning naming it. A fake answers the two installs with `INSTALL_COMMAND` and `OFFLINE_INSTALL_COMMAND`, and the two archives with `ARCHIVE_COMMAND` and `PACKAGE_ARCHIVE_COMMAND`, whose `tar` flags are spelled apart for exactly that. **An archive is only ever made from an install a restore ran**, never from a live sandbox at the end of a turn: the agent's own `node_modules` may not be what the committed inputs produce. And **it is made after `openProject` returns, while the turn runs**, which is why `archiveDependencies` refuses a tree that moved after the install's record (by `ctime`, which a tarball extracted over the tree cannot set back), and why tool caches such as `node_modules/.vite` are excluded from both the archive and that check: a dev server writes them whenever a page is loaded. `storeArchive` never rejects, so a mistake inside it fails silently; its tests await `dependencyCacheWrite` and assert `true`. Nothing in a restore boots Vite: `setStartCmd` already did that as part of sandbox creation. See ADR-0032.

- **E2B kills a sandbox five minutes after it is created, whatever is happening inside.** `defaultSandboxTimeoutMs` is 300 000 and the timer starts at creation, not at the last thing anyone did — so a conversation that pauses for a coffee comes back to a workspace that no longer exists, and a reaper meant to snapshot idle projects loses that race every time. Sandboxes are created with an explicit `timeoutMs` and every turn pushes the deadline back through the `keepAliveMs` it passes to `SandboxManager.resume`. That rides on the resume because on E2B both are one `connect` request; a separate `extendTimeout` afterwards was a second round trip at the start of every turn, and `acquire-sandbox.test.ts` fails if one comes back. E2B's connect only ever *lengthens* a deadline, so the port promises "at least", and a `resume` without `keepAliveMs` still sends the SDK's five-minute default. A wrapper that forwards `resume` must forward its options too: dropping them type-checks.

- **Somebody looking at a project is activity, and three easier versions of that are each wrong.** Reading code or using the preview writes no event, so the idle sweep used to reap the sandbox under the person using it. A visible tab now sends `viewing` when its socket opens, when it becomes visible, and beside each `pong` — not the `pong` alone, since the first ping is half a minute after connecting and a sweep in that window would take the sandbox from someone who has just come back — and `PostgresProjectSandboxStore.recordViewer` stamps `projects.viewed_at`, which `sweepIdleProjects` reads (`packages/runtime/src/reaper.ts`). (1) **Not the socket being open**: a background tab answers the heartbeat too, so a forgotten tab would keep a sandbox billed for as long as the laptop stays awake. (2) **Not `updated_at` or an event**: those are the activity clock that `NAP_VIEWER_KEEP_WARM_MINUTES` is measured from, and a viewer moving that clock would make the cap reset every minute and so never apply. (3) **Not `extendTimeout`**: it *replaces* a deadline and could cut short the longer one a turn's verification set. The sweep keeps warm with `resume({ keepAliveMs })`, which only ever lengthens it. Sparing the project is only half of the fix, since E2B's timer runs from the last turn and kills what the sweep spared. The throttle is in the statement's `where`, because the row is shared by every tab on every pod; a per-connection limit in `apps/api/src/ws/viewer-signal.ts` stops one looping client from making each frame a query. A viewer never makes a project *busy*, so close and delete are unaffected.

- **The E2B adapter's handle cache forgets a handle when a call through it says the sandbox is gone, and holds at most `HANDLE_CACHE_LIMIT`.** Nothing in a process hears about a sandbox ending elsewhere: the reaper is another process, and E2B's timer kills sandboxes nobody destroyed. So a cached handle used to fail every later call through it, and the map only ever grew. A `not_found` drops the handle, and so does a `timeout`, because E2B answers a file operation on a dead sandbox with a 502 that the SDK raises as `TimeoutError`. The next call then reconnects, or reports the sandbox missing. Dropping a good handle costs one `connect`, nothing more. **That `connect` can lengthen a deadline**: the SDK sends its five-minute default with it. That matters to the thumbnail lane, which ADR-0022 says never extends a sandbox because its handle is cached. A timeout can evict a live handle, and the size cap does not pin active handles. The lane can therefore reconnect and extend or resume a sandbox after eviction. A killed sandbox still reports missing; reconnect does not recreate it. **The relationship between the two numbers is load-bearing: the reaper's idle threshold must stay below the sandbox TTL**, because the reaper snapshots before destroying and E2B's timer does not. `apps/api/src/env.ts` refuses to boot when they are the wrong way round.

- **The reaper destroys sandboxes it cannot find in the database, and the two guards on that are the whole design.** A sandbox created a moment before the row recording it failed is running, billed, and named nowhere — the only way to find it is `SandboxInventory.list()`, asking E2B what it is running. That capability is dangerous in exactly one direction, so `reconcileCapacity` (`packages/runtime/src/reconcile-capacity.ts`) refuses to use it twice over. **A failed read of the reference set returns immediately rather than carrying on with what it got**: everything below destroys what is *missing* from that set, so an unreachable Postgres would otherwise read as "nothing is referenced" and take the entire estate with it. And **nothing younger than a five-minute grace window is touched**, because a sandbox exists for a moment before anything is written down about it — without the window this pass races every acquire in the cluster and wins some of them. Two further guards are about *whose* sandbox it is, and the second is the one nobody expects: a sandbox with no `projectId` in its metadata was made by something else sharing the account — and a sandbox whose `projectId` this database has never heard of belongs to **our own tooling**. `bun run harness --real` creates sandboxes on the same E2B account against a throwaway database or none at all, so a deployed reaper that destroyed everything it could not account for would kill that run five minutes in. The same reasoning runs the other way in `PostgresCapacityReconciler`, where an `active` row is only believed stranded once it is older than the same kind of window: reclaiming a healthy row does not destroy anything, but it un-counts a live sandbox, which raises the ceiling that exists to cap the bill.

- **R2 is the S3 API, so the adapter is `@aws-sdk/client-s3` with `region: "auto"` and an account-scoped endpoint** — the bucket is a path, not a hostname. Failures are mapped by `name` and HTTP status rather than `instanceof`, because a missing object arrives as `NoSuchKey` from one call and `NotFound` from another, and the two mean the same thing. Keep `not_found` and `unavailable` apart at all costs: restoring a project falls back to a fresh template for the first and refuses to open for the second, so collapsing them loses work.

- **In the E2B base image, `/usr/local/bin` precedes `/usr/bin` on PATH.** Installing a newer Node from NodeSource lands in `/usr/bin` and changes nothing — `node --version` still reports the image's 20.9, silently, until something refuses to start. The template build relinks the binaries; anything else installing tooling into that image needs to do the same.

- **Deleting a project runs the opposite way round from putting one away.** Teardown writes everything down *before* destroying anything; a delete destroys in the order that keeps a retry possible — sandbox, then the R2 objects, then the rows. The snapshot rows are the only record of which objects exist, so deleting them first strands every bundle: unreferenced, unfindable and billed forever. `packages/runtime/src/delete-project.ts` stops before touching the database if any object delete fails, which is safe because `ObjectStore.delete` treats a missing key as success and the whole call can simply be made again.

- **A turn's work reaches R2 at the end of that turn; the reaper exists to stop paying for idle sandboxes, not to keep work safe.** That split is recent and was earned. Snapshots used to happen only in `putProjectAway` — close, or the reaper — and the reaper runs in this process, so a deploy or a crash left E2B's own timer to delete the only copy of everything since the project last went idle. `captureSnapshot` in `packages/runtime/src/teardown.ts` is a teardown minus the destroy, and `SingleAgentRuntime` calls it after the turn's terminal event is persisted, so nothing the user waits on is delayed. **Only when the turn committed** — a git bundle holds commits, not a working tree, so a turn that changed nothing (and a turn that failed before `finalize`) has genuinely nothing new to capture. **A failed snapshot never fails the turn and is never shown to the user**: the work is still in the live sandbox, the reaper is still the backstop, and a warning nobody can act on is what trains people to ignore the ones that matter. Consequence worth knowing: `tearDownProject` now **reuses an unchanged snapshot** rather than re-bundling, because arriving at an already-stored commit is the normal case once turns snapshot themselves — but a `latestFor` that *fails* must fall through and capture, since knowing whether it changed is an optimisation and the snapshot is not.

- **A project outliving its sandbox is announced, and resuming one runs on the turn queue.** Nothing used to say that a sandbox had been destroyed, so a preview pane kept an iframe pointed at a host that had stopped existing — the provider's "not found" page rendered inside a frame that otherwise looks like a working app. `putProjectAway` now appends **`preview.stopped`** to *every* session of the project, keyed to the destroy rather than to the bookkeeping (a failed row update still means the sandbox is gone) and deliberately silent on the one path that leaves it serving. Bringing a project back is `Runtime.resumeSession`, and it is **serialised against `runTurn` per session** — that is the whole reason it can be offered at all, since both paths create a sandbox when the project has none and a page that resumes while its user types would otherwise start two. That serialisation is the per-session *lease* now, not the in-process `SessionQueue`; both entry points enqueue a request and a worker claims it. Its failures are a `system.notice`, never a `turn.failed`: no turn ran, and `previewState` reads a sandbox failure as the state of the last turn. `POST /projects/:id/open` applies **the same sandbox quota a turn does**, because a ceiling with two doors is not a ceiling. The one thing still not announced by anyone is a sandbox the provider reclaims on its own timer, which is why the preview pane trusts `project.sandboxId` over a replayed `preview.ready` until somebody presses Resume.

- **Opening a project is the only thing that continues a job, and most opens continue nothing.** A process restart leaves a job open rather than failing it, and nothing sweeps for those — an autonomous loop spending tokens with nobody watching is a bill, and a crash loop plus auto-continue is a large one. `resumeSession` folds the log through `continuationFor` (`packages/runtime/src/continue-job.ts`, pure, so what an open costs is a table rather than a trace) and gets one of four answers, three of which spend nothing. **The log is not the only input, because it cannot be**: a turn commits inside `finalize` and the sha reaches the log only with `turn.completed`, so a worker dying in that gap leaves a real commit in the sandbox and a log saying nothing was committed — read from the log alone, that job closes `unverified` and the work sits permanently outside the verification loop. The restored workspace's own `git rev-parse HEAD` goes in beside the fold as evidence, and wins wherever it can be read, since it is the commit the checks are about to run against. It is read only once a job is found open, so the opens that continue nothing still cost no round trip; a HEAD that cannot be read at all falls back to the log. Two of its rules are counter-intuitive and both come from `foldJobs` counting repair attempts from **`verification.started`**. A round that was begun and never answered is *finished* rather than begun again — writing a second `verification.started` for the same round consumes an attempt no repair turn ever used, which is what `announce: false` exists for. And a job left `repairing` is repaired **from the failure the log recorded**, not by re-running the checks: the commit has not moved, so re-asking learns the same thing and costs an attempt for it. That is why `VerifiedCheck` and `RanCheck` meet in a `CheckFailure` — the log keeps no `detail`, so a continued repair says where its failure came from instead of inventing an exit code. Continuing runs turns, so `POST /projects/:id/open` resolves model access exactly as a turn route does: without it the deployment pays for a BYOK user's repair loop.

- **Anything that writes to the real bucket from a test must delete every key it wrote, not the newest one.** `full-cycle.integration.test.ts` runs against a throwaway Postgres and a *real* R2, so the rows naming its objects die with the container — it collects `snapshots.listFor` inside `beforeAll` and deletes them all in `afterAll`. It used to delete exactly one, which was correct only while a run produced exactly one; per-turn snapshots would have silently turned it into an orphan generator. There is no automatic orphan detection: the check is joining `ListObjectsV2` against the `snapshots` table by hand, and it has found real orphans.

- **On the sandbox, `/bin/sh` is dash, and dash's `kill` refuses `--`.** `kill -TERM -- -PID` is the textbook way to signal a process group and it is an "Illegal number" error under dash; a script with an `|| kill PID` fallback then stops only the leader and leaves its children running — a stopped background shell whose dev server is still bound to the port. macOS cannot show this, since its `sh` is bash. Write `kill -TERM "-$pid"` and test shell scripts on Debian as well (`node:24-bookworm` in Docker, running vitest under Node; see Testing). The same run proved `setsid` is present there and absent on macOS, which is why `shell.ts` starts a shell with `setsid` and falls back to `set -m`.

- **The context engine and the files panel list the project with `SandboxManager.listTree`, one call, never a `listFiles` walk or its own `exec`.** The walk was a round trip per folder, one after another, before every model turn and every time the panel opened or a file changed; both now cap the one listing with the same breadth-first `walkBreadthFirst`, and differ only in what a failure means — a missing hint for the model, a 503 for the panel; an `exec` from context assembly would throw on every scripted test sandbox that never scripted it (below). Every real shell answers through `listTreeViaExec` in `@nap/shared/list-tree` — git first for `.gitignore`, `find` in the same command when it is not a repository, NUL-separated, under an explicit deadline. Two things about git bite here. It prints untracked files before tracked ones when asked for both at once, so tracked and untracked are two calls, tracked first, or an unignored `vendor/` fills the byte ceiling and cuts every file the project owns; and its index is not the disk, so paths the index still has but the disk does not are subtracted, or a file deleted this turn is listed as present — and a failure says the listing is unavailable instead of failing the turn. The shell adapter also rejects output that reaches its 1MB byte ceiling: committed excluded paths can consume that ceiling before source paths, so treating a cut as success could show an empty project or let deep paths displace shallow ones. The panel returns 503 in that case; the context digest omits the hint.

- **Anything the agent loop does on *every* tool call must use a port method that answers "missing", never `exec`.** `InMemorySandboxManager` throws on a command nobody scripted — on purpose, it is a mistake in the test — so a hook that probed for a file with a shell loop broke every scripted turn in the repo at once. The project-rules hook reads candidate files with `readFile` in parallel, where `file_not_found` is an ordinary answer on every implementation.

- **A file kept outside `/home/user/app` is gone whenever the sandbox is replaced.** A snapshot is a git bundle of the project, so a project reopened after the reaper, a crash or E2B's timer comes back from the template with nothing else the old sandbox held. The compaction history lives in `/home/user/.nap/history` for exactly the reasons that also mean it is not snapshotted. So it is treated as a cache: each turn of a compacted session checks the record beside it and regenerates the file from events, and the agent is told about the file only after that check or write succeeded. Any new state that lives in the sandbox and outside the project needs the same arrangement, or a resumed session will point the agent at something that is not there. See ADR-0021.
