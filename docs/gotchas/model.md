# Gotchas: Model and provider

Learned the hard way; don't rediscover them. Read this before touching `packages/agent`, prompts, caching, streaming, OpenRouter, cost.

- **Nested JPEG tool results are measured on both Sonnet 5 and Opus 5 through OpenRouter.** The real spike used the production request mapper and a forced structured report of a random marker present only in the screenshot. Both models read it correctly with reasoning disabled and a 512-token output ceiling. The first blocked-page image correctly yielded UNKNOWN, so endpoint acceptance alone is insufficient; check actual visible fixture pixels before spending. [Reports and limitations](../research/computer-use-spike/README.md).

- **An app test is a separate turn, not another verification repair.** The queue stores kind `test` with the approved job ID, not a caller-written prompt. Under the lease, the runtime checks the latest completed checkpoint, actual HEAD, and a clean worktree, then builds the prompt from that job’s goal and full commit range. It records `test.started` rather than a `user.message` containing the generated diff: the context engine protects user requests across eviction and compaction, so storing that prompt as one would retain a large stale diff forever. During active-test compaction, rebuild it as the current request instead of a continuation whose prompt is assumed to be in history. A real-context regression test catches its loss. Test turns have their own budget, source-reading tools and computer input; write/edit/command calls are refused even if the model invents them. No commit, deterministic arbitration, checkpoint, or automatic repair runs on this path.

- **A test verdict needs confirmed input and a screenshot delivered to the model.** `AppTestRun` records an `untested` assertion before input and requires its ID and expectation to remain fixed. Authorization does not confirm input. Failed or ambiguous dispatch, including a thrown adapter failure, invalidates earlier evidence until fresh successful input and a delivered screenshot follow. Stored screenshots qualify only when their image blocks survive pruning and reach a model request. Sibling calls from the response that produced the screenshot cannot use it. Later image pruning preserves eligibility already earned through delivery. Setup precedes test chapters. A worker lost mid-test is closed as interrupted by the janitor; existing assertions survive and no test is requeued. These guards enforce sequence, not the model’s factual judgement.

- **Images inside tool results need mapping and accounting at both levels.** The installed Anthropic SDK's `ToolResultBlockParam.content` accepts text/image block arrays. Nap maps nested JPEG observations to `source: {type: "base64", media_type, data}` and keeps the outer tool result's ID, error flag and cache marker. Both `estimateContextTokens` and the context engine count nested images at the existing image estimate instead of charging for base64 text. The scripted provider snapshots requests before later pruning can mutate them. The upstream `claude-api` skill was read for this milestone because no local copy was installed; no model/configuration migration was made. Free tests prove the SDK request shape only. The image-forwarding measurement is linked above.

- **Read the `claude-api` skill once per milestone that touches the Anthropic API, and pin what you learn here as a gotcha.** Never answer from memory — the model id, `effort: "xhigh"`, `display: "summarized"`, `stop_reason: "refusal"` handling and tool-call mechanics are all details that change, and the intelligence plane is where a stale recollection costs most. But do not re-read it per task either: the skill inlines its whole documentation set, most of which (Managed Agents, Bedrock, Vertex, model migration) can never apply here, and it dominated one session's context to answer a single question about tool-definition shape. The first task of a milestone reads it and writes the answers down; every task after that reads *this file*. A written record is not recollection — the `usage.input_tokens`, `signal`-argument and `maxRetries` notes below are exactly that, captured once and load-bearing ever since.

- **The build-mode command guard refuses `2>/dev/null`.** `inspectCommand` resolves every redirect target as a path and `/dev` is in its system directories, so a model's habitual `2>/dev/null` comes back `destructive-filesystem`. `2>&1` is split at the `&` into a second segment headed `1`. Found while implementing plan mode and left as it was; loosening it is a guard change that needs its own failing test first. Plan mode refuses `run_command` entirely, independently of this guard.

- **`usage.input_tokens` from the Anthropic API is the *uncached remainder*, not the input total.** Cache writes and cache reads are billed and reported in their own fields (`cache_creation_input_tokens`, `cache_read_input_tokens`), so a heavily-cached call can report a few hundred input tokens against a prompt of tens of thousands. `toTokenUsage` in `packages/agent/src/claude-provider.ts` sums all three into `inputTokens`, so that it is the size of the prompt, **and keeps the two cached parts beside it** (`cacheWriteTokens`, `cacheReadTokens`) — because the budget charges each part at its billed weight, and folding them in without saying so made a cache read cost the budget ten times what it cost the bill, ending cached turns around their eleventh step. Build, add and price usage only through `@nap/shared/usage`; a hand-written `a.inputTokens + b.inputTokens` drops the split at the first `+`. The weights differ by model, so charge usage at the `billedWeights` of the `LLMTurn` that produced it — a fallback and a helper each have their own — and never pass one turn's weights for another's usage. Old browser tabs parse usage strictly, so the API strips the cache fields unless a socket sends `usageCacheSplit=1`. See [ADR-0034](../adr/0034-the-turn-budget-is-denominated-in-what-is-billed.md). Tests pin both halves.

- **The Anthropic SDK takes `signal` in its *second* argument, not the request body** — `messages.stream(body, { signal })`. And under `exactOptionalPropertyTypes` a narrow client type must say `signal?: AbortSignal | undefined`, since "absent" and "present but undefined" are different types and no-signal is the normal case.

- **A throttled model arrives as a 200 that fails halfway through, and no status code goes with it.** OpenRouter accepts the request, starts the stream, and reports the upstream rate limit as an SSE `error` frame; `core/streaming.js` turns that into `new APIError(undefined, body, …)` — **`status` is `undefined`** and the only clue is `type`, copied from `body.error.type` (`rate_limit_error`, `overloaded_error`). Every status-based retry rule is blind to it: `RateLimitError` is constructed *only* from a 429 response, so `isRetryable` gave up on the first attempt and a turn that three retries would have saved died instead. Worse, `APIError.makeMessage` looks for `message` at the *top* of the body, does not find it one level down at `body.error.message`, and falls back to `JSON.stringify(body)` — which is how a wall of vendor JSON ended up in a user's chat. Match on `type` before `status`, and pull the sentence out of the body yourself (`describeError`). A rate limit also needs its own backoff: half a second is right for a dropped socket and spends all three attempts inside the same per-minute window.

- **The SDK's own retries are invisible to a test.** `new Anthropic()` retries twice by default, so a provider that also retries makes three attempts look like nine and "gives up after N" unprovable. `ClaudeProvider` constructs the client with `maxRetries: 0` and owns the loop.

- **All of a turn's `tool_result` blocks go back in one user message.** Parallel tool use is on by default: a single assistant message can carry several `tool_use` blocks. Answering them in separate user messages is accepted by the API and quietly trains the model to stop asking for tools in parallel — the failure is a slower agent, never an error. Execute the batch, then send every result together, including the failures: a failed tool is a `tool_result` with `is_error: true`, never a dropped block. This is the shape `executeTool`'s `ok` field exists to feed.

- **`@anthropic-ai/sdk` and `@anthropic-ai/claude-agent-sdk` are different products.** The first is the Messages API client this repo uses. The second is Claude Code packaged as a library — it owns the agent loop and ships the built-in `Read`/`Write`/`Edit`/`Bash`. We want neither of those: the loop has to emit typed events and be cancellable, and file and command tools proxy to `SandboxManager`, while the image-gated computer uses the `SandboxDesktop` port. The plan originally specified the second one — see the amendment note in `docs/PLAN.md` §0 for why it did not survive contact with the testing strategy.

- **A tool call and its result travel together or not at all.** The API rejects a `tool_use` block with no answering `tool_result`, and vice versa — so anything shortening a conversation to fit a budget cannot simply delete the biggest block it finds. `NapContextEngine` reclaims tool output by replacing the *content* while keeping the block and its `toolCallId`, and drops history a whole turn at a time so both halves leave together. Deleting a result to save tokens does not produce a smaller request, it produces a 400. There is a test asserting no orphan in either direction, at five budgets.

- **Compaction replaces working context only after its event boundary is durable.** Keep cheap staleness pruning, complete tool exchanges, original user requests and the current job brief. Rebuild from the latest API compaction checkpoint plus events strictly after `coveredThrough`; native markers never hide API events. Summary calls spend the same turn's steps and budget, at billed weight. Automatic compaction fires on the context's size only — the ceiling or the model's window — never on what is left of the budget (ADR-0034). Oversized protected instructions stop the turn instead of being cut. Native capability is explicit, never inferred from a model name. See [ADR-0016](../adr/0016-compaction-preserves-the-event-log.md) and [integration/verification notes](../compaction.md).

- **Original request protection cannot depend on compaction succeeding.** A summary failure falls back to the assembled context, so requests evicted by its turn window or budget must already be preserved there. Retained exchanges keep their normal frames; covered or evicted requests keep text and named media references. Native restoration must strip encoded frame bytes before turning that context into `input_text`.

- **A turn's bill is the assembled context *times* its step count, and the context budget does not cap it.** Two different ceilings, and the one that fires is not the one people reach for: `NAP_CONTEXT_BUDGET_TOKENS` caps a single request, `TurnBudget`'s `DEFAULT_MAX_TOKENS` caps the sum over a turn's round trips — in billed tokens, so a cached re-send costs it a tenth of its size (ADR-0034) — and every round trip re-sends the whole transcript. A real four-turn session died on the second while sitting at a fifth of the first, which means **the truncation ladder can be perfectly correct and never run**. The consequence for anything that adds to the prompt: a kilobyte of context is a kilobyte charged ten to forty times, so "it fits" is not the test — and if you are about to raise a ceiling, measure which one first. `NapContextEngine`'s staleness pass is what came of that. **ADR-0011 has the numbers**, and `packages/context/scripts/measure-audit-session.ts` reproduces them against a committed log for free; don't copy them here, two copies of a measurement is one that goes stale.

- **The system prompt has no "verify your work" instruction, and that is the design.** `claude-opus-5` already checks its own work; telling it to do so again produces redundant tool calls and long reports *about* the checking rather than fewer mistakes, and removing such instructions costs no capability. The omission reads as an oversight, so `system-prompt.test.ts` fails on a phrase list plus any `/\bverif/i` match. If you are about to "improve" the prompt by adding a verification step, that is the thing this is here to stop.

- **The prompt's facts must match `packages/sandbox/template/` exactly.** The first draft claimed a `public/` directory the template does not have and said nothing about Tailwind v4 having no config file. Neither produces a confused agent — both produce a confident one, writing files nothing serves. Tests pin both.

- **The context token budget is a cost limit, not the model's context window.** `claude-opus-5` accepts 1M tokens; `DEFAULT_BUDGET_TOKENS` is 120k, and the gap is deliberate — a bigger window is not a reason to raise it. Token counts are a local estimate (~4 chars/token) because the exact number is a network call per string, which would make the budget untestable and every turn a round trip.

- **Anything that can spend real money defaults to the free path.** `ClaudeProvider` takes `model`, `effort` and `maxTokens`; `bun run harness` runs on `ScriptedLLMProvider` + `InMemorySandboxManager` unless given `--real`, and a real run defaults to Sonnet at `medium` with 12 steps and a 40k context budget. The fakes exercise the same composition the real components plug into, so the wiring is verifiable for free and spend is reserved for what only a real API can prove — the request shape, and that a real sandbox ends up with a real commit. Build the free half first, and ask before spending.

- **OpenRouter is the only route this project uses, and it reaches every vendor's models — not just Anthropic's.** It publishes a *native Anthropic Messages endpoint*, so `@anthropic-ai/sdk` reaches it with `baseURL: "https://openrouter.ai/api"` — note the root, not `/v1`, because the SDK appends `/v1/messages` and a doubled `/v1/v1/` 404s in a way that reads like the service is missing. **Their docs hedge that the endpoint is designed for Anthropic models; that is not a restriction, and it was measured rather than assumed.** A request to `openai/gpt-5.6-luna` comes back as a well-formed `tool_use` block with `stop_reason: "tool_use"`, accepts `cache_control` markers without complaint, and — the part that matters — reports `usage` in *Anthropic's* shape (`cache_read_input_tokens`), not OpenAI's `prompt_tokens_details.cached_tokens`. That is what keeps `toTokenUsage` honest, and it is exactly why nothing goes near the OpenAI-shaped `/chat/completions` endpoint, which returns the other shape and would make `TurnBudget` under-count silently. **Mind the separator** — OpenRouter namespaces with `anthropic/`; `toOpenRouterModel` therefore passes through any id already containing a `/` and prefixes anything else, so `openai/gpt-5.6-luna` survives and a bare `claude-sonnet-5` still becomes Anthropic's. Pricing is each vendor's own plus a top-up fee, so Claude through here is Anthropic's price and buys *access*, never savings; the savings come from choosing a cheaper model.

- **OpenRouter reserves the whole of `max_tokens` against your balance before the request runs, which Anthropic does not.** Anthropic bills tokens *generated*, so a high ceiling on a short answer is free; OpenRouter treats the ceiling as admission control and answers `402 "You requested up to 64000 tokens, but can only afford 418"` before the model sees anything. So `DEFAULT_MODEL_CONFIG.maxTokens` (64k) needs roughly $1.60 of credit on Opus 5 just to be *allowed* to ask a one-line question. Budget by the ceiling on this route, not by the expected answer. The failure costs nothing and is not retried — `isRetryable` only retries 5xx, rate limits and dropped connections, so a 402 stops at the first attempt.

- **OpenRouter does not implement `messages.countTokens` — it 404s** — and that turned out to be a better test rather than a worse one. Counting the prefix and comparing it to the documented minimum only supports an *inference* that caching will happen; a non-zero `cache_creation_input_tokens` on a real call **is** the claim. `prompt-caching.integration.test.ts` now sends the real `SYSTEM_PROMPT` + `TOOL_DEFINITIONS` and asserts on the counters, which works on every route. Related and sharper: **an assertion that a cache entry was *written* is clock-dependent.** An entry lives ~5 minutes, so re-running inside the TTL finds the prefix warm — `cache_creation_input_tokens` is 0, `cache_read_input_tokens` is thousands, and the test fails against code that is working perfectly. The fix is to salt the prefix with a `crypto.randomUUID()` line so every run starts cold; without it the test measures how recently you last ran it.- **Debug on `openai/gpt-5.6-luna`, demo on `anthropic/claude-opus-5`.** Most turns during development are spent debugging the loop — event ordering, tool sequencing, did the commit land — which needs a model that returns well-formed tool calls, not a good one. Luna is ~$0.10/$0.60 per MTok against Sonnet 5's $2/$10, so an afternoon of running the loop costs cents rather than dollars; that is the whole reason it is the `NAP_MODEL` and `HARNESS_DEFAULTS` default. **What crossing vendors actually costs is two things, and OpenRouter's translation absorbs both:** `toTokenUsage` sums `input_tokens` with both cache fields because Anthropic reports the uncached remainder, where OpenAI's `prompt_tokens` already includes cached tokens — same code, double count; and Anthropic answers N tool calls in **one** user message where OpenAI wants N `role: "tool"` messages, inverting the rule `agent-service.test.ts` pins. Going through the *Anthropic* endpoint means OpenRouter normalises both before we see them, which is measured, not assumed. **What it does not absorb:** the system prompt's deliberately missing verification instruction is tuned to Claude, so prompt-quality regressions on a cheap model are a property of the model and not a bug to chase. `packages/shared/src/ports/llm-provider.ts` is still the seam that would carry a genuinely different vendor SDK in v2.

- **Images go through the Anthropic-shaped endpoint to a non-Anthropic model, and two of its answer's quirks cost a paid call each to find.** Measured on `openai/gpt-5.6-luna` and `openai/gpt-5.6-terra`: an `image` content block with a base64 PNG source is forwarded intact, the model looks at it, and the reply is a well-formed `tool_use` — so `tool_choice` is a usable way to get structured output out of a vision call, and there is no need to parse prose. What the documentation does not say: (1) the model fills in **every** property the tool schema mentions, including `reason: ""` beside a grade it has just given, so a schema that treats a blank string as a value refuses a whole answer over a tidy model — read blank as absent on the way *in*, and keep the strict schema strict on the way out; (2) OpenRouter answers `cache_creation_input_tokens: null` for a model that does no prompt caching, so every usage counter must be `nullish()` rather than `optional()` or a paid judgement is thrown away over a token count nothing decides on. Both are in `apps/napbench/src/vision-judge.ts`, which is also the reason there is a plain `fetch` there: `@anthropic-ai/sdk` belongs to `@nap/agent`, and the judge must not share anything with the thing it grades.

- **Prompt caching is a prefix match, and the minimum prefix is per-model and *not monotonic*.** The API renders a request as `tools` → `system` → `messages`, so `ClaudeProvider` puts a `cache_control` marker on the system block (which covers the tool schemas rendered before it), on the last block of the last message (which covers the conversation so far), and on the up to two messages the context engine marks `cacheBreakpoint` as settled history — four, the API's ceiling. A prefix shorter than the model's minimum **silently does not cache** — no error, just a zero in `cache_creation_input_tokens`. The minimums do not follow model recency: **512** on `claude-opus-5`, **1024** on `claude-sonnet-5`, 2048 on Opus 4.7, 4096 on Opus 4.6 and Haiku 4.5. Sonnet 5 is the `NAP_MODEL` default *and* the stricter of the two we run, so 1024 is the number that binds; our tools+system prefix estimates at ~1188 by the local 4-chars/token rule, which is not a comfortable margin — `prompt-caching.integration.test.ts` measures it with `count_tokens` rather than trusting the estimate.

- **Use explicit per-block `cache_control`, never the top-level automatic form.** The SDK accepts a top-level `cache_control` that places the breakpoint for you, and it is simpler and wrong here: automatic caching exists only on the first-party API, and OpenRouter — the route this project uses — is a translating proxy where only the per-block markers were measured to be accepted. Per-block markers work on both routes. Related: a breakpoint walks back **at most 20 positions** to find a prior entry (a run of consecutive `tool_use` blocks counts as one, as does a run of `tool_result` blocks), which a tool loop can exceed in three steps if it stops moving the marker to the end — and which one whole turn routinely exceeds, which is why the next turn's read of the previous history needs a marker of its own rather than a lookback.

- **Nothing that varies between turns may sit before the conversation — and the tool declarations count.** The system prompt used to carry the file listing and the job brief, history was emptied one turn late, and a repair turn declared one tool fewer; each alone made every turn's first request re-write the whole context at the cache-write price, and every answer stayed correct, so nothing noticed. A per-turn fact goes at the end of the turn's own message; on a repair turn, `ask_user` is refused at execution rather than left undeclared, so a repair declares exactly a person's tools. App-test turns are the exception, deliberately: they declare a narrower, look-but-don't-touch set, so the cache misses around an app test, on its requests and on the person's turn after it. `packages/agent/src/cache-prefix.test.ts` fails on all three. See [ADR-0024](../adr/0024-the-cached-prefix-is-never-rewritten.md). **Shortening a turn's own conversation is a rewrite too:** turning one old screenshot into text changes bytes every in-turn cache entry covers, so that request re-writes the whole turn so far. They are cut in batches, never one per step — the same test fails if they are not, and ADR-0018's amendment to D5 has the numbers and why they stop where they do.

- **Both the reasoning and the answer are streamed, coalesced, and folded back together at every layer that reads them.** The model's `thinking` and `text` deltas arrive on the SDK's `MessageStream` (`stream.on("thinking" | "text", (delta, snapshot) => …)`; the wire events are `content_block_delta` with `delta.type` of `thinking_delta` or `text_delta`, and the helper hands over *the piece, then the running total*, so forwarding the second argument repeats every earlier word in every event). `ClaudeProvider` forwards them to `LLMRequest.onThinkingDelta` and `onTextDelta`; `AgentService` buffers each through a `DeltaStream` that flushes at 120 characters or 400ms, whichever comes first, and emits `agent.thinking` and `agent.message` events. That keeps a turn at a few dozen rows instead of thousands and leaves the durable-append-then-fanout path untouched, so a reload mid-turn replays what has been written so far. **The assembled `result.text` is emitted only when nothing was streamed** — both halves of that are load-bearing and each is a mutation: emitting it as well prints the whole answer twice, and dropping the fallback means a model or route that sends no text deltas says nothing at all. **The flush sits before the refusal and error branches**, since a turn that failed is where the reasoning is the only account of what happened. Two request-level facts are easy to undo by accident: `display: "summarized"` is required, because the default on `claude-opus-5` is `"omitted"` — which still streams thinking blocks but with empty text, so the symptom is silence rather than an error — and a retried attempt is a new stream that re-sends its reasoning from the start.

- **Whether reasoning comes back is a property of the *model*, not of the route — and the cheap model is the one that talks.** Measured twice on the same endpoint, same request, same `thinking: { type: "adaptive", display: "summarized" }`: `anthropic/claude-opus-5` produced **no** `agent.thinking` events across five model calls, while `openai/gpt-5.6-luna` produced five in one turn, carrying real summarized reasoning. An earlier version of this note concluded from the Opus run alone that OpenRouter's Anthropic endpoint drops thinking deltas; that was wrong, and it was wrong in the direction that would have sent someone to rewrite the transport. **Do not generalise a capability from one model to a route.** OpenRouter documents reasoning only for its *unified* OpenAI-shaped API — a `reasoning` parameter returning a `reasoning` field — which is still the endpoint this repo must not use, because its `usage` shape would make `TurnBudget` under-count silently. The Anthropic-shaped endpoint forwards what the upstream model emits, and that is model-specific.

- **A coalescing window belongs to the buffered text, not to the stream.** `DeltaStream` originally started its window at construction; a model takes seconds to produce its first token, so that window had always expired by the time the token landed and the delta was emitted alone. The first real turn printed `I` / `'ll look at the current app first.` and `There` / `'s now a button…`. The window now opens when text first enters the buffer and closes with it. Worth knowing what this did **not** fix: threshold chunking always leaves a remainder, so the piece after the last flush can be a single character — a real run ended a message with `.` on its own event. That is invisible in the pane, because the transcript folds a run of `agent.message` events into one paragraph, and it was invisible for the leading fragment too. **The fragments were never a rendering bug; they were an event-log one**, and the fix is about not writing a row per character.

- **A time threshold checked only when the next delta lands is not a time threshold.** `DeltaStream`'s 400ms used to be a comparison made inside `push`, so a preamble under 120 characters — "Let me build the board." — waited for the next text delta. A tool call's arguments are not text (the SDK streams them as `input_json_delta`, and the provider forwards only `thinking` and `text`), so the next push came only when the whole response had finished, and the sentence introducing a `write_file` sat unseen for as long as the file took to write. The window is now a timer armed when text enters an empty buffer, a `tool_use` block opening (`onToolCallStart`, read off the SDK's `streamEvent`) flushes at once, and each channel flushes the other before it speaks so a long reply cannot overtake the short thought before it. **A timer brings back the thing the old design could not do: write after the step is over.** Every step therefore ends both streams in a `finally` — `close` hands over the tail, `abandon` drops it on a cancelled turn — and an ended stream refuses later deltas, since a transport tearing down after a cancel still delivers what it had. The tests count armed timers on an injected `ManualScheduler` *before* moving time: a timer that has already run is no longer counted, so asserting after `advance` passed with the disarm deleted.

- **Prose in pieces has to be rejoined in two places, and neither is optional.** `NapContextEngine` appends to the open assistant *text block* rather than pushing a new one, so the conversation the model is re-sent looks the way it did when it wrote it — one answer, not a paragraph broken at whatever sizes the network delivered, and not a message that grows a content block per event. `buildTranscript` does the same for the pane. Both join text only to text from the same speaker: a tool call between two pieces of prose means the model said two things, and folding across it would attribute the second half to before the tool ran. **A short answer looks identical either way** — its deltas coalesce into one event — so any test meaning to prove streaming needs prose long enough to cross the flush threshold, or it passes against code that streams nothing.

- **Prose that has been shown cannot be retried; it can only be continued.** A retry is a new stream that writes the answer from its first word. Words already handed to `onTextDelta` are in the log as `agent.message`, and the next turn's conversation is rebuilt from that log, so a retry after the first word printed the opening twice, for the person and for the model. So `ClaudeProvider` retries an attempt only while it has shown no prose (reasoning may repeat, as the bullet above says), and otherwise returns the failure. Before re-asking, whether for its own one longer wait or for the fallback model, `AgentService` puts what the step showed into the conversation as the assistant's words and asks for the rest: the shape it uses for a reply cut off at the output limit. Nothing shown means the request goes again unchanged. The cost: a failure after the first word gets the agent's one longer wait rather than the provider's quick retries.

- **The SDK's `timeout` stops at the headers, so a stream that goes quiet after opening was waited on forever.** In `@anthropic-ai/sdk` 0.116.0, `fetchWithTimeout` clears its timer when `fetch` resolves, and for a stream that is the moment the headers arrive. So `ClaudeProvider` arms its own idle window (`STREAM_IDLE_TIMEOUT_MS`, 90s) on each attempt, from before the request is sent, and a stall becomes a retryable `StreamStalledError`. **The window counts bytes, not the events a listener sees**, which is the half that is easy to get wrong. The SDK's SSE decoder drops `ping` events before any listener runs, and OpenRouter's keep-alives are SSE comments it never parses. A model thinking with nothing to summarise, or writing a large tool call (the API buffers each argument until it is whole), sends only those for minutes. A window on `streamEvent` alone would call that a stall and cut off a large `write_file` on every retry. The bytes are read through per-request `middleware` that pipes the body through a `TransformStream`, not a custom `fetch`, because a client is shared by every turn and the window belongs to one attempt. The trade-off is deliberate: an upstream that hangs behind a proxy that keeps the socket warm is not caught, and only a ceiling on total time could catch it, which would also cut off a long, honest answer. A stall aborts through the same signal as a cancel, and the SDK reports both as `APIUserAbortError`, so the watch's own flag decides which it was. A cancel always wins and is never retried. **Worst case:** one call on a model that has stopped answering is `WORST_CASE_STALLED_CALL_MS` (3 × 90s + 1.5s of backoff, 271.5s). A step whose model and fallback both stay quiet ends after three such calls plus `DEFAULT_RETRY_DELAY_MS`: about 13.9 minutes, then `model_unavailable`. A retryable failure that survives every retry moves the turn to `NAP_FALLBACK_MODEL` under the refusal fallback's rules: once per turn whichever the reason, never on a person's own key, never on a non-retryable error. `stream-stall.test.ts` drives the real SDK over a fake `fetch` to prove the pings count.
