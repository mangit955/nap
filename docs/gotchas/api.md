# Gotchas: API, auth and logging

Learned the hard way; don't rediscover them. Read this before touching `apps/api` — routes, auth, limits, logging, `/health`; the turn queue and leases; the three entrypoints.

- **An abandoned desktop request can block its replacement.** Strict Mode and navigation can abort a stream fetch while its server-side desktop start keeps the action lock. Forward the request signal to startup and skip credential acquisition after cancellation. Otherwise a later start can hold the lock beyond the earlier credential command's five-second wait and fail the visible connection. The local app exposed this race; the route regression checks signal forwarding and the post-start cancellation boundary.

- **Bun HTTP idle timeout also bounds lazy desktop requests.** The installed Bun defaults to ten seconds, while a real desktop start plus credential command exceeded that. Both API launchers use the shared 120-second listener setting. The free `apps/api/scripts/http-idle-smoke.ts` uses an actual Bun listener and external curl: `--default` reproduces the disconnected response, and the normal command retains it. Desktop commands retain their own shorter execution bounds.

- **An unowned legacy repair can remain open in the log after its request ended.** Do not guess ownership from text, time, job or proximity, and do not reset all activity when an unrelated terminal arrives. The ownership-checked activity endpoint reads an event prefix before queue state; its idle result retires only that covered prefix for controls and the clock. A stale response must not settle a newer local request or suppress later events. Old browser sockets receive prompts without the optional repair metadata unless they opt in. See [ADR-0017](../adr/0017-repair-prompts-record-request-ownership.md).

- **A queued cancellation can have no transcript event.** Correlate a pending prompt with the admitted request ID and its ownership-scoped queue status. Another turn's failure, identical prompt text and a late cancel response cannot identify that request. See [compaction integration](../compaction.md) for receipt and rollout details.

- **Splitting the API from the worker without `NAP_EVENT_BUS=postgres` produces a deployment where everything works and nothing appears to.** The worker really claims the request, really runs the turn, really commits and really appends every event to the durable log — and publishes each one to an `InProcessEventBus` inside itself, where the only subscribers are none. Every socket watching that session is on an API pod. So the chat pane sits still, the preview never arrives, and the *logs on both processes are clean*: nothing failed. It is only visible as a reconnect with `?afterSeq=` suddenly delivering a completed turn all at once, because replay reads the log rather than the bus. `bootNap` therefore refuses to start a **worker** on the in-process bus — both halves read the same variable, so failing the one that publishes is what gets it fixed for the pair, while an API started alone on it is an ordinary thing to want and streams nothing only because nothing is running.

- **A semaphore that decrements before waking the next waiter is not a semaphore.** A permit released and then re-acquired by a waiter that resumes on a microtask leaves a window one microtask wide in which a *fresh* caller finds the count under the limit and takes the same permit. At a bound of one that is two Chromiums, which is the exact thing the bound exists to prevent, and it would appear only under load. `ThumbnailLane` avoids it by starting shots from one synchronous `#pump` that counts and starts in the same tick, never across an `await`.

- **Anything that reads a sandbox's git state beside a running turn must not take `index.lock`.** A plain `git status` refreshes the index and locks it to do so, and a turn's `git add` that meets the lock fails, which fails its commit and so the turn. `workspaceState` uses `git --no-optional-locks status` for this reason: measured against a real repository, 4 `git add`s in 300 failed beside a plain status and none beside this one. The thumbnail lane is the first reader outside the lease; anything else that joins it must use the same function.

- **Of the two housekeeping steps after a turn, only the snapshot has to finish before the lease goes back.** Verification and a repository publish stay under the lease as well; they are part of the turn's outcome, not housekeeping. The photograph is taken by the thumbnail lane afterwards, and moving the snapshot to join it looks like the same easy win. It is not: a restore reads the newest snapshot row, and the idle sweep only checks `anyLeased` before destroying a sandbox. Inside a job, a round's snapshot also has to settle before the *next round* starts. Running a repair beside the upload looks safe because the job waits for every upload before it returns, but that wait is a `finally`, and a worker killed outright runs none: a repair that had committed by then leaves the newest durable snapshot older than both rounds. Overlapping them needs a durable pending-snapshot record that the reaper reconciles. See ADR-0022 D4.

- **The per-session lease is a partial unique index, and three things about writing against it are not obvious.** `turn_requests` carries `unique (session_id) where state = 'leased'`, and that index — not any application check — is what stops two processes running a turn on one session and leaving the project holding two sandboxes. (1) **The claim is two statements inside one transaction, not the one the design writes.** A single `update … where id = (select … for update skip locked)` is correct, but when the index fires it has aborted the transaction without ever saying *which* candidate it was about to take, so "try the next one" has nothing to exclude; selecting the candidate first makes the id known before the update that may violate the index. The id has to be captured in a variable **outside** the transaction callback, because by the time the error is catchable there is nothing left inside it to ask. (2) **Cancelling has to name both in-flight states in one statement.** A cancel that matched only `queued` would, when a claim commits underneath it, re-read the row as `leased` and match nothing — the turn would run on happily having been cancelled. One `update … where state in ('queued','leased')` with a `case` that fails the queued ones is what makes the race harmless in either order. A cancelled *queued* request is failed outright rather than left queued and permanently skipped: a row with no terminal state is a chat pane spinning on an event that will never come. (3) **Renewal is how a worker asks whether it is still allowed to run, and zero rows back is fatal.** It is conditional on the request id, the owner *and* the state; a worker that outlived its lease through a GC pause must abort at once rather than keep appending to a session somebody else now owns. A renewal that could not be *asked* — the database blinked — is not a lease that was lost, and aborting on the first of those would make a blip cost every turn in flight. The windows in `@nap/shared/lease-windows` are why that gap is safe: the worker aborts by expiry + one renewal interval, and the janitor only reclaims at expiry + the grace.

- **Orphaning a request and announcing it cannot be one transaction, so the order is load-bearing.** One half is a row in `turn_requests` and the other is an append plus a fanout, and nothing spans them. The janitor takes the row **first** — that is what makes it exclusive, so only one janitor reclaims a leased row, although multiple readers can announce the same orphan — and marks it announced **only once its events are durable**. `finished_at` is the marker: an `orphaned` row with a null one is a request whose terminal events are still owed, which is what the next tick reads and finishes. Doing it the other way round leaves, on a crash in between, a request that is terminal in the queue and a chat pane still spinning on an event nobody will ever write, which is the exact failure the janitor exists to prevent. The cost of this order is that a crash between the append and the mark can duplicate a `turn.failed`; a second terminal event is untidy, and no terminal event at all is unbounded.

- **An expired lease still holds its session — expiry frees nothing.** The partial unique index is over `state = 'leased'` and knows nothing about the clock, so only the janitor moves a row out of it, and only past the grace. `InMemoryTurnQueue` used to disagree, treating an expired lease as free, and a test asserted that: a fake that hands the session over on expiry is a fake in which the whole fencing argument is invisible, because the zombie and its successor never overlap in it.

- **Opening a project is the second long-running entry point, and it is easy to miss because the route answers immediately.** `POST /projects/:id/open` used to call `resumeSession` and let the promise run detached, which meant the continuation of whatever Job the log left open executed **without a lease**, in whichever pod took the request, possibly beside a worker turn on the same session — the two-sandbox failure the lease exists to prevent, reachable through a door nobody was looking at. It is a queued `resume` request now and takes the same lease a turn does. Two things follow that a reader would not guess. **A queued row carries a concrete model**, so the model settings are *required* on the project routes rather than optional as the ceilings are: the row is written before anything downstream could apply a default, and a row with no model would run whatever the provider defaults to, which is paid. And **an open can therefore be refused for a model nobody asked for** — `resolveTurnAccess` says no to an Anthropic key when the Opus line has no usable version, which used to fall through to the runtime's own default and now has to reach the caller. An orphaned `resume` gets only a notice if it started no repair. Once it does, the repair prompt records its owning request, and the janitor closes that repair under its own turn ID. The open operation itself still has no turn to fail. See ADR-0017 for the legacy ownership boundary. `SessionQueue` in the runtime is no longer the only thing keeping a turn and an open apart, but it is kept: it is the in-process half of the same rope, and the lease is enforced in a database it cannot see. What the route still cannot see is a resume *already queued* — the `already_running` guard reads `project.sandboxId`, which stays null until a worker picks the request up, so opens repeated inside that window queue a row each. They fold to `none` when they run, which is why this is a cost rather than a bug.

- **One store and one bus per process, or the app compiles, boots, and streams nothing.** `composeNap` takes *one* `EventStore` and *one* `EventBus` and hands the same two to the runtime and to `/ws`. Constructing a second pair for the second consumer type-checks perfectly and produces a server where the runtime announces to a bus with no listeners while every open tab waits on an empty one — no error anywhere, just a turn that runs invisibly. Taking them as arguments is most of the defence: a composition that cannot build a store cannot build a spare one by accident.

- **The notify bus never carries the event, and five smaller things follow from that.** `PostgresNotifyEventBus` (`NAP_EVENT_BUS=postgres`) sends `{sessionId, seq}` through `pg_notify` and every process reads the rows out of the durable log — **a notification is a wake-up signal, the log is the delivery**. Carrying the payload would work in every test anyone would think to write and then fail on exactly the largest events, because Postgres caps a `NOTIFY` payload at **8000 bytes** and Nap's events hold command output and file contents. (1) **`LISTEN` cannot go through a transaction pooler**, and the failure has no error in it: the `LISTEN` lands on a backend that is handed back to the pool, so the process hears nothing while every query it runs keeps working. Hence a connection of its own, and `NAP_LISTEN_DATABASE_URL` for a deployment behind Neon's pooled endpoint. (2) **postgres.js reconnects and re-issues the `LISTEN` silently**, which means nothing tells the process the channel ever died — so the bus shouts on a second channel each tick and watches for its own echo, and `/readyz` reads that. A socket being open is not proof the backend is still delivering. `PostgresNotifyTransport` warns, naming the channel, each time postgres.js re-issues a `LISTEN` (its `onlisten` callback fires on the first answer and after every reconnect), because whatever was sent while the socket was down is gone and only the slower fallback recovers it. That line is a record and not a health check: a reconnect that never succeeds logs nothing, and the echo is still what notices. (3) **A subscription's cursor starts at the head of the log, not at zero**, or the first event would drag the whole history along behind it — and the head is a query, so an event appended while it is in flight would be skipped. A notification arriving before the answer therefore *wins* and sets the cursor to just below its own `seq`; nothing moves a cursor backwards after that, which is what stops an out-of-order wake-up re-delivering. (4) **The catch-up poll is one query for every session the process is streaming**, via `EventTailReader.readTails`, not a `readFrom` per session: a hundred sessions on a 2s tick is fifty queries a second of pure overhead otherwise (design §24, item 2). (5) **Notification-driven reads are coalesced**: while one is queued or running, every session a notification names joins the single read queued behind it, so a burst of a hundred events is two reads rather than a hundred. The cursors are untouched by it — it changes how many reads there are, never where one starts — and a test counting reads has to hold the reader mid-query to put a notification *during* a read, or the count depends on microtask timing. One thing that did *not* need changing, pleasantly: `openEventStream`'s note that "the bus delivers synchronously" was load-bearing only for the buffer flush, and an asynchronous delivery either lands in the buffer or passes the `lastSentSeq` gate.

- **Three processes come out of one composition, and which loops start is the only difference.** `role` is `api`, `worker`, `reaper` or `all`, and it gates loops rather than objects: a worker builds the Hono app it never serves and an API builds the runtime it never drives, because a composition function per role is three sets of assumptions about which dependencies each may skip. Two consequences are easy to get wrong. **The reaper must be exactly one process**, since two sweeps would snapshot and destroy the same project at once — `replicas: 1` covers the steady state and a `pg_try_advisory_lock` on a connection of its own covers the rolling update that briefly runs two; a composition given no `sweepLock` sweeps unguarded, which is right for one container and for tests. And **its timers are the only thing referencing its event loop**, unlike the other two, so `startSweeping` is asked to `holdProcessOpen` there — unreferenced, as it is everywhere else, the process would exit before its first sweep. The **janitor rides in the same process on a tighter ticker and is deliberately not under the lock** (design §24, item 3): it is one query with no sandbox behind it, its clock is tighter than the idle sweep's, and two of them are safe because the reclaim holds each row with `for update skip locked` — the moment two exist is a rolling update, which is exactly when turns are being orphaned in bulk.

- **"Is this session busy?" is a lease read, and it has to be, because nothing that asks it runs turns.** Closing a project, deleting one and the idle sweep all call `TurnQueue.anyLeased`, which is `state = 'leased'` over the project's sessions — the same rows the partial unique index is over, and deliberately nothing about the clock, so an expired lease still reads busy until the janitor closes it out. It replaced a per-process `TurnRegistry` lookup that was correct only while the routes and the turns shared a process: an API pod composed apart from its workers read every busy session as idle and would have let somebody close a project mid-turn. The registry survives only as a *fast path* for compositions running every role in one process, meaning scripts and tests; in a deployed process it finds nothing, and nothing but the cancel route reads it.

- **A cancel wake-up names a request and only ever causes a renewal.** Naming the session would let a late notification stop the turn that came after the one somebody cancelled, and aborting on the notification alone would let any process on the database stop a turn with an unflagged id. The worker looks the id up in the turns it is running, renews if it finds one, and lets the row decide. Send it only after `requestCancel` has returned, which is why that is what hands back the id; a wake-up that beats the commit reads an unflagged row, and the turn then waits for its next renewal. `NapDeps.cancels` is required and nullable because forgetting it compiles to a healthy deployment with a fifteen-second stop button. See `docs/adr/0023`.

- **An idle worker claims on a wake-up, so every writer of a turn request has to announce one, after its commit.** The worker polls only every `NAP_WORKER_FALLBACK_POLL_SECONDS` (5 s) while it can hear, so a writer that forgets to announce breaks nothing a test of that writer would notice: its requests are still claimed, seconds late. There are more writers than `queue.enqueue`. `PostgresSessionStartStore.start` (every new project's first turn) and `PostgresGitHubStore`'s import and feedback approval insert into `turn_requests` inside transactions of their own. Settle and the janitor's reclaim announce too, because each frees a session. Clearing or abandoning owner computer control announces after commit as well. Broadcasts are coalesced to one claim round per 100 ms; own turn completions refill immediately. Each writer takes `{ claims }` as a required, nullable constructor option. A new file inserting into `turn_requests` fails `test/claim-writers.test.ts` until it calls `.announce()`, and `packages/db/src/claim-announcements.db.test.ts` is where its announcement is shown to come after the commit. An announcement sent inside the transaction is worse than none: the woken worker reads an empty queue and goes back to sleep for the whole fallback. Never give a channel to any writer built on a transaction: a nested savepoint is not the outer commit. A worker that cannot hear (its `LISTEN` failed, has not answered, or the event bus's echo says the socket is deaf) polls at the old 100 ms, so a dead listener costs load, never a stuck turn. See `docs/adr/0027`.
- **Every writer of something a session card draws announces its owner, after its commit.** Tabs read `GET /sessions` when `/ws/account` says the list changed, and otherwise only every five minutes (ten seconds while the socket is down), so a writer that forgets to announce breaks nothing a test of it would notice: the change just shows up minutes late. Each writer in `@nap/db` takes `{ sessionList }` as an optional constructor option and calls `sessionList.announce` with whatever it knows (a user, a project or a session; `PostgresSessionListChannel` looks up the owner). Announce only what a card draws: `updateJob` compares the pull request fields it is given against the row first, because the GitHub refresh sweep rewrites unchanged jobs and a notice for each would be a poll by another name. `test/session-list-writers.test.ts` fails on a shipped file that writes one of the list's tables without announcing (or a reason in its exemption list), and on a writer `boot.ts` builds without the announcer. `packages/db/src/session-list-announcements.db.test.ts` is where each one is shown to announce after the commit. The API's hub (`ws/session-list-hub.ts`) listens on the first `/ws/account` subscriber, never at boot, so workers and the reaper only announce. It is handed the event bus's echo as `hearing`, like claims: while that says the listener is deaf, the hub refuses new account sockets and each open one closes at its next heartbeat, so tabs fall back to the ten-second read rather than trust a socket that hears nothing.

- **The composition is a function; `index.ts` only reads the environment and calls it.** `apps/api/src/compose.ts` assembles the runtime, the agent, the limiters, the routes and the reaper from ports it is handed, so a test — and a load harness, and a worker entrypoint — can build *the same* system with fakes rather than a similar one. What stays in `index.ts` is what a process does: validate the environment, construct the real clients, log what it is about to spend money on, and handle signals. Two things deliberately did not move: `/health`, because `E2BSandboxManager.ping()` is not on the `SandboxManager` port, and the provider, because which vendor pays is an environment fact. `compose.test.ts` is the first test that composes boot — it was worth writing for the assertion that the reaper actually sweeps, which nothing else covered end to end.

- **A claimed turn runs detached from the claim loop, so `TurnWorker.run` must not be able to reject or an unhandled rejection kills the Bun process.** `POST /sessions/:id/turns` only writes a row and answers 202; the worker starts `run` without awaiting it, and one throwing turn would otherwise take the process down with every turn on it. So `run` catches and settles the request `failed`. Its `finally` matters as much — it releases the `TurnRegistry` entry, and without that the entry for every finished request stays in memory, holding its controller, for as long as the process lives. Entries are keyed by request, so a late cancel can no longer reach the *next* turn on a session. Both are tested in `packages/runtime/src/turn-worker.test.ts`.

- **`hono/bun`'s `upgradeWebSocket` needs a live `Bun.serve`** — it reads the server off `c.env` and throws without one, so no route that upgrades can be exercised under Vitest. `createApp` takes the adapter as a dependency and all the connection logic lives in `apps/api/src/ws/event-stream.ts` behind a two-method socket type; what is left is covered by `bun run ws:smoke`, which is free. Note the successful upgrade returns a **200**, not a 101 — the runtime has already answered the handshake by then, and `new Response(null, { status: 101 })` is not even constructible under Node.

- **Better Auth is mapped onto this repo's tables, and two settings hold that together.** `betterAuth` takes a `modelName` per model (`user` → `users`, **`session` → `authSessions`**, `account` → `accounts`, `verification` → `verifications`), and `drizzleAdapter` resolves a model by looking that name up as a key in the schema object it is given. `usePlural: true` would look like the tidy answer and is the trap: it maps `session` to `sessions`, which in this repo is a *conversation*, and login rows would go into the chat table. The second half is passing an explicit four-key `schema` rather than the whole one — together they turn a wrong mapping into a loud "model not found" instead of a quiet write into the wrong table, and removing either one alone is the bad case. Ids need `advanced.database.generateId: "uuid"`, or the library inserts its own random strings into uuid columns. Field names in a mapping are *drizzle property* names, not SQL column names.

- **The deployment's own key buys nothing unless `NAP_FREE_MODEL` is set, and then nothing but that one model — and one pure function is what enforces it.** Unset is the default and means no free tier at all: a keyless caller is refused with `byok_required`, because each turn still costs a sandbox; every route that queues sandbox work resolves access through `resolveTurnAccess` (`apps/api/src/turns/model-access.ts`) before it writes anything, and the worker refuses an unbilled row as a backstop for what was queued before the switch. It decides which model a caller runs, at what effort, *and* whose account pays, together, because they are the same fact — somebody with no key gets the free model at `NAP_EFFORT` on this deployment's account, an OpenRouter key any of the nine model lines billed to them (Sol by default), an Anthropic key the four Claude lines (Opus by default). It returns a **concrete version**, never a line, and that version is what the queued row carries: a worker never consults the catalog, and a caller that has to remember to apply a default afterwards is one that will eventually forget. A line is resolved against the catalog the API process refreshes hourly (`apps/api/src/models/model-catalog.ts`); a line with no usable version answers `model_unavailable` (409, a refusal before anything is written, so the dashboard's composer gives the draft back), and a turn naming nothing falls to the first line the key reaches that has a version, which is also what `/models` names as the default. The request's `model` may also be an exact version a saved draft held, read as its line, so a browser deployed before the API keeps working. `NAP_FREE_MODEL` is one exact id, never a line, and may be a paid model, which bills every keyless turn to the deployment on purpose, bounded by the free tier's rate limit and the sandbox ceilings — so changing it is a spending decision, visible otherwise only on an invoice. The models the deployment names itself (`NAP_FALLBACK_MODEL`, `NAP_SUBAGENT_MODEL`) also run on its key, but only inside turns it already pays for. The free tier gets its **own `TurnRateLimiter` instance**, not a second number on one: the window is per-limiter as well as per-user, so sharing would let somebody's paid turns eat their free allowance. `/models` marks unavailable lines rather than hiding them, from the same rules, and a test asserts the two agree for every kind of caller — two lists that drift produce a menu offering lines every turn is then refused for naming.

- **A credential is the second thing that varies per turn, and it travels the model's path exactly.** `startTurn({ model, credentials })` → `ClaudeProvider` builds a client per credential, cached by `platform + apiKey` because a client owns a connection pool and one per turn is a fresh TLS handshake per message. **`createClient` is injectable and that is not gratuitous**: the only way to observe which client a turn picked is to make a request with it, so the first version of that test sent live calls to a vendor from the unit suite. **An Anthropic key needs the namespace taken back off** — this codebase spells every model the OpenRouter way, and `anthropic/claude-opus-5` is a 404 at Anthropic's own API, three layers from the key that caused it (`toDirectAnthropicModel`). A credential must never reach an event payload or a log line: the `events` table is the audit log by design and has the retention of a chat transcript.

- **Somebody else's API key is sealed with AES-256-**GCM**, and the authentication is the point.** `apps/api/src/account/secret-box.ts` — a wrong encryption secret or an altered ciphertext *fails* rather than returning plausible garbage that would then be sent to a vendor as a key. Fresh 12-byte IV per seal, never reused, which is why `seal` takes no IV argument. The store handles **ciphertext only** (`UserKeyStore`), so encryption stays in the layer that has the secret and the database, its backups and its query log hold nothing anybody can spend. **Nothing ever answers with a key** — `GET /account/api-key` returns `{configured, platform, hint}` and its test uses `toEqual`, not `toMatchObject`: the realistic regression is not somebody adding the plaintext back (the route has never had it) but passing the whole stored row through and shipping the ciphertext, and a `not.toContain` on the plaintext stays green through exactly that. Keys are verified against the vendor before storing, but **a network failure is not a bad key**: that check catches typos and must not become a gate.

- **better-auth's `anonymous` plugin needs a column, and it is easy to ship without one.** `users.is_anonymous` is declared by the plugin rather than wanted by anything here; without the migration the flag is silently absent and a demo visitor is indistinguishable from a paying account — which is the free tier not applying to the people it exists for. The library types a session user as `Record<string, any> & {…}`, so `session.user.isAnonymous` is `any`; it is parsed with a two-line Zod schema rather than cast, and a failed parse reads as `false`, because the safe answer to "is this a throwaway?" grants less rather than more. One user row per visitor, so demo projects are isolated — a single shared demo account would show every visitor everyone else's work.

- **`unique(provider_id, account_id)` on `accounts` is a backstop, not the mechanism** — and the difference was only found by deleting it. A repeat GitHub login finds the same person because the library looks the row up before inserting, so dropping the constraint leaves every sign-in test green. It catches the race the lookup cannot: two callbacks for one account arriving together, both finding nothing, both inserting. Since no ordinary path reaches it, `packages/db/src/accounts.db.test.ts` asserts it directly, on SQLSTATE `23505`. Same reasoning as `unique(session_id, seq)` in the event store.

- **The auth client throws when there is no server, and answers when there is one — those are different code paths and only one of them was handled.** `authClient.signIn.email` returns `{ error }` for a *refused* sign-in and **rejects** for a sign-in it could not send at all: API down, connection dropped, browser offline. Uncaught, that rejection went nowhere — `submitting` was never cleared, the button sat on "One moment…" for as long as the page stayed open, and nothing on screen said why. Found by pressing the button with the API not running, which is the normal state of a local checkout, and not by any test. The message for it is deliberately not the one for a bad password: telling somebody their credentials failed when the network is down sends them off to reset a password that was fine. `live-sign-in.test.tsx` mocks the client and pins both branches.

- **CORS credentials and a wildcard origin are mutually exclusive, so the web origin is configured rather than reflected.** A browser will not attach a cookie to a cross-origin request unless the response names the origin exactly *and* sets `Access-Control-Allow-Credentials` — `*` with credentials is refused outright. `apps/api` had no CORS middleware at all until sign-in needed one, which meant the browser could not reach the API from `:3000`; every hand-written call now goes through `apps/web/src/api/credentialed-fetch.ts` so `credentials: "include"` lives in one place instead of four.

- **Authorization is deny-by-default, and the route table is what enforces it.** A `requireUser()` call at the top of each handler protects the routes somebody remembered; the failure worth designing against is the route added later by someone who did not know to add it. So one `app.use("*", requireUser(...))` sits ahead of every route in `apps/api/src/app.ts`, and the only public paths are the ones named in `require-user.ts` — `/health`, `/livez`, `/readyz` (each polled by something that has no session and never will), `/api/auth/*` (you cannot require a session to reach the thing that issues sessions) and `/auth/providers`. **`authenticate` being absent means refuse, not allow**, so an app wired up without it reaches nobody's data. `route-coverage.test.ts` reads Hono's own `app.routes` and fails naming any route missing from `route-table.ts`, in both directions — an unclassified route *and* a table entry for a route that no longer exists, since the second is an authorization test passing against nothing. **Another user's resource is 404, never 403**: a 403 confirms the row exists, which is a fact about someone else's data. Ownership is enforced in the *query* — `ProjectStore` takes a userId and `SessionRecord` carries one down from the join `PostgresSessionStore` already performs — because a filter a handler has to remember is one that will eventually be forgotten, silently. **The fakes enforce it too**: `InMemoryProjectStore` filters on the id rather than accepting and ignoring it, or every authorization test above it would pass against a store that leaks.

- **Both spending limits live at the turn route, and they answer differently on purpose.** `POST /sessions/:id/turns` is the only way to start a turn, so it is the only place either ceiling has to be applied. A rate limit is a *speed* problem — **429 with a `Retry-After` header**, not just a body, because that header is what a proxy or client library obeys on its own. A sandbox quota is a *state* conflict — **409**, since the fix is closing a project rather than waiting, and a `Retry-After` would be a lie. Both carry a `code` so the browser tells them apart without parsing prose. Three things are load-bearing and each was a mutation: **a refused attempt does not consume the allowance** (otherwise a retrying client pushes its own recovery away forever, and the advertised wait never arrives); **the limiter window slides**, so `Retry-After` can be computed exactly rather than guessed at a fixed boundary; and **a turn whose project already has a sandbox skips the quota entirely**, or the cap silently means "projects you may talk to" and a user at their limit finds the conversation they are in has stopped accepting messages. `NAP_MAX_SANDBOXES_TOTAL` is a cluster-wide ceiling beyond what the milestone asked for: per-user limits alone multiply by the number of users, which is the arithmetic that matters the first time strangers use it.

- **The rate half of it is a table, and every property it had survived the move.** `TurnRateLimiter` is a port now (`@nap/shared/ports/turn-rate-limit`); the deployment's implementation is `PostgresTurnRateLimiter`, one row per **accepted** turn in `turn_rate_events(user_id, tier, at)`. A `Map` in the process was a correct sliding window in the wrong place — two replicas meant two allowances, so the free-tier ceiling that makes an open demo door affordable multiplied by the replica count. Four things are load-bearing. **The database's clock, everywhere**: `check` takes no `now`, because the only clock every replica agrees on is Postgres's, and `retryAfterSeconds` is therefore computed in SQL rather than from a `Date` the driver handed back. **The count and the insert are one transaction under `pg_advisory_xact_lock`**, keyed per user and tier rather than globally like the capacity lock, since the count being protected is over one person's rows — without it a burst of 30 admissions against a limit of 5 lets 18 through, which is what the db suite asserts. **`tier` is what keeps two allowances two**, so somebody's paid turns cannot eat their free ones. **The quota is checked before the rate limit**, which it was not before: the rate check *records*, so asking it first spent an hour of somebody's allowance on a turn a `409` then refused — a person at their sandbox cap could burn their whole hour without starting anything, and durably. The visible consequence is that somebody at both limits now gets the `409`, which is the answer they can act on. And **`sweep` is the reaper's**, called from the composition beside the capacity reconciliation, with its own `catch` — a failure to tidy must not cost that tick the projects it was about to put away, which is the half that spends money.

- **The sandbox half of that route is now advisory.** Counting sandboxes and then creating one is a time-of-check-to-time-of-use race, and under a burst of admissions every caller reads the same number and every one of them decides it is under the cap — so the authoritative ceiling moved to `SandboxCapacity`, reserved in a Postgres transaction under `pg_advisory_xact_lock` at the moment a sandbox is created. Read the rule as **rate and model access at the route; sandbox capacity at the point of creation**. The route's check stays because a `409` in milliseconds beats one after a queue and a cold start, and because its message is the one a person can act on — but nothing there bounds the bill.

- **A reservation has two ends, and forgetting the second one is a cap on projects-ever.** `acquireSandbox` reserves before it creates, activates once the sandbox is recorded against the session, and releases the instant creation fails; `putProjectAway` releases whatever the project holds when its sandbox is destroyed, on both the put-away and the already-gone paths — and *not* on the path that leaves it serving, because that sandbox is still being billed. Without the teardown half, a ceiling of ten stops admitting anybody after the tenth project the cluster ever opened. Rows rather than a counter for a reason a sweep needs: a counter cannot tell a leaked increment from a creation still in flight, so nothing could ever safely decrement it. A `reserved` row whose process died holds its slot until `expires_at` passes and the same project asks again — the row is then handed back rather than duplicated, which is also what lets a project whose sandbox the provider reclaimed still restore. The reaper's `PostgresCapacityReconciler` pass sweeps what no ordinary path gave back, so a slot nobody asks for again comes back in minutes rather than never. **And `activate` reports its rowcount, because a create whose renewals stopped landing for the two-minute TTL comes back to find its row already reclaimed** — renewal runs from reservation to activation, so a merely slow create or repository setup keeps its row, and only a process that cannot reach the store loses it; an update matching nothing used to resolve as if it had worked, leaving a running, billed sandbox that no row counted. The asymmetry in how `acquireSandbox` reads its answer is the part worth keeping: an `activate` that *throws* is a store that could not be reached and nothing is known, so the turn goes ahead on a ceiling that is briefly inaccurate — while a returned `reservation_reclaimed` is a definite answer, and only that one costs the sandbox and the turn.

- **The command guard matches the *head of a shell segment*, never a substring.** `inspectCommand` splits on `;`/`&&`/`||`/`|`, pulls `$(…)` and backticks out as commands of their own, follows `sh -c`, and strips `sudo`/`env`/`VAR=x` — then matches only the resulting command name. Searching the raw string for "curl" instead is shorter, blocks `echo "run curl to fetch it"`, and there is an allow-list row that fails when someone tries it. Both tables are the test: `packages/agent/src/safety/commands.test.ts` pins ~28 blocked forms *and the rule each is blocked by*, plus 16 ordinary ones that must run. The guard is not the isolation boundary — the E2B VM is — it exists so a prompt-injected model does not get the whole VM.

- **Admission reads the project's name off the session lookup, and a record that grows can break whoever spreads it.** `SessionRecord` carries `projectName` from the join `PostgresSessionStore.get` already does, so naming a project after its first prompt costs no query on any later turn. Adding that field turned every computer-control grant into a `409 stale_grant`: the grant was signed from `{ ...owned.value, … }` and verified against a strict schema, so the extra key made every token unverifiable, and it would have carried the project's name inside the token as well. The grant now names its fields one by one. Anything signed, persisted or sent to a strict schema should list its fields rather than spread a record that other readers are free to widen. Two smaller points: the caller's key lookup starts beside the session lookup but is read only after the session is authorized, through `startedAlongside`, which also catches its rejection so a 404 that never reads it cannot leave an unhandled one; and the limiter's lock stays a statement of its own, because a statement's snapshot is taken before the locks it asks for are granted.

- **Hono resolves no route parameters inside a wildcard middleware, and says nothing about it.** In `app.use("*", …)` the matched route *is* `*`, so `c.req.param("sessionId")` is `undefined` even on a request to `/sessions/:sessionId/turns` — the field is simply absent, which is indistinguishable from a request that had no session. Every turn and cancel had been logged without a session id from M0-6 until this was found. Ids for the log context come from `apps/api/src/log-ids.ts`, which reads the raw path; enriching from inside each handler is the alternative and it is worse twice over — a line in every route that someone will forget, and too late for the 401s and 404s that never reach a handler.

- **The log-context seam is in `@nap/shared/logging`, and the logging library is not.** Every layer has to report under the same ids and the dependency direction allows exactly one shared home, so the `AsyncLocalStorage`, the `LogContext` and a deliberately narrow `Logger` interface live in the base package — while pino, the stream and the level stay in `apps/api/src/logger.ts`, which calls `setRootLogger` once at boot. A real pino logger satisfies that interface structurally, with **no adapter and no cast**: `createLogger`'s return annotation is what proves it, and it is the one place the two shapes meet. The default root discards, so importing the module never writes anywhere. Two ways to add context and they are not interchangeable — `withLogContext` opens a scope (the request, the turn), `addLogContext` enriches the scope already open. Authentication needs the second: the caller's id is learned after the context was opened and before the request's own summary line is written, so nesting would leave the one line carrying the status code as the only line that could not say whose it was.

- **`/health` answers 200 even when it is degraded.** A non-2xx is how an orchestrator decides to restart or de-register a process, and neither fixes an unreachable database — it removes the instance that was still able to report it, and during a shared-dependency outage takes every instance out at once. The verdict is in the body, named per dependency. The endpoint is also public, necessarily, so `createHealthProbe` caches for 5s and collapses concurrent polls: without that, anyone who can reach it can drive unlimited load against E2B's API at our expense. Every probe has a deadline, because the characteristic database failure is an accepted connection that never answers. `E2BSandboxManager.ping()` is deliberately **not** on the `SandboxManager` port — that port is about one project's workspace and every method takes a sandbox id, while "is the provider up?" is a question about the deployment that the in-memory fake could only answer meaninglessly.

- **Liveness, readiness and health are three questions, and one endpoint can only answer one of them.** `/health`'s 200-when-degraded is right for a human and fatal for a probe, so `/livez` and `/readyz` exist beside it rather than instead of it. `/livez` **touches nothing** — whatever a liveness probe consults becomes a reason to kill the container, so including the database there means a Neon blip restarts every replica, the healthy ones included. `/readyz` is the only one that answers with a *status code*, because that is all a load balancer reads, and it checks **the database and not the sandbox provider**: an unreachable database means this pod cannot serve while another can, whereas every replica shares E2B, so de-registering on it empties the rotation instead of shifting work. Its probe is a second `createHealthProbe` rather than a reading of `/health`'s, so a slow sandbox `ping()` cannot delay the answer to "may this pod have traffic" — and it is cached for **1s where `/health` caches for 5s**, because that 5s is there to stop a public endpoint billing an E2B call per poll and readiness only runs a local `select 1`, where staleness costs a probe interval in each direction. Absent probes mean *ready*, matching the rest of `AppDeps`: an app assembled with no database has nothing to be unready for. Readiness **fails** when the Postgres LISTEN connection is down, and it is a second check in the same probe rather than a change to the route. Failing rather than warning was the open question (design §24, item 5) and the answer is that a pod with a dead listener still serves every event — the catch-up poll sees to that — but two seconds late, and another pod does not. The check only exists under `NAP_EVENT_BUS=postgres`; with the in-process bus there is nothing to be down.

- **A health check's deadline is sized by the slowest *healthy* case, not the impatient one.** `/health`'s probe timeout was 2s and reported `degraded` on the first poll after every cold boot, because a Neon instance that has scaled to zero takes **~1.8s** to answer its first query — measured, not guessed. A false outage is worse than a missed one: it is the reading that teaches people to stop trusting the endpoint, and anything automated watching it acts on a lie. The default is 5s. The same shape of mistake is waiting in any probe pointed at serverless infrastructure that idles down.

- **`bun run acceptance` is the v1 acceptance run, and it spends real money.** `apps/api/scripts/acceptance.ts` drives `docs/PLAN.md` §6 over the real HTTP and WebSocket surface — needs `bun run dev` alongside it, takes `--keep` to leave the preview up for a demo. Deliberately absent from the permission allow-list and matched by no vitest glob, for the same reason `test:integration` is: the prompt is the only checkpoint before the spend. **Two of §6's steps are not machine-checkable and it does not pretend otherwise** — whether the preview *looks* right, and whether an edit arrived by HMR rather than a reload — so they print as `LOOK` lines while their checkable halves are asserted. Two traps it walked into, both worth not repeating: a per-turn socket opened at `seq=0` replays the whole session, so searching *all* of a stream's events for `turn.completed` finds the **previous** turn's and reports the new one finished before it started; and grepping written source for "dark"/"purple" reported a false negative against a correct app, because Tailwind v4 `@theme` tokens express it as `oklch(0.14 0.02 300)`. A third, and the only one a person rather than a test caught: **closing a project destroys the sandbox its preview URL points at**, so a URL captured before step 5 is dead by the end of the run — a restored project comes back on a *new* host and re-announces `preview.ready`, which is the announcement to print. Anything handing a preview URL to a human should poll it for a 200 first; the cost of being wrong is someone opening "Sandbox Not Found" and concluding the product is broken.

- **Bun's HTTP idle timeout can drop a connection while its handler is still working.** `Bun.serve`'s configured default is 10 seconds, but the wall-clock cutoff is approximate. Bun 1.3.13 probes on Darwin and Linux ARM64 with a 25-second handler closed the default connection after about 12 seconds; `idleTimeout: 30` returned HTTP 200 after 25 seconds. Reproduce with a 25-second handler and external `curl`; a 12-second handler returned 200 in an earlier probe. A handler can still finish and log 200 after the connection drops, while `apps/web/src/github/request.ts` reports "Could not reach the server". The reported GitHub incident logged `status:200 durationMs:21726`, consistent with this failure. Bun can print `` [Bun.serve]: request timed out after 10 seconds. Pass `idleTimeout` to configure. `` in development/debug mode with the default timeout and non-silent operation; do not expect that warning in production. `apps/api/src/index.ts` uses the shared 120-second timeout from `http-options.ts`, which also accommodates lazy desktop startup, so slow upstream calls have time to return a response instead of a misleading network error. This is finite idle headroom, not a request deadline. Keep slow routes fast: the repository listing now shares one installation token and bounds permission checks with `PERMISSION_CONCURRENCY`. The worker and reaper serve no HTTP and need no setting; WebSockets have a separate idle timeout on `websocket`.

- **Steer admission locks the running request `for no key update`, not `for share`, and both halves of the fence are load-bearing.** `close` updates the same row to set `steering_closed`, and that update is what conflicts with admission's lock: a steer either commits first and the close resolves it, or waits, re-reads the row closed, and becomes a turn. `for share` would fence the close just as well and let two admissions read the backlog count together, so a fourth steer could join where only three may wait. The cost of the stronger lock is a renewal that waits behind an admission for the length of one insert. The window that matters is narrow: an admission that has read the request as open and not yet inserted. `postgres-turn-queue.db.test.ts` parks one there on purpose, with a blocker holding an uncommitted row under the steer's own id, so that test does not depend on timing. The burst test beside it also failed with the lock removed when this was built, but a burst lands in the window by chance, so do not rely on it alone. The backlog half has its own staged test, which holds the row while two admissions queue on it for the last place; it is the only test that goes red under `for share`. See ADR-0028.

- **Sidebar search reads the person's own words, never the agent's, and the reason is the event log's shape.** `agent.message` is written in coalesced pieces of about 120 characters, so a substring match over rows misses any phrase that straddles two of them, quietly and at random. `user.message` and `steer.received` hold a whole message each, so a match over them is complete; repair prompts (`payload ? 'repair'`) are the verifier's and are left out. The trigram index `events_message_text_trgm` is partial on exactly `type in ('user.message', 'steer.received')`, and the query repeats that list word for word, because the planner uses a partial index only when it can prove the query's predicate implies the index's. `session-navigation-store.db.test.ts` asserts the plan names the index with sequential scans off; reword either list and that test is what notices.

- **A settle written in SQL has to look like one written in TypeScript.** `applyNavigationChange` stamps `doneAt` with `toISOString()` (milliseconds, `Z`), and the web and the reorder check compare those strings and `Date.parse` them. The reaper's auto-settle writes the same field from Postgres's clock, so it formats with `to_char(now() at time zone 'utc', 'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')`; `to_jsonb(now())` would write `+00:00` with microseconds, which `NavigationSchema` refuses and the whole session list would fail to parse.

- **`ProjectStore.rename` defaults to `source: "user"`, so the first-prompt namer must pass `"seed"`.** A user rename is the safe default for every caller that is a person, but the namer in `turns/routes.ts` is not one: called without the argument it would mark every new project as named by hand, which silently stops the model's title from ever being asked for (docs/adr/0031). The seed form also writes only over a name that is still a seed, so a namer racing a rename cannot overwrite it. `turns/routes.test.ts` asserts the name source after a first prompt.
