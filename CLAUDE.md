# CLAUDE.md

Nap is a Lovable-style AI app builder: the user describes an app in chat, an agent writes code into an isolated E2B sandbox, and a live preview updates as it works. It is built task by task across many sessions, so **start every session with the protocol at the bottom of this file.**

## Where things are written down

| File | Answers | Read it |
|---|---|---|
| `docs/PLAN.md` | *What* v1 is; the spec and full task list (§4) | Every session, per its §1 |
| `CLAUDE.md` (this file) | *How* to work here — commands, conventions, gotchas | Auto-loaded |
| `PROGRESS.md` | *Where* we are — status and deps per task | Every session |

Keep each fact in exactly one of these. This file must never restate a task spec — link to `docs/PLAN.md` §4 instead.

## Commands

```bash
bun run test              # unit + type + db suites — deterministic and free; db needs Docker
bun run test:fast         # unit + type only — the Docker-free inner loop
bun run test:integration  # real E2B + real model calls; run at milestone boundaries only
bun run harness "<prompt>"        # one turn, printing the event stream — fakes, free, no network
bun run harness --real "<prompt>" # the same turn against real E2B + a real model; this spends money
bun run harness --real --model=anthropic/claude-opus-5 "<prompt>"  # the demo model, ~20x the cost
bun run ws:smoke          # drives /ws over a real Bun socket — fakes, free, no database
bun run typecheck         # turbo: tsc --noEmit per workspace, then a root pass for test/ + configs
bun run lint              # biome check
bun run format            # biome check --write — Biome owns formatting, don't hand-format
bun run build             # turbo build
bun run dev               # turbo dev — api on :3001, web on :3000; copy apps/api/.env.example to .env first
```

> ⚠️ **Always `bun run test`, never `bun test`.** `test` is a Bun built-in command that shadows the package.json script; bare `bun test` runs Bun's own runner over our Vitest files and reports nonsense.

A lefthook pre-commit hook runs `biome check` + `typecheck` + `vitest --changed`. It will block the commit if any fail — fix the cause, don't bypass it. The same three gates run in CI (`.github/workflows/ci.yml`) on every push to `main` and `feat/**`, so `--no-verify` only defers the failure.

## Definition of done

**No task, step, or feature is complete until all five hold.** This is a gate, not a checklist to skim — work through it before marking anything `DONE`.

**1. Gates pass.** `bun run test`, `bun run typecheck`, `bun run lint`. Read the real output. Never infer success from having written the code.

**2. Anything that guards must be seen to fail.** For a check, validator, test, or enforcement rule: deliberately break the thing it protects and confirm it catches the breakage, then revert. *A check that has never been observed failing is not known to work* — it may be silently passing on everything.

**3. Integration review — the step that gets skipped.** Ask explicitly, every time:

   - **Is the new code inside *every* existing gate?** A new directory is not automatically typechecked or linted. Verify, don't assume.
   - Does it interact with the hooks in `.claude/settings.json`, lefthook, or CI?
   - Does any existing test, script, config, or glob need to learn that it exists?
   - Do `CLAUDE.md`, `docs/PLAN.md`, and `PROGRESS.md` still describe reality after this change?

**4. The task's own "Done when"** from `docs/PLAN.md` §4 is satisfied literally. It is often stricter than "tests pass" — e.g. M2-7 wants ordering tests green *10 runs in a row*; M1-3 wants a recorded cold-start time.

**5. Tree clean and committed.**

> This rule exists because it was earned. `test/` shipped outside typecheck: the suite was green, the new tests passed, and two enforcement modules sat unchecked for two commits. Step 1 passed while step 3 was never asked.

## Conventions

- **TypeScript strict.** No `any`. No non-null `!` except in tests.
- **Zod at every boundary** — env vars, HTTP bodies, WebSocket frames, persisted event payloads. Infer types from schemas; never hand-write a type alongside its schema.
- **Errors:** typed result objects for *expected* failures (sandbox unavailable, budget exceeded); thrown exceptions only for programmer error.
- **No barrel files** re-exporting across packages. Import the specific module.
- **Every exported function gets a test before it gets an implementation.** Write the test, watch it fail for the right reason, then implement.
- **Read a library's installed types before writing against it** — `node_modules/<pkg>/**/*.d.ts`, not memory. Every version surprise in this repo so far was found this way and none would have been caught by recall: zod 4 moved to `z.iso.datetime()` and a two-arg `z.record()`, drizzle 0.45's table-extras callback returns an *array*, pino takes `(options, stream)`, Next exports a `Viewport` type. Checking costs one `grep`; being wrong costs a debugging session.
- **An env key becomes required in the task that first reads it.** `apps/api/src/env.ts` validates only what the API uses today; `apps/api/.env.example` lists the rest commented out. A boot check that fails on credentials nothing uses teaches people to paste dummy values, which is worse than no check.
- **Comments explain why, and address a reader who has never seen the plan.** No task IDs (`M2-5`) in any package's or app's `src` — they are bookkeeping, they say *when* code was written rather than *why* it is the way it is, and they point at a tracker the reader cannot open. Cite a section instead (`docs/PLAN.md §5`), or just say the reason. Enforced by `test/comments.ts`; `test/` and `docs/` are exempt.

## Layout

```
packages/  shared  db  sandbox  storage  agent  context  runtime
apps/      web (Next.js)   api (Hono, runs on Bun)
```

**Dependency direction, enforced:** `runtime` → {`context`, `agent`, `sandbox`, `storage`, `db`} → `shared`.
`agent` imports the `SandboxManager` *interface*, never the E2B adapter.

This is enforced by `test/architecture.ts`, not by vigilance — adding a dependency that
violates it fails `bun run test`. Adding a new workspace package also fails the test until
you add it to the rule table there.

## Component ownership

Drift here is the most expensive kind of mistake. Before adding code to a component, check it belongs there.

| Component | Owns | Never does |
|---|---|---|
| `Runtime` | Turn lifecycle: acquire sandbox → build context → run agent → persist → publish → commit → snapshot. Budgets, cancellation, recovery. | Prompt content, model params, tool implementations |
| `ContextEngine` | Assembling context and owning the token budget + truncation order | Calling the model; deciding when a turn ends |
| `AgentService` | Driving the model loop for one turn; executing proxy tools; emitting typed events | Persistence, git, sandbox lifecycle, prompt assembly |
| `LLMProvider` | Model id, effort, thinking config, refusal/fallback policy, retries, usage accounting | Vendor abstraction — it is *not* a cross-vendor swap |
| `MemoryProvider` | `retrieve()` / `write()`. v1 is `NoopMemoryProvider` | Anything in v1 — but its call sites are real |
| `SandboxManager` | Sandbox lifecycle, filesystem, exec, preview URL | Knowing what an agent or a turn is |
| `EventStore` / `EventBus` | Durable append, **then** fanout — in that order | Business logic |

**Where tools execute:** we run no agent harness with built-in tools, because a harness's `Read`/`Write`/`Edit`/`Bash` act on the API server's filesystem, not the sandbox. `AgentService` owns its own loop over the `LLMProvider` port, and **the only tools that exist are the six in `packages/agent/src/tools/`**, every one of which proxies to `SandboxManager`. See `docs/PLAN.md` §0.

## Testing

- **`*.test.ts` → unit. `*.test-d.ts` → types. `*.test.tsx` → web. `*.db.test.ts` → db. `*.integration.test.ts` → integration.** Filename decides, not directory, so all five can sit side by side in one package. Each project exists because it needs a different *environment* — node, tsc, jsdom, a Postgres container — not for tidiness. The `.ts` infix names still match `*.test.ts`, so each of those must also be *excluded* from `unit` or it runs twice.
- **A test in the wrong project is not collected, and silently passes.** This has now bitten twice: `*.test-d.ts` files ran nowhere until the `types` project existed, and `.tsx` matched no glob at all. After adding any suite, run `vitest list --project <name>` and confirm the file appears — do not infer it from a green run.
- **Component tests query by role and accessible name**, never class names or test ids. The panes are placeholders that later tasks replace wholesale, so markup-anchored assertions would break on contact with the real thing; a role query also fails when a landmark is unreachable to a screen reader, which is worth catching.
- **The `db` suite runs against a real Postgres in a throwaway container**, one per run, migrated by `globalSetup`. It is deterministic and free, so `docs/PLAN.md` §3 keeps it in the default suite — but it needs Docker and costs seconds, hence `test:fast`. Tests share the container, so none of them may assume an empty table. Assert on SQLSTATE codes (`23505`, `23503`), not driver message text: drizzle wraps errors, so `.message` is `"Failed query: …"` and the real reason is on `.cause`.
- **Type tests are compile-time only, so they need their own runner.** `expectTypeOf` has no runtime effect: without the `types` project in `vitest.config.ts`, a `*.test-d.ts` file is never collected and a *wrong* assertion in it passes silently. That project needs `tsconfig.test-d.json` — the root `tsconfig.json` covers only `test/`, and each package's covers only its own `src`, so neither is a program containing every type test. `bun run typecheck` catches these too, via each package's own tsconfig; the two are deliberate belt and braces.
- Unit tests are deterministic and free. **If a test needs the network, it belongs in `test:integration`.**
- **Never assert on model prose.** Assert on tool-call sequences, event types and ordering, and filesystem effects.
- Fakes live in `packages/*/src/testing/` and are exported. They are production-quality code — every downstream package's tests depend on them.

## Repo-specific gotchas

Learned the hard way; don't rediscover them.

- **Packages resolve to TypeScript source**, via `"exports": { "./*": "./src/*.ts" }` in each `package.json`. Import as `@nap/shared/version`, not `@nap/shared`. There is no build step for tests or typecheck, and no root barrel to import from — which is what enforces the no-barrel-files rule.
- **Relative imports need an explicit `.ts` extension** (`allowImportingTsExtensions` is on in `tsconfig.base.json`). Safe because `tsc` never emits — Vite and Bun do the transpiling.
- **Adding a cross-package dependency requires re-running `bun install`** to create the workspace symlink, or the import resolves at typecheck but fails at runtime.
- **`bun run <script>` resolves against the nearest `package.json`, and a shell's cwd persists between commands.** A stray `cd` is enough for `bun run test` to quietly run a single package's scripts, or for `bun add` to install into the wrong workspace — both of which have happened. Run from the repo root unless you specifically mean not to.
- **Anything the root `vitest.config.ts` imports must be a *root* devDependency.** `@vitejs/plugin-react` installed into `apps/web` fails at config load with `ERR_MODULE_NOT_FOUND`, because the config resolves from the root.
- **`Omit` over a discriminated union silently collapses it.** `Omit<NapEvent, "seq">` flattens every member into one object whose `type` and `payload` are independent unions — so `tool.call` would accept a `turn.failed` payload, and adding `seq` back no longer yields a `NapEvent`. Distribution needs a naked type parameter: `T extends unknown ? Omit<T, K> : never`. `packages/shared/src/ports/event-store.ts` exports a `DistributiveOmit` doing this — use it rather than writing a second copy. The type tests caught this; nothing at runtime would have.
- **`created_at` is `timestamptz`, so the driver returns a `Date` — but the event contract types `createdAt` as an ISO string.** Whatever implements `EventStore` maps it with `.toISOString()`. `packages/db/src/schema.ts` explains why the column stays a real timestamp.
- **Read the `claude-api` skill once per milestone that touches the Anthropic API, and pin what you learn here as a gotcha.** Never answer from memory — the model id, `effort: "xhigh"`, `display: "summarized"`, `stop_reason: "refusal"` handling and tool-call mechanics are all details that change, and the intelligence plane is where a stale recollection costs most. But do not re-read it per task either: the skill inlines its whole documentation set, most of which (Managed Agents, Bedrock, Vertex, model migration) can never apply here, and it dominated one session's context to answer a single question about tool-definition shape. The first task of a milestone reads it and writes the answers down; every task after that reads *this file*. A written record is not recollection — the `usage.input_tokens`, `signal`-argument and `maxRetries` notes below are exactly that, captured once and load-bearing ever since.
- **A `PostToolUse` hook reformats each file after you write it.** So an `Edit` whose `old_string` came from text you wrote earlier in the turn can fail to match — Biome may have reflowed it. Re-read the file rather than guessing at the diff.
- **`next dev` writes `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` itself**, and re-creates them if deleted. They are committed so the tree stays clean. The generated note is worth heeding: Next 16 differs from what most training data assumes, and `apps/web/node_modules/next/dist/docs/` is the version-accurate reference.
- **Turbo runs tasks in strict env mode**, so an exported variable does *not* reach a task unless it is listed in that task's `passThroughEnv` in `turbo.json`. `DATABASE_URL=… bun run dev` silently produced a "missing DATABASE_URL" boot failure until `dev` declared it. The normal path is a `.env` file, which Bun auto-loads from the app directory.
- **`apps/api` env is validated at boot by a pure `parseEnv(record)`**, not by reading `process.env` at import time. Keep it that way — it is what lets the env tests run without mutating global state, and it keeps boot order independent of import order.
- **Bun installs and dispatches; Node executes.** `bun run` honours a binary's shebang, so Vitest and Next.js run under Node. Only `apps/api` and our own entrypoints use the Bun runtime. This is deliberate — see "Bun/Node split" in `docs/PLAN.md`.
- **E2B's contract differs from ours in three places**, all resolved in `packages/sandbox/src/e2b-sandbox-manager.ts` and all found by running the conformance suite for real. `commands.run` **throws `CommandExitError` on any non-zero exit** — ours treats a failing command as data, so the adapter converts it; without that, a failing build reaches the agent as an infrastructure fault. `AuthenticationError` extends `Error`, **not** `SandboxError`, so an `instanceof SandboxError` catch-all silently misses a bad API key. And E2B validates the *shape* of a sandbox id before looking it up: an arbitrary string is `400: Invalid sandbox ID`, not a 404, which is why the conformance harness supplies `unknownSandboxId()` rather than inventing one.
- **A `Proxy` cannot reach a class's `#private` fields.** The receiver becomes the proxy, so any method touching `#state` throws `TypeError: Receiver must be an instance of class`. Wrapping an object that has private state means spelling out the delegated methods.
- **The integration suite loads `apps/api/.env` itself**, via `test/integration-setup.ts`. Bun auto-loads that file for the API, but Vitest runs under Node, which does not — so without it every integration run would need the variables exported by hand.
- **`process.loadEnvFile` is a Node API that Bun does not implement.** It is fine in `test/integration-setup.ts` (Vitest → Node) and throws in anything run by `bun run`. Scripts under `bun run` parse the file themselves.
- **The sandbox project template is built by hand** — `bun run template:build` in `packages/sandbox`, never by a test. It publishes a named, billable artifact that later sandbox creation depends on. `packages/sandbox/template/` is a separate app with its own React/Vite toolchain: it is outside our tsconfigs on purpose, so the only thing that type-checks it is a `tsc` run *inside* a sandbox, in the integration suite. That check earned itself immediately by catching two broken imports.
- **Anything from a model that reaches a command line must be shell-quoted.** `shellQuote` lives in `packages/shared/src/shell.ts` because two unrelated callers need it — git commit messages and the `search_files` grep pattern — and the attacker is whatever the user typed into a chat box. The one deliberate exception is `run_command`'s command itself: quoting it would turn a pipeline into a filename, so what may run is the safety guard's question instead — `packages/agent/src/safety/commands.ts`. Quoting is verified by round-tripping hostile inputs through a real `sh` in the unit tests — asserting on the *shape* of the quoted string does not distinguish safe from unsafe, because the payload text is present either way.
- **A bound port is not a loadable preview.** E2B's `waitForPort` readiness check fires when something binds the port *inside* the sandbox, but users reach it through a public proxy that becomes ready separately, and its 502s during that gap are "not yet" rather than "broken". `waitForPreview` on the `SandboxManager` port polls the real URL for a 200; anything showing a preview should wait on that, not on `getPreviewUrl`, which only composes an address and promises nothing.
- **"Missing" and "could not tell" are different failures, and only one of them may fall back.** Opening a project restores its last snapshot; a snapshot that is *absent* or that git refuses falls back to a fresh template with a `system.notice`, because the work is gone either way and an error page in place of an app helps nobody. A store that cannot be *reached* fails the open instead — hand back an empty template on a transient outage and the next teardown snapshots the emptiness over a good snapshot. The same reasoning orders `packages/runtime/src/restore.ts` the opposite way round from `teardown.ts`: fetch the row and the bytes *before* creating a sandbox, so a storage failure costs nothing and leaves nothing running to be billed for.
- **The project template's `bun.lock` is tracked, which is what makes "install only if it changed" possible.** `bun install` runs during the image build and writes the lockfile into the workdir *before* `git init`, so it is in the initial commit and travels in every bundle. A restore compares the lockfile before and after unbundling, and skips the install when they match — which is what keeps opening a project at seconds rather than a minute. Nothing there boots Vite, either: `setStartCmd` already did that as part of sandbox creation.
- **E2B kills a sandbox five minutes after it is created, whatever is happening inside.** `defaultSandboxTimeoutMs` is 300 000 and the timer starts at creation, not at the last thing anyone did — so a conversation that pauses for a coffee comes back to a workspace that no longer exists, and a reaper meant to snapshot idle projects loses that race every time. Sandboxes are created with an explicit `timeoutMs` and every turn pushes the deadline back through `SandboxManager.extendTimeout`. **The relationship between the two numbers is load-bearing: the reaper's idle threshold must stay below the sandbox TTL**, because the reaper snapshots before destroying and E2B's timer does not. `apps/api/src/env.ts` refuses to boot when they are the wrong way round.
- **R2 is the S3 API, so the adapter is `@aws-sdk/client-s3` with `region: "auto"` and an account-scoped endpoint** — the bucket is a path, not a hostname. Failures are mapped by `name` and HTTP status rather than `instanceof`, because a missing object arrives as `NoSuchKey` from one call and `NotFound` from another, and the two mean the same thing. Keep `not_found` and `unavailable` apart at all costs: restoring a project falls back to a fresh template for the first and refuses to open for the second, so collapsing them loses work.
- **In the E2B base image, `/usr/local/bin` precedes `/usr/bin` on PATH.** Installing a newer Node from NodeSource lands in `/usr/bin` and changes nothing — `node --version` still reports the image's 20.9, silently, until something refuses to start. The template build relinks the binaries; anything else installing tooling into that image needs to do the same.
- **`usage.input_tokens` from the Anthropic API is the *uncached remainder*, not the input total.** Cache writes and cache reads are billed and reported in their own fields (`cache_creation_input_tokens`, `cache_read_input_tokens`), so a heavily-cached call can report a few hundred input tokens against a prompt of tens of thousands. `toTokenUsage` in `packages/agent/src/claude-provider.ts` sums all three, because a budget built on the unsummed number would be wrong by most of the prompt. There is a test pinning this.
- **The Anthropic SDK takes `signal` in its *second* argument, not the request body** — `messages.stream(body, { signal })`. And under `exactOptionalPropertyTypes` a narrow client type must say `signal?: AbortSignal | undefined`, since "absent" and "present but undefined" are different types and no-signal is the normal case.
- **The SDK's own retries are invisible to a test.** `new Anthropic()` retries twice by default, so a provider that also retries makes three attempts look like nine and "gives up after N" unprovable. `ClaudeProvider` constructs the client with `maxRetries: 0` and owns the loop.
- **All of a turn's `tool_result` blocks go back in one user message.** Parallel tool use is on by default: a single assistant message can carry several `tool_use` blocks. Answering them in separate user messages is accepted by the API and quietly trains the model to stop asking for tools in parallel — the failure is a slower agent, never an error. Execute the batch, then send every result together, including the failures: a failed tool is a `tool_result` with `is_error: true`, never a dropped block. This is the shape `executeTool`'s `ok` field exists to feed.
- **`@anthropic-ai/sdk` and `@anthropic-ai/claude-agent-sdk` are different products.** The first is the Messages API client this repo uses. The second is Claude Code packaged as a library — it owns the agent loop and ships the built-in `Read`/`Write`/`Edit`/`Bash`. We want neither of those: the loop has to emit typed events and be cancellable, and the only tools that may exist are the six that proxy to `SandboxManager`. The plan originally specified the second one — see the amendment note in `docs/PLAN.md` §0 for why it did not survive contact with the testing strategy.
- **A tool call and its result travel together or not at all.** The API rejects a `tool_use` block with no answering `tool_result`, and vice versa — so anything shortening a conversation to fit a budget cannot simply delete the biggest block it finds. `NapContextEngine` reclaims tool output by replacing the *content* while keeping the block and its `toolCallId`, and drops history a whole turn at a time so both halves leave together. Deleting a result to save tokens does not produce a smaller request, it produces a 400. There is a test asserting no orphan in either direction, at five budgets.
- **The system prompt has no "verify your work" instruction, and that is the design.** `claude-opus-5` already checks its own work; telling it to do so again produces redundant tool calls and long reports *about* the checking rather than fewer mistakes, and removing such instructions costs no capability. The omission reads as an oversight, so `system-prompt.test.ts` fails on a phrase list plus any `/\bverif/i` match. If you are about to "improve" the prompt by adding a verification step, that is the thing this is here to stop.
- **The prompt's facts must match `packages/sandbox/template/` exactly.** The first draft claimed a `public/` directory the template does not have and said nothing about Tailwind v4 having no config file. Neither produces a confused agent — both produce a confident one, writing files nothing serves. Tests pin both.
- **The context token budget is a cost limit, not the model's context window.** `claude-opus-5` accepts 1M tokens; `DEFAULT_BUDGET_TOKENS` is 120k, and the gap is deliberate — a bigger window is not a reason to raise it. Token counts are a local estimate (~4 chars/token) because the exact number is a network call per string, which would make the budget untestable and every turn a round trip.
- **Anything that can spend real money defaults to the free path.** `ClaudeProvider` takes `model`, `effort` and `maxTokens`; `bun run harness` runs on `ScriptedLLMProvider` + `InMemorySandboxManager` unless given `--real`, and a real run defaults to Sonnet at `medium` with 12 steps and a 40k context budget. The fakes exercise the same composition the real components plug into, so the wiring is verifiable for free and spend is reserved for what only a real API can prove — the request shape, and that a real sandbox ends up with a real commit. Build the free half first, and ask before spending.
- **Bedrock is a transport, not a vendor — and its client throws before it ever reaches the network.** `packages/agent/src/bedrock.ts` reaches the same models through an AWS account: same Messages API, same `tool_use`/`tool_result` blocks, same streaming, same refusal semantics, so nothing above `LLMProvider` can tell the difference. Only two things change — the client class and an `anthropic.` model-id prefix. `AnthropicBedrockMantle` **throws at construction** when no region resolves from `awsRegion`, `AWS_REGION` or `AWS_DEFAULT_REGION`, which is why callers check for a region themselves rather than letting a stack trace stand in for a sentence. A Bedrock API key goes in as `apiKey` (bearer) or `AWS_BEARER_TOKEN_BEDROCK` — no SigV4 needed. None of this weakens the no-second-vendor rule below; that rule is about *different vendors*, whose failures are silent.
- **OpenRouter is the only route this project uses, and it reaches every vendor's models — not just Anthropic's.** It publishes a *native Anthropic Messages endpoint*, so `@anthropic-ai/sdk` reaches it with `baseURL: "https://openrouter.ai/api"` — note the root, not `/v1`, because the SDK appends `/v1/messages` and a doubled `/v1/v1/` 404s in a way that reads like the service is missing. **Their docs hedge that the endpoint is designed for Anthropic models; that is not a restriction, and it was measured rather than assumed.** A request to `openai/gpt-5.6-luna` comes back as a well-formed `tool_use` block with `stop_reason: "tool_use"`, accepts `cache_control` markers without complaint, and — the part that matters — reports `usage` in *Anthropic's* shape (`cache_read_input_tokens`), not OpenAI's `prompt_tokens_details.cached_tokens`. That is what keeps `toTokenUsage` honest, and it is exactly why nothing goes near the OpenAI-shaped `/chat/completions` endpoint, which returns the other shape and would make `TurnBudget` under-count silently. **Mind the separator** — OpenRouter namespaces with `anthropic/`, Bedrock with `anthropic.`; `toOpenRouterModel` therefore passes through any id already containing a `/` and prefixes anything else, so `openai/gpt-5.6-luna` survives and a bare `claude-sonnet-5` still becomes Anthropic's. Pricing is each vendor's own plus a top-up fee, so Claude through here is Anthropic's price and buys *access*, never savings; the savings come from choosing a cheaper model.

- **OpenRouter reserves the whole of `max_tokens` against your balance before the request runs, which Anthropic does not.** Anthropic bills tokens *generated*, so a high ceiling on a short answer is free; OpenRouter treats the ceiling as admission control and answers `402 "You requested up to 64000 tokens, but can only afford 418"` before the model sees anything. So `DEFAULT_MODEL_CONFIG.maxTokens` (64k) needs roughly $1.60 of credit on Opus 5 just to be *allowed* to ask a one-line question. Budget by the ceiling on this route, not by the expected answer. The failure costs nothing and is not retried — `isRetryable` only retries 5xx, rate limits and dropped connections, so a 402 stops at the first attempt.

- **OpenRouter does not implement `messages.countTokens` — it 404s** — and that turned out to be a better test rather than a worse one. Counting the prefix and comparing it to the documented minimum only supports an *inference* that caching will happen; a non-zero `cache_creation_input_tokens` on a real call **is** the claim. `prompt-caching.integration.test.ts` now sends the real `SYSTEM_PROMPT` + `TOOL_DEFINITIONS` and asserts on the counters, which works on every route. Related and sharper: **an assertion that a cache entry was *written* is clock-dependent.** An entry lives ~5 minutes, so re-running inside the TTL finds the prefix warm — `cache_creation_input_tokens` is 0, `cache_read_input_tokens` is thousands, and the test fails against code that is working perfectly. The fix is to salt the prefix with a `crypto.randomUUID()` line so every run starts cold; without it the test measures how recently you last ran it.- **Debug on `openai/gpt-5.6-luna`, demo on `anthropic/claude-opus-5`.** Most turns during development are spent debugging the loop — event ordering, tool sequencing, did the commit land — which needs a model that returns well-formed tool calls, not a good one. Luna is ~$0.10/$0.60 per MTok against Sonnet 5's $2/$10, so an afternoon of running the loop costs cents rather than dollars; that is the whole reason it is the `NAP_MODEL` and `HARNESS_DEFAULTS` default. **What crossing vendors actually costs is two things, and OpenRouter's translation absorbs both:** `toTokenUsage` sums `input_tokens` with both cache fields because Anthropic reports the uncached remainder, where OpenAI's `prompt_tokens` already includes cached tokens — same code, double count; and Anthropic answers N tool calls in **one** user message where OpenAI wants N `role: "tool"` messages, inverting the rule `agent-service.test.ts` pins. - **CORS credentials and a wildcard origin are mutually exclusive, so the web origin is configured rather than reflected.** A browser will not attach a cookie to a cross-origin request unless the response names the origin exactly *and* sets `Access-Control-Allow-Credentials` — `*` with credentials is refused outright. `apps/api` had no CORS middleware at all until sign-in needed one, which meant the browser could not reach the API from `:3000`; every hand-written call now goes through `apps/web/src/api/credentialed-fetch.ts` so `credentials: "include"` lives in one place instead of four.

- **Authorization is deny-by-default, and the route table is what enforces it.** A `requireUser()` call at the top of each handler protects the routes somebody remembered; the failure worth designing against is the route added later by someone who did not know to add it. So one `app.use("*", requireUser(...))` sits ahead of every route in `apps/api/src/app.ts`, and the only public paths are the three named in `require-user.ts` — `/health`, `/api/auth/*` (you cannot require a session to reach the thing that issues sessions) and `/auth/providers`. **`authenticate` being absent means refuse, not allow**, so an app wired up without it reaches nobody's data. `route-coverage.test.ts` reads Hono's own `app.routes` and fails naming any route missing from `route-table.ts`, in both directions — an unclassified route *and* a table entry for a route that no longer exists, since the second is an authorization test passing against nothing. **Another user's resource is 404, never 403**: a 403 confirms the row exists, which is a fact about someone else's data. Ownership is enforced in the *query* — `ProjectStore` takes a userId and `SessionRecord` carries one down from the join `PostgresSessionStore` already performs — because a filter a handler has to remember is one that will eventually be forgotten, silently. **The fakes enforce it too**: `InMemoryProjectStore` filters on the id rather than accepting and ignoring it, or every authorization test above it would pass against a store that leaks.

- **Both spending limits live at the turn route, and they answer differently on purpose.** `POST /sessions/:id/turns` is the only way to start a turn, so it is the only place either ceiling has to be applied. A rate limit is a *speed* problem — **429 with a `Retry-After` header**, not just a body, because that header is what a proxy or client library obeys on its own. A sandbox quota is a *state* conflict — **409**, since the fix is closing a project rather than waiting, and a `Retry-After` would be a lie. Both carry a `code` so the browser tells them apart without parsing prose. Three things are load-bearing and each was a mutation: **a refused attempt does not consume the allowance** (otherwise a retrying client pushes its own recovery away forever, and the advertised wait never arrives); **the limiter window slides**, so `Retry-After` can be computed exactly rather than guessed at a fixed boundary; and **a turn whose project already has a sandbox skips the quota entirely**, or the cap silently means "projects you may talk to" and a user at their limit finds the conversation they are in has stopped accepting messages. `NAP_MAX_SANDBOXES_TOTAL` is a process-wide ceiling beyond what the milestone asked for: per-user limits alone multiply by the number of users, which is the arithmetic that matters the first time strangers use it.- **The command guard matches the *head of a shell segment*, never a substring.** `inspectCommand` splits on `;`/`&&`/`||`/`|`, pulls `$(…)` and backticks out as commands of their own, follows `sh -c`, and strips `sudo`/`env`/`VAR=x` — then matches only the resulting command name. - **Every failure's wording lives in `apps/web/src/errors/failure-copy.ts`, and the recoveries deliberately differ.** Three surfaces can describe the same `turn.failed` — the transcript, the preview pane, the box you type into — and left alone each grows its own vocabulary, so one failure reads as three problems depending on where you look. - **The landing page's rim light is a canvas raster, and the order of its beats is what makes it affordable.** `apps/web/src/glow/` masks each glow layer with a PNG it draws — `roundRect`, stroke with a conic gradient of *opacity*, blur, `toDataURL` — because a width-20 stroke blurred 32px is a soft band that reads as light, where a bordered box with a CSS blur reads as a lit border. **Every angle the pulse animates is a registered `@property`**; an unregistered custom property has no type, so the browser cannot interpolate it and the gradient jumps between keyframes instead of sweeping — silent, and it looks like a broken easing curve. - **`background-clip: text` and an animated element are mutually exclusive, and the failure is a blank page.** An element running an animation of opacity, transform or filter is composited into a layer of its own, and a composited descendant contributes *nothing* to an ancestor's text clip — so a heading clipped to text whose words animate has no glyphs to clip to, paints no background, and renders its `color: transparent` ink as nothing at all. No error, no warning, no clue in the computed styles, which all read exactly as intended. The landing headline hit this and the effect was cut rather than worked around; anything reaching for clipped text again needs the clip and the animation on *different* elements, one animation each. Related, for whoever tries the sweep again: `background-attachment: fixed` is what makes separate word boxes share one band of light instead of each staging its own flash, and **percentage background positions run backwards** when the image is wider than its positioning area.

- **A real browser is two commands away, and this repo's effects need one.** Chrome is at `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`; `--headless=new --screenshot` is enough for a static look, and anything involving animation needs `--remote-debugging-port` plus a CDP socket, because `--virtual-time-budget` does **not** advance CSS animations — a page screenshotted that way shows every `animation-fill-mode: both` element holding its *first* frame, which looks exactly like the bug you are hunting. Driving it properly also allows `Emulation.setEmulatedMedia` for `prefers-reduced-motion`, and `Runtime.evaluate` to read computed styles and `getAnimations()` off the live page. The invisible-headline bug above survived four wrong hypotheses and was found in one screenshot.

- **`data-no-trail` is a page-wide contract, not a prop.** The landing page's badge trail refuses to drop a badge onto any element carrying that attribute, and deflects its phantom cursor around one — the hero's content column, the footer line and each end of the header bar wear it today. An attribute rather than a ref because the things to avoid are not the trail's siblings: the header is drawn over the stage from `landing.tsx`, two levels up, and threading a ref through would make every future overlay somebody's job to remember. Two things bit here and both are in `geometry.ts`: the clearance around text is deliberately wider than the badge-to-badge gap (a badge touching a sentence is a word with something stuck to it), and a deflected point must be pushed **half a badge past** the boundary rather than onto it — a badge is centred on the point, so a point on the edge still lands half its box inside, every drop is refused, and the trail empties while the phantom slides along a wall. That failure reads as the effect being dead, not as a rule working.

- **Hono resolves no route parameters inside a wildcard middleware, and says nothing about it.** In `app.use("*", …)` the matched route *is* `*`, so `c.req.param("sessionId")` is `undefined` even on a request to `/sessions/:sessionId/turns` — the field is simply absent, which is indistinguishable from a request that had no session. - **The log-context seam is in `@nap/shared/logging`, and the logging library is not.** Every layer has to report under the same ids and the dependency direction allows exactly one shared home, so the `AsyncLocalStorage`, the `LogContext` and a deliberately narrow `Logger` interface live in the base package — while pino, the stream and the level stay in `apps/api/src/logger.ts`, which calls `setRootLogger` once at boot. A real pino logger satisfies that interface structurally, with **no adapter and no cast**: `createLogger`'s return annotation is what proves it, and it is the one place the two shapes meet. The default root discards, so importing the module never writes anywhere. Two ways to add context and they are not interchangeable — `withLogContext` opens a scope (the request, the turn), `addLogContext` enriches the scope already open. Authentication needs the second: the caller's id is learned after the context was opened and before the request's own summary line is written, so nesting would leave the one line carrying the status code as the only line that could not say whose it was.

- **Logs carry the *shape* of a turn, never its content.** `packages/runtime/src/turn-log.ts` renders each event as `{eventType, seq}` plus identifiers — tool name, file path, failure reason, token counts — and no message text, no diffs, no command output. All of that is already in the `events` table, addressable by the very ids on the line, and that table is the audit log by design (`docs/PLAN.md` §5); copying it into logs is a second home for a user's private project with a different retention and different readers. `seq` is on every line because log timestamps are per-line and two events appended in the same millisecond sort arbitrarily by them. A test asserts no payload text reaches a field, and the `switch` over the discriminator is what makes a new event type a compile error rather than a line with only its name.

- **`/health` answers 200 even when it is degraded.** A non-2xx is how an orchestrator decides to restart or de-register a process, and neither fixes an unreachable database — it removes the instance that was still able to report it, and during a shared-dependency outage takes every instance out at once. The verdict is in the body, named per dependency. The endpoint is also public, necessarily, so `createHealthProbe` caches for 5s and collapses concurrent polls: without that, anyone who can reach it can drive unlimited load against E2B's API at our expense. Every probe has a deadline, because the characteristic database failure is an accepted connection that never answers. `E2BSandboxManager.ping()` is deliberately **not** on the `SandboxManager` port — that port is about one project's workspace and every method takes a sandbox id, while "is the provider up?" is a question about the deployment that the in-memory fake could only answer meaninglessly.

- **A health check's deadline is sized by the slowest *healthy* case, not the impatient one.** `/health`'s probe timeout was 2s and reported `degraded` on the first poll after every cold boot, because a Neon instance that has scaled to zero takes **~1.8s** to answer its first query — measured, not guessed. A false outage is worse than a missed one: it is the reading that teaches people to stop trusting the endpoint, and anything automated watching it acts on a lie. The default is 5s. The same shape of mistake is waiting in any probe pointed at serverless infrastructure that idles down.

- **`bun run acceptance` is the v1 acceptance run, and it spends real money.** `apps/api/scripts/acceptance.ts` drives `docs/PLAN.md` §6 over the real HTTP and WebSocket surface — needs `bun run dev` alongside it, takes `--keep` to leave the preview up for a demo. Deliberately absent from the permission allow-list and matched by no vitest glob, for the same reason `test:integration` is: the prompt is the only checkpoint before the spend. **Two of §6's steps are not machine-checkable and it does not pretend otherwise** — whether the preview *looks* right, and whether an edit arrived by HMR rather than a reload — so they print as `LOOK` lines while their checkable halves are asserted. Two traps it walked into, both worth not repeating: a per-turn socket opened at `seq=0` replays the whole session, so searching *all* of a stream's events for `turn.completed` finds the **previous** turn's and reports the new one finished before it started; and grepping written source for "dark"/"purple" reported a false negative against a correct app, because Tailwind v4 `@theme` tokens express it as `oklch(0.14 0.02 300)`. A third, and the only one a person rather than a test caught: **closing a project destroys the sandbox its preview URL points at**, so a URL captured before step 5 is dead by the end of the run — a restored project comes back on a *new* host and re-announces `preview.ready`, which is the announcement to print. Anything handing a preview URL to a human should poll it for a 200 first; the cost of being wrong is someone opening "Sandbox Not Found" and concluding the product is broken.

- **A turn's work reaches R2 at the end of that turn; the reaper exists to stop paying for idle sandboxes, not to keep work safe.** That split is recent and was earned. Snapshots used to happen only in `putProjectAway` — close, or the reaper — and the reaper runs in this process, so a deploy or a crash left E2B's own timer to delete the only copy of everything since the project last went idle. `captureSnapshot` in `packages/runtime/src/teardown.ts` is a teardown minus the destroy, and `SingleAgentRuntime` calls it after the turn's terminal event is persisted, so nothing the user waits on is delayed. **Only when the turn committed** — a git bundle holds commits, not a working tree, so a turn that changed nothing (and a turn that failed before `finalize`) has genuinely nothing new to capture. **A failed snapshot never fails the turn and is never shown to the user**: the work is still in the live sandbox, the reaper is still the backstop, and a warning nobody can act on is what trains people to ignore the ones that matter. Consequence worth knowing: `tearDownProject` now **reuses an unchanged snapshot** rather than re-bundling, because arriving at an already-stored commit is the normal case once turns snapshot themselves — but a `latestFor` that *fails* must fall through and capture, since knowing whether it changed is an optimisation and the snapshot is not.

- **A project outliving its sandbox is announced, and resuming one runs on the turn queue.** Nothing used to say that a sandbox had been destroyed, so a preview pane kept an iframe pointed at a host that had stopped existing — the provider's "not found" page rendered inside a frame that otherwise looks like a working app. `putProjectAway` now appends **`preview.stopped`** to *every* session of the project, keyed to the destroy rather than to the bookkeeping (a failed row update still means the sandbox is gone) and deliberately silent on the one path that leaves it serving. Bringing a project back is `Runtime.resumeSession`, on the **same per-session queue as `runTurn`** — that is the whole reason it can be offered at all, since both paths create a sandbox when the project has none and a page that resumes while its user types would otherwise start two. Its failures are a `system.notice`, never a `turn.failed`: no turn ran, and `previewState` reads a sandbox failure as the state of the last turn. `POST /projects/:id/open` applies **the same sandbox quota a turn does**, because a ceiling with two doors is not a ceiling. The one thing still not announced by anyone is a sandbox the provider reclaims on its own timer, which is why the preview pane trusts `project.sandboxId` over a replayed `preview.ready` until somebody presses Resume.

- **Anything that writes to the real bucket from a test must delete every key it wrote, not the newest one.** `full-cycle.integration.test.ts` runs against a throwaway Postgres and a *real* R2, so the rows naming its objects die with the container — it collects `snapshots.listFor` inside `beforeAll` and deletes them all in `afterAll`. It used to delete exactly one, which was correct only while a run produced exactly one; per-turn snapshots would have silently turned it into an orphan generator. There is no automatic orphan detection: the check is joining `ListObjectsV2` against the `snapshots` table by hand, and it has found real orphans.

- **Both the reasoning and the answer are streamed, coalesced, and folded back together at every layer that reads them.** The model's `thinking` and `text` deltas arrive on the SDK's `MessageStream` (`stream.on("thinking" | "text", (delta, snapshot) => …)`; the wire events are `content_block_delta` with `delta.type` of `thinking_delta` or `text_delta`, and the helper hands over *the piece, then the running total*, so forwarding the second argument repeats every earlier word in every event). `ClaudeProvider` forwards them to `LLMRequest.onThinkingDelta` and `onTextDelta`; `AgentService` buffers each through a `DeltaStream` that flushes at 120 characters or 400ms, whichever comes first, and emits `agent.thinking` and `agent.message` events. That keeps a turn at a few dozen rows instead of thousands and leaves the durable-append-then-fanout path untouched, so a reload mid-turn replays what has been written so far. **The assembled `result.text` is emitted only when nothing was streamed** — both halves of that are load-bearing and each is a mutation: emitting it as well prints the whole answer twice, and dropping the fallback means a model or route that sends no text deltas says nothing at all. **The flush sits before the refusal and error branches**, since a turn that failed is where the reasoning is the only account of what happened. Two request-level facts are easy to undo by accident: `display: "summarized"` is required, because the default on `claude-opus-5` is `"omitted"` — which still streams thinking blocks but with empty text, so the symptom is silence rather than an error — and a retried attempt is a new stream that re-sends its reasoning from the start.

- **Prose in pieces has to be rejoined in two places, and neither is optional.** `NapContextEngine` appends to the open assistant *text block* rather than pushing a new one, so the conversation the model is re-sent looks the way it did when it wrote it — one answer, not a paragraph broken at whatever sizes the network delivered, and not a message that grows a content block per event. `buildTranscript` does the same for the pane. Both join text only to text from the same speaker: a tool call between two pieces of prose means the model said two things, and folding across it would attribute the second half to before the tool ran. **A short answer looks identical either way** — its deltas coalesce into one event — so any test meaning to prove streaming needs prose long enough to cross the flush threshold, or it passes against code that streams nothing.

- **A word that animates must keep its animation class forever, not just while it is the newest.** `StreamingText` reveals only the words that just arrived, and the obvious implementation compares the current word count against the previous render's. It is wrong in a way no green test shows: a word that was new last frame is old this frame, loses the class, loses `animation-fill-mode: both` with it, and snaps from mid-blur to sharp. The stagger delay for each word index is written into a ref the first time that index renders and never recomputed. Relatedly, **the transcript folds a run of `agent.thinking` events into one passage keyed to the `seq` it opened with** — keyed to the newest event instead, the element remounts on every frame the model is thinking and restarts the reveal of every word already on screen. And **"is this passage live" is `it is the last item`, full stop**: adding a `turnStartedAt` check looks like a safety net and is a bug, because a finished turn ends *with* its terminal event (so the last line has no prose to reveal anyway) while a client that reconnected mid-turn has no `turn.started` in its log and would have the passage it is actually watching frozen.

## Session protocol

**Starting:**
1. `git status` and `git log --oneline -10`.
2. Read `PROGRESS.md`.
3. Run `bun run test` — **confirm green before starting new work.** If red, fixing it is the session's first task.
4. Pick the next `TODO` task whose deps are all `DONE`.
5. Mark it `IN_PROGRESS` in `PROGRESS.md` and commit that single-line change.

**Finishing a task:**
1. `bun run test` and `bun run typecheck` — both must pass.
2. Mark it `DONE` in `PROGRESS.md`, with a one-line note on anything surprising.
3. Commit: `feat(<scope>): <task id> <summary>`, tests included.

**Stopping mid-task:** commit `wip(<scope>): <task id> — <what's left>` and leave the task `IN_PROGRESS` with a "next step" note.

> **Never end a session with uncommitted work.** A future session cannot recover context that exists only in a dirty working tree.

Branch per milestone (`feat/m0-scaffold`, `feat/m1-execution-plane`, …), one commit per completed task.
